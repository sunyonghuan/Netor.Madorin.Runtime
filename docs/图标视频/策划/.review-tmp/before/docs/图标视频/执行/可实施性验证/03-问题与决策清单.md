# 问题与决策清单

[返回验证总览](./README.md) · [场景推演](./01-场景推演与预期结果.md) · [Provider 映射](./02-Provider字段映射与证据.md)

本清单记录文档级可实施性证据。问题结论不自动修订设计方案或既有执行文档。严重度是对其影响的工程判断，不代表代码缺陷已实测。

## 1. 验证结论

**整体可实施，有条件，不能按当前文字无歧义地直接批量开工。** 统一请求文件、Provider 内部映射、纯本地预检、异步查询/下载以及按 RID 发布都有落地路径。没有证据表明核心架构必须推翻；但通用字段归属存在上游冲突，特定异步 API、取消和超时需要先明确交接，执行文档有若干降低/改变约束的转述。跨 CLI 传同一 JSON 也不保证相同功能、参数均保留或结果相同。

目前阶段建议按下表关口推进：方案中立且已明确的契约可做最小原型；跨 Provider 是否支持某能力取决于字段映射/恢复证据；与 `agents.md` 的范围冲突在用户裁决前不固化实现。

| 结论类别 | 当前判定 | 进入实施的条件 |
| --- | --- | --- |
| 公共请求与本地处理管线 | 可原型验证 | 用假 Provider 覆盖严格 JSON、长提示词、多附件、合并、转换、丢弃和安全预检。 |
| 跨 Provider 复用 | 机制可行、语义有条件 | 每个具体任务填写字段映射表；区分原生支持/等价转换/丢弃/拒绝；调用方接受丢弃后的目标意图。 |
| 多图图片/视频 | 常见有序参考图可映射 | 每项 metadata 记录 role、顺序、数量和原生提示词位置语法；时间关键帧不冒充普通附件。 |
| 公开异步 | Provider-specific | 仅在新进程具备所需任务、路由、认证及槽位上下文时声明 `supports_async=true`。 |
| Native AOT 多 RID | 可分宿主构建和汇总 | 使用目标 OS runner/受支持环境构建；验证统一入口能调度/接收各 RID 包。RID 列表不是交叉编译保证。 |
| 真实平台/发布 | 未验证 | 后续实现后，分别提供 Native AOT 构建和目标系统实机证据。 |

## 2. 设计契约或范围的待决项

| ID | 级别 | 问题与证据 | 影响 | 建议方向及关闭条件 |
| --- | --- | --- | --- | --- |
| F01 | 严重 | 根 `agents.md:65` 将协议特定的分辨率、时长、帧率限定由 Provider 独立维护且不混入通用参数；设计第 2.3、2.4、2.5 节却把 `duration`、`resolution`、`fps` 等放入通用 `parameters` 并规定跨 Provider 转换。统一秒/像素等语义可以做中间层，但当前没有明确“协议特定字段”与“公共规范字段”边界。 | DTO、Schema 和 Provider metadata 字段归属会分叉，超出目前已授权的约束边界。 | 明确仅把可跨 Provider 解释的语义规范字段列入公共参数；供应商字段仍位于 `provider_parameters`。或先取得更新工作树约束的授权。以字段归属矩阵（含时长、分辨率、fps、seed、style、quality）经确认关闭。 |
| F02 | 严重 | 设计第 3.4 节 `provider_metadata.request_id` 可保存 Provider “请求/任务 ID”，但第 3.5 节另设查询所需 `task_id`；第 3.7 节公共失败信封没有必需 `task_id`。第 5 节又要求超时/取消保留已取得的任务 ID 并区分提交是否受理未知。 | 异步失败后主程序不能确定某个远端 ID 是追踪 ID，还是可以恢复/查询的任务句柄。 | 明确分列远端请求追踪 ID 与任务 ID，或给复用字段增加类型且失败响应可携带恢复句柄。构造“提交已被接受后本地超时/取消”失败信封用例，经主程序按 ID 恢复路径核对后关闭。 |
| F03 | 一般 | BFL 官方提交响应必需 `id` 与 `polling_url`；全局和区域端点须使用响应中的 `polling_url` 轮询。设计后续 `query` 示例仅传 `--task-id`，没有规定该额外上下文跨进程由谁持有。见[Provider 字段映射](./02-Provider字段映射与证据.md)第 4 节。 | 若任务新进程中只有 ID，不能按官方要求由方案推导查询 URL。 | 将其作为该 Provider 的异步准入门槛：定义符合安全边界的本地任务上下文传递/恢复，或不声明公开 query/download；内部一次 generate 轮询仍可单独评估。用“进程 A 提交退出、进程 B 仅接恢复上下文完成查询”的 Provider 专项原型关闭。 |
| F04 | 一般 | 设计第 5 节要求宿主显式通知子 CLI 取消，但没有给通知通道、取消触发、超时宽限以及 Windows/Linux/macOS 的落地方式。根 `agents.md:65`、`:69` 又要求取消合作和停止写新产物。 | 宿主取消等待可能只停止等待而非取消 CLI；强杀则不保证结构化 JSON 和清理。 | 对承诺协作取消的宿主集成，在对应执行文档确定平台调用/接收方式、传到 Provider 的取消 token、退出宽限及强杀边界；不得在本清单中直接新增公共取消选项。每目标 OS 有离线生命周期证据后关闭。 |
| F05 | 一般 | `--timeout` 定义提交/轮询/下载总时限，但没有规定从命令入口、完成本地校验或开始远端操作哪个时刻起算；媒体读取/编码/上传前置阶段是否占用时限也不明。 | 同样的数值在不同 Provider/实现中会在不同总耗时触发，宿主等待预算无法一致推导。 | 在原型/实现执行约定中确定统一单调时钟起点和计入阶段；另计最多 5 秒取消清理。用附件准备 + 远端延迟的边界场景唯一判定是否 timeout 后关闭。 |
| F06 | 一般 | 设计第 2.1 节称 `--verbose` 不得改变 stdout JSON；第 2.3 节把 `execution.verbose` 与该开关等同；第 2.9 节要求预检回显显式输入和有效参数。因此预检切换 `verbose` 会使回显字段变化。 | 严格按字面同时实现两条规则不可能。 | 明确“不改变 stdout JSON”的不变量范围：建议保持 Provider request/业务结果/产物不变，允许输入控制值在 try-run 回显中反映；或决定排除回显并同步修订回显范围。用同请求 `verbose=false/true` 比对预检报文关闭。 |
| F07 | 一般 | xAI video `keyframes[]` 项需要图片和 `timestamp_s`；统一附件对象只有 `id`、`role`、`source`。这是 Provider 特有时间轴结构，不能直接套用通用附件数组。 | 通用附件顺序不能表示关键帧时间；但现有设计允许 Provider 专用参数及其嵌套 Schema，并未要求为此修改公共契约。 | 将源引用、时间戳、顺序和边界纳入目标 Provider 的专用 Schema/映射；若复用附件文件，另写明确关联规则；不声明该任务时不阻塞基础 CLI。 |
