# 小型计划功能使用指南

> Expert 模式内置的轻量执行计划系统

## 为什么需要计划？

当任务复杂度中等（需要 3~12 个明确步骤）时，让 Agent 自己维护一个结构化的计划，能带来以下好处：

- 清晰的进度可视化
- 更好的上下文注入（每次调用模型前自动带上当前计划状态）
- 支持中断后恢复
- 降低 Agent 遗漏步骤或重复执行的风险

## 计划的生命周期

一个计划包含：
- `title`：计划标题
- `steps`：2~15 个步骤
  - `stepId`（自动生成，如 `step-1`）
  - `title`
  - `description`
  - `agentName`（可选，建议由哪个 Agent 执行）
  - `status`：pending / running / completed / failed / skipped
  - `progress`：0~100
  - `result` / `errorMessage`

计划状态会自动推导：
- 全部完成 → Completed
- 任意失败 → Failed
- 有 running → Running
- 否则 Pending

## 核心工具

### 1. create_plan

创建新计划。

参数示例：
```json
{
  "title": "实现用户登录功能",
  "steps": [
    {
      "title": "调研现有认证模块",
      "description": "分析当前项目的认证代码和依赖",
      "agentName": "code-researcher"
    },
    {
      "title": "设计登录接口",
      "description": "定义 API 契约、错误码和安全要求"
    },
    {
      "title": "实现后端登录逻辑",
      "description": "包含密码校验、Token 生成、刷新机制"
    }
  ]
}
```

工具返回计划 ID 和步骤概览。

### 2. execute_step

执行某个步骤并标记完成。

```json
{
  "stepId": "step-2",
  "notes": "已完成接口设计，文档已更新到 docs/api/login.md"
}
```

执行后该步骤状态变为 completed，进度 100%。

### 3. get_plan

查询当前活跃计划的完整状态（包括所有步骤的当前进度）。

### 4. update_step_status

手动更新步骤状态（用于跳过、标记失败等）。

```json
{
  "stepId": "step-3",
  "newStatus": "skipped",
  "notes": "该步骤已由其他任务完成"
}
```

### 5. abandon_plan

放弃当前计划。所有未完成步骤会被标记为 skipped，计划状态变为 Cancelled。

## 计划如何影响模型行为？

每次模型调用前，Runtime 会自动把当前计划以结构化文本形式追加到 System Prompt 末尾，格式大致如下：

```
## 📋 Active Execution Plan

**Goal:** 实现用户登录功能
**Status:** Running
**Progress:** 33%

### Steps:

✅ **Step step-1**: 调研现有认证模块 (Completed)
▶️ **Step step-2**: 设计登录接口 (Running) [████░░░░░░] 40%
⬜ **Step step-3**: 实现后端登录逻辑 (Pending)

### 🎯 Next Action:
Execute **Step step-2** using `mcli_expert_execute_step`
```

这能显著提升 Agent 的“自我觉察”能力。

## 使用建议

### 什么时候用计划？

推荐使用：
- 需要明确多步拆解的任务
- 希望记录每一步的产出
- 任务可能跨多次对话（需要恢复）

不推荐使用：
- 简单问答
- 高度开放的创意任务
- 步骤数超过 15 或需要非常动态调整的任务

### 计划 vs Agent 自己维护 TODO

- 内置计划：结构化、自动注入、支持工具化更新、文件持久化
- Agent 自己维护 TODO：更灵活，但容易遗漏或格式不一致

对于 3~12 步的任务，强烈建议使用内置计划。

### 恢复机制

- 只有状态为 `Pending` 或 `Running` 的计划才会被恢复
- 计划按 Session 隔离
- 如果检测到损坏或滞后的计划指针，会安全回退，不会错误恢复旧计划

## 示例流程

1. Agent 收到复杂需求后，先调用 `create_plan`
2. 模型返回计划创建成功
3. Agent 开始执行第一步，完成后调用 `execute_step`
4. 计划状态自动更新并注入到下一次提示词中
5. 全部完成后，Agent 给出最终总结

如果中途用户中断，下次使用同一个 Session 启动时，计划会自动恢复。

## 与并行作业的结合

计划中的某一步可以是“并行执行多个子任务”：

- Step 3：并行完成前端 + 后端实现
  - 在这一步内部使用 `mcli_agent_job_create_many`
  - 等所有 job 完成后，调用 `execute_step` 标记本步骤完成

这样既保留了计划的结构化，又获得了并行的好处。

## 故障处理

- 某一步失败：可以 `update_step_status` 标记 failed，然后决定是重试还是跳过
- 计划不再需要：调用 `abandon_plan`
- 想从头开始：先 abandon，再创建新计划

## 最佳实践

1. 计划标题要简洁具体
2. 每个步骤的 description 写清楚“要做什么”和“产出是什么”
3. 尽量为步骤指定合适的 `agentName`
4. 重要步骤完成后及时更新状态和 notes
5. 不要让计划无限增长，超过 15 步建议拆分成多个计划
