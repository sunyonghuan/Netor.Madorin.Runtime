# 执行步骤 01：P0 工具结果附件映射与上下文保护

> 状态：本地实现与门禁通过；真实厂商支持未验收。图片映射、完整性、取消和 SDK 缓冲采样已完成，按第 5 节保留真实端点未验证标记，不能视为整个附件功能完成。
>
> 优先级：P0，必须最先完成。完整架构见[专项改造方案](../方案设计/13-本地文件附件读取与Provider双向收发改造方案.md)第 3.4.2、9 节。

## 1. 问题与目标

当前 OpenAI、Anthropic、Kimi、DeepSeek 对复杂 `ToolResultContentBlock` 使用 `ConvertToolResult` 将 `ContentBlock[]` 序列化为 JSON。结果里的 `BlobRefContentBlock` 只留下 BlobId、MIME、长度等引用元数据，真正文件内容没有映射成 Provider 附件 part。模型得到的不是该文件。

修复不能简单把整个附件 Base64 塞入 FunctionResultContent：那会令文件进入普通文本/JSON 请求，放大 payload 与 token/context 消耗，并可能撞请求大小与上下文限制。

目标：

- 对只有文本的工具结果保持原有文本映射。
- 对包含 Blob 引用的工具结果，Provider 请求实际携带符合该 API 协议的附件 part 或受控上传后的 file_id。
- 内部只传 Blob 引用和有界元数据；完整字节只经 Blob 通道及 Provider 附件传输。
- 若附件不能放入 tool result，Provider 请求投影保留完整的 tool_call/result 关联，再将实际附件放入协议允许的关联消息/part。不得篡改权威历史。
- 暂不等文件工具、外部路径权限和 Worker 双向 IPC 全部完成；使用已有进程内 Resolver/Fake Provider 测试构造 P0 行为。

## 2. 不变量

1. 拒绝“只把 `blob_ref` JSON 交给模型、却声称附件已发送”。
2. 拒绝把附件完整字节、Base64、data URL 或 byte[] JSON 写入 `FunctionResultContent`、普通 `TextContent`、prompt 或协议错误回退文本。
3. 简短 JSON 元数据可以包含文件名、MIME、长度、SHA-256 和内部引用；它不是文件内容。绝对本地路径、宿主私有 Blob 路径和授权凭证不得发给 Provider。
4. 不按用户手写的 Vision/Audio/Files 能力字段删除附件或阻止请求。服务端返回的错误须保留；哈希、租期、配额和本地授权失败仍由 Runtime 阻止。
5. Provider 输入投影只操作请求副本；CanonicalHistory 中 tool call/result、CallId 和原始 BlobReference 不变。
6. 多个并行 tool call 的结果必须保持 CallId 配对和顺序；没有直接附件表达的 API 只能按该厂商协议生成兼容请求副本。
7. 不能可靠表达附件的 Provider/API 路线要明确失败并报告缺失 codec，不得把引用 JSON 伪装成成功发送。

每个文件修改前检查它所在目录 README；目录无 README 时跳过该项。当前已调研的候选点包括 OpenAI/Anthropic/Kimi/DeepSeek 的 `ConvertToolResult`、异步 `ConvertMessages`、Capability Validator 和 RequestCompatibilityProjector。不要假设位置/签名未变。

具体执行：

1. 固化测试夹具：构造文本+附件工具结果，包含 tool call、同 CallId 工具结果、JSON 元数据与 BlobRef；Fake Resolver 提供可校验的 PNG 字节和文件名。另提供超大二进制 fixture 用于检查序列化大小与内存路径。
2. 先写失败测试：捕获四个直接 Adapter 的 Provider 请求，断言附件字节没有被转入 FunctionResult JSON/普通文本，且存在预期的真实附件输入结构或正确的“该 API 路线不能表达”错误。
3. 将同步 `ConvertToolResult` / `ConvertMessages` 调整为能异步解析嵌套 Blob；递归遍历 `ToolResultContentBlock.Content`，逐个调用受控 Resolver 并校验引用元数据。
4. 先按 OpenAI Responses、Anthropic Messages、DeepSeek/Kimi OpenAI-compatible 当前真实 API 区分 tool result 多模态表达。某路线无 tool-result 附件 part 时，生成独立 Provider Request Projection：回执必须可关联，附件进入厂商允许的图像/文件输入位置；禁止以通用串接字符串代替协议映射。
5. 只有文本的工具结果仍以纯文本映射，避免为兼容附件把所有工具结果结构化为长 JSON。
6. 如果协议同时需要保留 JSON 状态和附件输入，两者按不同 part 表达；JSON 严格排除原始字节、Base64/data URL 及未经需要的冗长 Blob store metadata。
7. 修复 Capability Validator/Projector 中 Blob 根据 Vision/Audio/Files 手填值被拒绝/丢弃的分支；只改附件 case，不放宽 reasoning、tool_calling、structured output 等无关能力。
8. 保留 Blob SHA-256/MIME/长度校验、授权域检查与取消传播。Resolver 未配置、Blob 越权、过期或不完整必须失败，不能降级为引用 JSON。
9. 检查所有基于 `Microsoft.Extensions.AI` 的 Adapter 路径是否真实支持相应 `AIContent` 组成；测试要审查最终 HTTP 请求结构，不只审查转换对象类型。区分内部 Invoke/工具结果文本与 Provider 网络协议的原生附件字段：某些 API 的图片 part 会在 JSON 请求体中使用 Base64/data URL，这本身不等于把附件塞入 prompt；只要字段/编码符合该厂商协议，且内容没有复制进普通文本或工具结果 JSON，即可作为网络边界编码。

## 4. 自动化测试

- 对 OpenAI、Anthropic、Kimi、DeepSeek 各加一条嵌套附件工具结果请求测试，断言工具回执和附件分别映射到正确协议结构。
- 对仅文字结果保留原有请求结构的回归测试。
- 对顶层 User Blob 与工具结果内嵌 Blob 分别测试，不得以顶层 Blob 测试代替。
- 对多个并行 tool call 验证每个结果仍匹配正确 CallId，附件没有串位、丢失或重复。
- 在 `Vision=false`、`Audio=false`、`Files=false` 或这些字段缺省下，测试仍把 Blob 送入真实转换/HTTP 请求，不出现本地能力拦截或兼容投影静默删除。
- Resolver 返回错误长度、错误 SHA-256、错误 MIME、过期/缺失 Blob 时确认请求不发送且输出可诊断失败。
- 使用非文本随机二进制构造请求，检查附件 payload 未被内联到 Worker Invoke JSON、普通 prompt、FunctionResultContent 或工具结果 JSON；对 Provider 网络请求按具体协议检查原生附件 part（包括协议要求的 Base64/data URL）或上传引用，并分别统计文本/工具结果与附件编码体积、token/context accounting 和缓冲峰值。
- 测试取消在读取大 Blob 期间可传播、结束且不残留后台读取。

## 5. P0 验收门禁

- 四个直接 Adapter 的工具结果附件都能生成正确附件协议结构，或该 API 不支持时明确拒绝，绝无“引用 JSON 当附件”的假成功。
- 顶层附件输入路径保留且有独立回归，不被工具结果修复破坏。
- Worker Invoke JSON、普通 prompt 与 FunctionResultContent 不含附件全文、Base64、data URL 或 byte[] 数组；Provider 网络请求只在厂商协议明确要求的附件字段中编码附件，或使用已验证的上传引用，不将其作为普通文本计入工具结果/上下文。
- 多工具结果配对稳定，CanonicalHistory 未被 Provider 投影改写。
- Debug/Release 相关项目零警告构建；四个 Provider 定向测试通过；协议/序列化快照逐项检查。
- 真实厂商尚无凭据时标为“网络结构测试通过、厂商支持未验收”，不能把 P0 本地完成标成整个附件功能完成。

## 6. 不在本步骤做

- 不加 `mcli_fs_attach`、不改文件读写权限、不过度放宽工作区边界。
- 不改 Worker IPC；本阶段的进程内注入只用于先解决请求模型语义和 P0 上下文/序列化错误。
- 不承诺视频、音频、PDF 或 Provider 输出附件能力。随后步骤逐项扩展。
