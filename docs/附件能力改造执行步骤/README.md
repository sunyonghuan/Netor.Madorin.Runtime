## 全局约束

1. 按 01 -> 02 -> 03 -> 04 -> 05 -> 06 -> 07 推进。每阶段完成并通过其门禁后才进入后续阶段；除明确写出的并行子任务外，不跨阶段提前假设接口已经存在。
2. 01 是当前优先任务，也是附件功能的 P0。先修工具结果请求投影与回归测试，不等整个读取/授权系统完成。
3. JSON 只传有界控制数据、元数据和 Blob 引用。完整附件走 Blob 通道与 Provider 原生附件 part/上传引用；不得把附件字节、Base64、data URL 或逐字节 JSON 数组塞进 FunctionResultContent 或 prompt。
4. 附件传输不由用户填写的 Vision/Audio/Files 能力决定。模型不支持时保留真实 Provider 错误，不在 Runtime 静默过滤、摘要替代或切模型。
5. 十个 Provider 分别验输入和输出。共享 Adapter 的代码路径、HTTP 200、假文件请求中出现 Base64或模型口头说“收到了”都不是完整附件验收。
6. 宿主已有的 NeedsPermission、Grant 保存和回填链路应复用；工作区外读/写范围通过现有读/写根 Grant 表达，不另造外部权限字段或第二个附件发送授权。
7. 新协议字段、联合类型、Worker 帧、Source Generation、协议快照、持久化和 AOT 变更按现有门禁执行。每次实施先检查目标目录 README 和最新源码。

## 范围边界

- P0 先保证工具返回附件不会丢失为引用 JSON，并且不会为修复而导致上下文爆炸；P0 不要求先完成视频上传、外部路径授权 UI 或 Provider 输出附件。
- 附件读取从 `mcli_fs_attach` 开始；现有 `mcli_fs_read` 保持文本读取语义。
- 第一轮优先图片二进制端到端；PDF、音频、视频逐类接入并有大小、格式、服务端/API 证据。不得把一种模态的通过报告外推为所有附件支持。
- 本专项不增加图片/视频生成业务、不自动 OCR/抽帧/转码，也不修改无关 Provider 能力。
