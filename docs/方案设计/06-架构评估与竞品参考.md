> 本文对 Madorin AI Runtime V1 的架构设计进行系统性评估，并以 Claude Code CLI、Codex CLI 作为业界参考坐标，识别架构优势与真实风险。

---

## 1. 架构定位的本质差异

在评估之前，必须先明确 Madorin 与 Claude Code / Codex CLI 的根本性差异：

| 维度 | Claude Code / Codex CLI | Madorin AI Runtime |
|---|---|---|
| 产品形态 | 面向开发者的单进程命令行工具，打开即用 | 带 CLI 入口的常驻 Runtime + Client SDK，CLI 是调试入口而非主路径 |
| 架构模型 | Monolithic CLI，内建 AI 执行循环 | Client-Runtime 分离，双进程通过版本化 IPC 协议通信 |
| 集成方式 | 终端直接使用 | 宿主程序通过 Client SDK + 版本化协议调用 |
| 定位目标 | 开发者工具，快速可用 | 可嵌入的 AI 执行引擎，服务主程序 |

Madorin 和 Claude Code 不是同一类产品的竞争实现，而是处于架构栈的不同层级。CLI 作为备用与调试入口是产品本身的策划定位（见 §4A），不是缺陷。

## 2. 架构优势

### 2.1 协议优先设计（Protocol-First）

这是整个架构最核心的优势，也是与 Claude Code / Codex CLI 最大的结构性差异。

Claude Code 的主程序与 AI 执行耦合在同一进程内，宿主程序若要集成只能 fork 进程并解析 stdout——这正是本项目设计文档明确禁止的路径。Madorin 从协议第一版就建立了：

- 全局单调序号（GSN）+ Run 内序号双轨事件流
- 版本化消息信封（protocolVersion、correlationId、gsn、runSequence 全部字段）
- 断线重放（`events.acknowledge + events.replay`）
- 工具幂等键（callId）+ 权限申请握手（tool.permission.request / response）

IPC 双通道协议的复杂度是架构本身的组成部分，不是外部风险，是为实现断线恢复、事件重放、多 Run 隔离这些目标而必须承担的设计决策。

### 2.2 四级执行层次结构清晰

```
Session → Run → AgentInvocation → ProviderRequest
```

每一层职责边界明确，状态权威方唯一（见 README §7.3 状态权威表格）。这解决了多 Agent 场景下 Claude Code 完全没有暴露的问题：会议模式里谁是当前发言者、工作模式里哪个子智能体在执行哪个步骤，以及各自的工具调用权限是否继承。

架构修订文档（02）把 Turn/Run 混用问题升级为阻断级修订并强制落地 `AgentInvocation` 层，这是在开发过程中主动识别并纠正结构性问题的决策。

### 2.3 Next-Turn Selection + Session 不中断切换

同一 `sessionId` 内支持流式输出进行中提交新的 Selection（Provider、模型、Agent、提示词）、当前流正常结束、下一轮立即生效——这整条链路在 Claude Code 里完全不存在，因为 Claude Code 不维护持久 Session 层。这是 Madorin 作为 Runtime 而非 CLI 工具的核心差异化能力。

### 2.4 持久化设计扎实

JSONL + SQLite 双轨设计（正文写文件、索引写 DB、先落文件再更新索引）是业界成熟的 append-only 存储模式。Blob 内容寻址（SHA-256 前缀分片）、崩溃恢复（端行检测 + `.jsonl` 重建 `state.db`）、Session 游标分页（`updatedAt + sessionId` 复合游标，避免大 OFFSET）都是有经验的工程决策。

### 2.5 工具权限模型严格

Grant 系统（委派链、`allowDelegation` 控制、子智能体默认不继承权限、多策略取交集）比 Claude Code 目前的白名单粒度细得多。路径边界校验（符号链接 / Reparse Point 二次校验、规范化副本仅用于权限判断不覆盖原始值）显示对 Windows 文件系统攻击面有明确意识。

### 2.6 三种运行模式已经过迁移验证

Expert / Meeting / Work 三种模式的业务逻辑来自当前 Netor.Cortana.AI 的迁移，`MeetingAgentBuilder.BuildParticipantAgentsAsync`、`GeneralManagerAgentBuilder.BuildAsync` 等核心路径都有生产运行基础，复杂度边界在迁移前已经经过实际运行的检验。这是相较于业界纯新建 CLI 工具的成熟度优势，不是待验证的风险。

### 2.7 Native AOT + .NET 10

冷启动速度是 CLI 工具的核心体验指标。Claude Code 与 Codex CLI 均为 Node.js，首次启动都有 100-300ms 的 VM 初始化开销。Native AOT 发布后启动时间可压到个位数毫秒级，在频繁调用的场景（自动化流水线、宿主频繁发起 Run）有明显优势。

## 3. 真实风险与未完成项

经修正后，以下三项是发布前需要管理的真实风险。产品定位、IPC 协议复杂度、三模式复杂度均属架构本身的既定组成部分，不列为风险。

### 3.1 macOS IPC 认证未完成（Phase 2 最后一项）

Unix peer credentials 校验缺失是具体的安全空洞，属未完成项而非复杂度问题。当前 IPC 认证在 macOS 上存在信任边界缺口，V1 发布前必须关闭。

### 3.2 Skills 系统未实现

Skills 加载方案（见 05-Skills加载与调用方案）设计完整，但执行步骤尚未拆分，当前无代码落地。这是与 Claude Code 功能差距的主要来源之一。MAF 集成路径清晰（`AgentSkillsProvider`、`AgentFileSkillsSource` 已在锁定版本可用），但仍需执行。

### 3.3 Provider 真实调用的测试覆盖

10 个 Adapter 的真实 API 调用循环（而非 mock）测试矩阵未完成，是 V1 发布质量门禁的最大未知量。每个 Adapter 需覆盖流式事件格式、工具调用格式、能力声明、取消 / 限流 / 401 续期各家差异。

## 4. 与 Claude Code / Codex CLI 的功能横向对比

| 功能维度 | Claude Code | Codex CLI | Madorin（当前） |
|---|---|---|---|
| 多 Provider 支持 | Anthropic only | OpenAI only | ✅ 10 个 Provider |
| 持久对话历史 | ✅ 本地 JSONL | ✅ 本地存储 | ✅ JSONL + SQLite |
| 会话切换不重置 | 有限支持 | 无 | ✅ Next-Turn Selection |
| 多 Agent 编排 | 单 Agent | 单 Agent | ✅ Expert/Meeting/Work（已迁移验证） |
| 宿主集成 SDK | ❌ 无 | ❌ 无 | ✅ Client SDK + IPC |
| 工具权限粒度 | 白名单 | 白名单 | ✅ Grant 委派链 |
| 断线恢复 | ❌ | ❌ | ✅ GSN + 重放 |
| Skills / Prompts | ✅ 成熟 | 有限 | ⚠️ 方案已设计，未实现 |
| 冷启动速度 | ~200ms (Node.js) | ~200ms (Node.js) | ✅ <10ms (Native AOT) |
| macOS 支持 | ✅ | ✅ | ⚠️ IPC 认证未完成 |
| 终端 UI（动画/颜色） | ✅ 丰富 | 较基础 | 基础实现 |

## 5. 总结性判断

架构方向正确。协议优先 + Client SDK + 多模式 + 多 Provider 的组合，在需要深度嵌入业务系统、需要多 Agent 协作、需要跨会话恢复的场景下，是 Claude Code 和 Codex CLI 目前完全做不到的。这是清晰的差异化护城河。

CLI 作为备用与调试入口、IPC 双通道协议的复杂度、三种模式的编排复杂度，均为产品策划与架构设计的既定组成部分，不构成风险。

发布前最需要收口的三件事，按优先级：

1. 关闭 macOS IPC 认证缺口（Phase 2 最后一项）——决定 V1 能否安全交付。
2. 补齐 Provider 真实调用的端到端测试矩阵——决定发布质量门禁。
3. 落地 Skills 系统——补齐与 Claude Code 的主要功能差距。

前两项为发布阻塞项，第三项为功能完整性项。
