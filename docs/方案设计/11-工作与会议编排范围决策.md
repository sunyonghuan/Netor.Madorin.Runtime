# 工作与会议编排范围决策

**日期：** 2026-09-15  
**状态：** 评估结论，尚未作为开发任务启动

## 1. 结论

当前 `Madorin.AI.Runtime` 不宜在 CLI/Runtime 内继续复刻完整的工作模式和会议模式。两种模式包含角色协作、状态机、用户确认、长任务调度、中断重规划、并发执行和最终验收等产品级编排能力，职责和维护成本已经超出 Runtime 核心边界。

建议将能力收敛为三层：

1. **Runtime Core**：Provider 接入、Session/Run 生命周期、Tool Gateway、权限、事件、持久化和基础恢复。
2. **Plan Engine**：面向通用目标的结构化计划、用户确认或修改、步骤执行、工具调用、重试、取消和结果汇总。
3. **Product Workflow**：需要总经理、项目负责人、员工 Agent、主持人等角色协议的完整工作流，放在产品层或独立程序集。

当前 CLI 保留专家/自由模式，并优先实现轻量通用 Plan 模式。完整工作模式暂缓迁移，会议模式暂缓实现；会议需求先用多 Agent 分析或 Plan 模式验证，避免在需求和价值尚未稳定时承担完整会议编排成本。

## 2. 为什么完整编排过重

工作模式不是一次计划调用，而是一个长生命周期业务流程：需求补齐、计划草案、用户确认、步骤派发、工具执行、失败处理、暂停、补充信息、重新规划、继续执行、最终验收和总结都需要稳定的协议与持久化。会议模式还要维护主持协议、参与者发言顺序、议题收敛、附件和结束确认。

这些能力会同时扩大提示词、工具目录、状态模型、事件协议、持久化版本和测试矩阵。它们对上层产品有价值，但不是 Provider、Session 或 Tool Gateway 的基础职责。

## 3. 当前实现与目标流程的差距

对策划文档中定义的工具和流程进行对照，现有代码不能仅通过补几个工具满足目标，至少缺少以下流程：

| 流程 | 当前情况 | 影响 |
| --- | --- | --- |
| 总经理角色协议 | `GeneralManager` 目前只是普通 Agent，主要输出 `WorkPlanDraft`，没有完整职责和对话协议 | 无法稳定完成需求澄清、计划解释和验收 |
| 专用工具目录 | `mcli_ask_user`、计划设置/确认、模板、历史计划、步骤派发，以及会议总结/结束确认等工具基本未实现 | 模式无法按文档通过工具推进 |
| 计划确认边界 | 没有 `WaitingForPlanConfirmation` 状态 | 讨论阶段可能直接进入执行 |
| 计划失败处理 | 解析失败会自动生成单步回退计划并执行 | 越过用户确认，产生错误执行 |
| 步骤并发 | `MaxConcurrentSteps` 只有配置，ready steps 仍按 `foreach` 顺序执行 | 无法满足并发派发要求 |
| 最终验收 | 所有步骤结束后 Runtime 直接标记 `Completed`，没有总经理最终验收 Invocation | 结果可能未经业务验收就结束 |
| 中断与补充 | 主要只有取消 Run，没有暂停、补充信息、恢复和重新规划的完整协议 | 无法处理中途改变需求的长任务 |
| 续跑版本 | Existing Session 续跑固定使用 `planVersion = "1"` | 已发布计划再次运行会出现版本冲突 |
| 会议主持流程 | 可以完成讨论、工具调用和总结，但结束确认、插话恢复和业务校验不完整 | 会议状态可能在未确认时结束 |

因此，策划文档中的工具是必要的接口清单，但不是完整解决方案。要满足目标，还必须同时补齐状态机、事件、持久化、并发、恢复和验收协议。

## 4. 轻量 Plan 模式建议

轻量 Plan 只承诺一条可验证的闭环：

1. 用户提交目标。
2. 模型生成结构化计划和步骤依赖。
3. Runtime 返回计划，等待用户确认或修改。
4. 用户确认后，执行器按依赖执行步骤，并调用已授权工具。
5. 支持取消、失败重试和基础恢复。
6. 执行完成后生成结果汇总，并保留执行事件和步骤结果。

该模式不引入总经理、部门层级、会议主持人或员工 Agent 的固定角色。需要并行时，在计划步骤中声明依赖关系和并发上限，由执行器统一调度；需要人工决策时，通过通用的用户输入挂起点处理。

## 5. 迁移边界

- **保留在 Runtime**：现有专家模式、通用 Agent Invocation、Tool Gateway、权限授予、事件流、计划持久化基础类型和取消机制。
- **新增或收敛到 Plan Engine**：`Plan`/`PlanStep` 数据结构、确认状态、依赖调度、重试、取消、恢复、汇总和最小 CLI/SDK 接口。
- **隔离到产品层或独立程序集**：总经理与项目负责人提示词、角色工具白名单、会议主持协议、业务验收规则、附件语义和组织级重规划策略。
- **兼容策略**：Expert 不加载任何模式专用工具；Plan 通过独立 Mode/Run 类型接入；旧 Work/Meeting API 在迁移期只读或返回明确的“未启用”状态，不隐式执行回退计划。
- **长任务策略**：超过单次聊天生命周期的计划交给独立 Job Runner，聊天 Run 只负责提交、查询、暂停和恢复。

## 6. 实施顺序

1. 先冻结轻量 Plan 的协议和状态机，补充确认、暂停、恢复、重试和最终汇总的最小测试矩阵。
2. 将现有 Work 执行基础代码与产品角色协议解耦，避免继续扩大 Runtime 公共接口。
3. 用真实模型验证两个代表性场景：串行计划和带依赖的并行计划。
4. 根据实际使用数据再决定是否把完整 Work 提升为独立产品模块。
5. 会议模式暂不进入 Runtime 主线；只有在明确的会议业务指标和验收标准确定后再单独立项。

## 7. 决策矩阵

| 方案 | 业务价值 | 实现成本 | 维护风险 | Runtime 适配性 | 建议 |
| --- | --- | --- | --- | --- | --- |
| 继续在 Runtime 完整实现 Work | 中到高，但依赖具体产品场景 | 很高 | 很高 | 低 | 暂缓 |
| 在 Runtime 实现轻量 Plan | 高，覆盖大多数执行型任务 | 中 | 可控 | 高 | 优先 |
| 在 Runtime 完整实现 Meeting | 尚未验证 | 很高 | 很高 | 低 | 暂缓 |
| 产品层独立实现 Work/Meeting | 可按业务定制 | 中到高 | 边界清晰 | 通过接口接入 | 后续选择 |
