## 1. 结论与问题定性

本次问题不是简单地把两个 `config.json` 按“后加载覆盖前加载”拼接，而是需要明确区分两类配置的职责：

1. 用户全局配置是独立 CLI 的可信基础配置，保存 Provider、凭据、模型目录、公共 Agent 和全局默认选择。
2. 工作区配置是可选的项目级覆盖，只保存对全局 Provider、Model、Agent 的引用，不复制公共定义和凭据。
3. 工作区配置不存在或未填写某个字段时，必须回退到全局配置，不能因为缺少工作区配置而阻止启动。
4. 命令行显式参数优先级最高，工作区配置只能覆盖全局默认值，不能覆盖本次命令显式传入的选择。
5. 只有最终有效配置无法解析、工作区显式引用不存在，或者配置文件本身损坏时才返回配置错误。

修复前代码只读取用户全局配置，并不存在“工作区配置优先”的实现。因此，历史问题排查时若发现从工作目录读取完整 Provider 配置并因缺项失败，应检查 `MADORIN_CONFIG_DIR` 是否被设置为工作目录。该环境变量现在仍表示“整体替换全局配置目录”，不是工作区配置来源。

最终实现保留了“裸启动默认使用全局配置”的行为，并增加受限、可选、字段级的工作区覆盖能力。

### 2.2 修复前裸启动调用链

```text
madorin                         无参数
  -> 捕获 Directory.GetCurrentDirectory()
  -> NormalizeArgs
  -> run --workspace <startupDirectory>
  -> StandaloneRuntimeContext.Create
       WorkspaceRoot = <startupDirectory>
       ConfigDirectory = ~/.madorin
  -> StandaloneConfigLoader(~/.madorin)
  -> 加载 ~/.madorin/config.json
  -> 加载 ~/.madorin/agents/*.json
  -> 验证并解析 Provider / Model / Agent
  -> 启动独立 Runtime
```

因此，“无参数独立启动默认读取全局配置”是修复前主路径中需要保留的行为；最终实现已在其后加入固定工作区配置加载。

### 2.3 修复前失败条件

修复前及当前 `StandaloneConfigValidator` 都要求全局配置同时满足：

- `defaultProvider`、`defaultModel`、`defaultAgent` 均非空。
- 至少存在一个 Provider。
- 每个 Provider 至少声明一个 Model。
- 默认 Provider 和默认 Model 可以在 Provider 目录中解析。
- `agents/*.json` 存在默认 Agent，且 Agent 引用的 Provider/Model 有效。

修复前 `ServiceCommands.TryResolveSelection` 的选择顺序为：

```text
Agent:    --agent   > global.defaultAgent
Provider: --provider > selectedAgent.provider > global.defaultProvider
Model:    --model    > selectedAgent.model    > global.defaultModel
```

该逻辑现已提取到 `StandaloneConfigurationResolver`，并保留 Agent 自身显式 Provider/Model 的语义。

### 2.4 `MADORIN_CONFIG_DIR` 的真实含义

`MADORIN_CONFIG_DIR` 是进程级全局配置根目录覆盖，主要服务测试隔离、便携安装或受控部署。它的语义保持为：

```text
未设置：GlobalConfigRoot = ~/.madorin
已设置：GlobalConfigRoot = Path.GetFullPath(MADORIN_CONFIG_DIR)
```

它不得被解释为工作区配置目录，也不得参与工作区配置文件定位。若它指向一个没有完整 `config.json` 和 `agents` 的目录，仍按“全局基础配置不存在”处理。

## 3. 修复目标

1. 独立 CLI 始终先加载并验证用户全局配置，避免在每个工作区重复配置 Provider、API Key、Model 和公共 Agent。
2. 支持工作区根目录下的可选配置，只覆盖 Provider、Model、Agent 的默认引用。
3. 工作区配置文件不存在、为空对象或缺少任意字段时，自动继承全局默认值。
4. 命令行显式参数、Agent 自身配置、工作区默认值和全局默认值具备唯一、稳定、可测试的优先级。
5. Provider 定义、服务地址、协议、API Key 和模型目录只能来自全局可信配置。
6. 工作区配置使用独立强类型模型和严格 JSON Schema，不复用完整 `StandaloneConfig`，避免数组替换和凭据下沉。
7. 启动时生成一次不可变的有效配置快照；运行中不因文件变化而悄悄切换 Provider、Model 或 Agent。
8. `config show`、`config validate` 和 `doctor --workspace` 能解释全局值、工作区覆盖及最终生效值的来源。
9. JSON/JSONL、重定向和进程退出码保持稳定，不向机器输出混入配置向导或额外说明文本。
10. 宿主模式继续只使用宿主显式输入，不隐式读取用户全局或工作区 CLI 配置。

## 4. 非目标

- 不把两份完整 `StandaloneConfig` 做通用对象合并。
- 不允许工作区配置保存或覆盖 API Key、认证 Header、Provider Base URL、协议和能力声明。
- 不允许工作区自行增加或替换 Provider、Model 目录。
- 第一阶段不从工作区加载 `agents/*.json`；工作区只能选择全局已存在的 Agent。
- 不向上扫描父目录寻找 `.madorin/config.json`。
- 不自动在每个工作区创建配置文件或复制全局配置。
- 不在运行中监视配置文件并热更新当前 Session。
- 不改变 `/provider`、`/model`、`/agent` 对当前 Session Selection 的既有语义。
- 不改变 Client SDK、Runtime 公共协议或宿主配置注入模型。
- 不把 `MADORIN_CONFIG_DIR` 改成普通用户级命令行参数。

## 5. 配置分层与职责边界

### 5.1 全局配置

默认位置：

```text
Windows: %USERPROFILE%\.madorin\config.json
Linux:   ~/.madorin/config.json
macOS:   ~/.madorin/config.json
```

Agent 目录：

```text
~/.madorin/agents/*.json
```

全局配置继续保存：

- Provider 名称、协议、Base URL、认证信息和能力配置。
- 每个 Provider 的可用 Model 目录。
- 全局 `defaultProvider`、`defaultModel` 和 `defaultAgent`。
- 公共 Agent 定义及其可选 Provider/Model 绑定。

全局配置必须独立有效。工作区覆盖不能掩盖损坏的全局配置，也不能让无效的全局 Provider 目录通过验证。

### 5.2 工作区配置

固定位置：

```text
<workspace>/.madorin/config.json
```

第一阶段只允许保存：

- 工作区默认 Provider ID。
- 工作区默认 Model ID。
- 工作区默认 Agent ID。

工作区配置不保存定义，只保存引用。它引用的所有 ID 必须能从已验证的全局 Provider、Model 和 Agent 目录中解析。

### 5.3 配置来源优先级

总体优先级为：

```text
命令行显式参数
> Agent 自身显式 Provider/Model
> 工作区默认选择
> 全局默认选择
```

Agent ID 不存在 Agent 自身配置层，因此其优先级为：

```text
--agent
> workspace.selection.agent
> global.defaultAgent
```

Provider 和 Model 分别解析，不能把工作区配置理解为一个不可拆分的选择元组。

## 6. 工作区配置文件契约

### 6.1 JSON 示例

完整示例：

```json
{
  "schemaVersion": 1,
  "selection": {
    "provider": "openai",
    "model": "gpt-5",
    "agent": "code-expert"
  }
}
```

只覆盖 Agent：

```json
{
  "schemaVersion": 1,
  "selection": {
    "agent": "reviewer"
  }
}
```

有效的空覆盖：

```json
{
  "schemaVersion": 1,
  "selection": {}
}
```

### 6.2 强类型模型

最终实现使用独立内部模型，不直接反序列化为 `StandaloneConfig`：

```csharp
internal sealed class WorkspaceConfig
{
    public int? SchemaVersion { get; set; } = 1;

    public WorkspaceSelectionConfig? Selection { get; set; }
}

internal sealed class WorkspaceSelectionConfig
{
    public string? Provider { get; set; }

    public string? Model { get; set; }

    public string? Agent { get; set; }
}
```

新类型注册到独立的 `WorkspaceConfigJsonContext`，使用 JSON Source Generator 并启用 `JsonUnmappedMemberHandling.Disallow`，没有引入反射序列化。`schemaVersion` 和 `selection` 使用可空属性，以区分显式 `null`/缺失所表达的继承。

### 6.3 字段规则

| 字段 | 缺失或 `null` | 空白字符串 | 有值 |
| --- | --- | --- | --- |
| `schemaVersion` | 按 `1` 处理 | 不适用 | 必须等于当前支持版本 |
| `selection.provider` | 回退到后续来源 | 配置错误 | 必须引用全局 Provider |
| `selection.model` | 回退到后续来源 | 配置错误 | 必须属于最终解析出的 Provider |
| `selection.agent` | 回退到后续来源 | 配置错误 | 必须引用全局 Agent |

未识别字段必须报错，不能静默忽略。这样用户把 `providers`、`apiKey` 或拼错的 `defautModel` 写入工作区文件时，会立即得到明确诊断，而不是误以为配置已经生效。

### 6.4 明确禁止的工作区内容

下面的配置不得被工作区文件接受：

```json
{
  "providers": [],
  "apiKey": "...",
  "baseUrl": "https://example.invalid",
  "agents": [],
  "tools": {}
}
```

第一阶段遇到这些字段统一返回 `WorkspaceConfigurationInvalid`。不做“读取后忽略”，避免产生错误的安全预期。

### 6.5 文件读取约束

- 只读取规范化 `WorkspaceRoot` 下的 `.madorin/config.json`，不检查父目录、兄弟目录或当前进程后来切换到的目录。
- 工作区配置缺失时返回 `null`，不创建目录、不创建空文件、不启动工作区向导。
- 文件大小上限固定为 `64 KiB`；超过上限按无效配置处理。
- 使用共享读模式读取，允许编辑器或其他只读进程同时打开文件。
- 无效 JSON 的错误必须包含工作区配置路径，但不得回显原始 JSON 内容。
- 解析完成后形成内存快照；当前 Run 和 REPL Session 不热更新。
- 文件位于 Runtime 保留目录中，Agent 文件工具仍不得读取或修改它；只能由用户、CLI 配置命令或受信任宿主管理。

## 7. 有效配置解析算法

### 7.1 启动阶段

固定执行顺序：

```text
1. 捕获并规范化 WorkspaceRoot
2. 解析 GlobalConfigRoot
   - MADORIN_CONFIG_DIR 有值时使用该值
   - 否则使用 ~/.madorin
3. 加载全局 config.json
4. 加载全局 agents/*.json
5. 严格验证全局配置快照
6. 尝试加载 <WorkspaceRoot>/.madorin/config.json
7. 验证工作区配置语法、版本和允许字段
8. 生成 EffectiveDefaults
9. 按命令参数和 Agent 规则解析最终 Selection
10. 验证最终 Provider/Model/Agent 组合
11. 冻结配置来源与 Selection 快照
12. 创建并启动 LocalRuntime
```

全局配置加载和验证必须先完成。工作区文件不得为不存在的全局配置提供一个“看起来可用”的替代快照。

### 7.2 有效默认值

```text
EffectiveDefaultAgent =
  workspace.selection.agent
  ?? global.defaultAgent

EffectiveDefaultProvider =
  workspace.selection.provider
  ?? global.defaultProvider

EffectiveDefaultModel =
  workspace.selection.model
  ?? global.defaultModel
```

最终由 `StandaloneConfigurationSnapshot` 保存全局配置、只读 Agent 目录、两级路径、工作区存在状态、全局/有效默认值和初始有效 Selection。Resolver 不修改刚加载的全局对象。

### 7.3 最终 Selection 优先级

最终算法必须保留当前 Agent 绑定语义：

```text
agentId =
  commandLine.agent
  ?? effectiveDefaults.agent

agent = GlobalAgents[agentId]

providerId =
  commandLine.provider
  ?? agent.provider
  ?? effectiveDefaults.provider

provider = GlobalProviders[providerId]

modelId =
  commandLine.model
  ?? agent.model
  ?? effectiveDefaults.model

assert provider.models contains modelId
```

这意味着：

- `--provider` 和 `--model` 始终覆盖工作区及 Agent 默认值。
- Agent 文件中显式绑定的 Provider/Model 继续优先于工作区默认值。
- 工作区默认值只替代全局默认值，不改变 Agent 自身契约。
- 工作区只指定 Model 时，该 Model 必须属于按上述规则最终解析出的 Provider。

### 7.4 典型场景矩阵

| 全局配置 | 工作区配置 | CLI 参数 | 结果 |
| --- | --- | --- | --- |
| 完整有效 | 文件不存在 | 无 | 使用全局默认值，正常启动 |
| 完整有效 | `{}` | 无 | 使用全局默认值，正常启动 |
| 完整有效 | 只指定 Agent | 无 | Agent 使用工作区值，其他项按 Agent/全局规则解析 |
| 完整有效 | 指定 Provider/Model | 无 | 使用工作区默认 Provider/Model |
| 完整有效 | 指定 Provider/Model | 传入 `--model` | Model 使用命令行值 |
| 完整有效 | 引用不存在的 Agent | 无 | 明确报告工作区 Agent 引用无效 |
| 完整有效 | Model 不属于最终 Provider | 无 | 明确报告 Provider/Model 组合无效 |
| 缺失 | 任意 | 交互文本 | 运行现有全局首次配置向导，不创建工作区配置 |
| 缺失 | 任意 | JSON/JSONL | 返回 `ConfigurationNotFound` |
| 全局配置损坏 | 工作区值看似完整 | 任意 | 返回全局配置错误，不允许工作区掩盖 |

## 8. 验证与错误处理

### 8.1 分层验证

验证分为三步，不把所有错误压成一个模糊的 `SelectionNotFound`：

1. `GlobalConfigurationValidation`：复用并保持当前 `StandaloneConfigValidator` 的完整验证。
2. `WorkspaceConfigurationValidation`：验证工作区文件格式、Schema 版本、允许字段和非空引用。
3. `EffectiveSelectionValidation`：验证最终 Agent、Provider、Model 是否存在且组合兼容。

### 8.2 稳定错误码

| 错误码 | 使用条件 | 实际退出码 |
| --- | --- | --- |
| `ConfigurationNotFound` | 全局 `config.json` 不存在且当前场景不能运行交互向导 | `2` |
| `ConfigurationInvalid` | 全局配置或全局 Agent 目录无效 | `2` |
| `WorkspaceConfigurationInvalid` | 工作区配置 JSON、Schema 或字段无效 | `2` |
| `WorkspaceSelectionNotFound` | 工作区显式引用的 Agent/Provider/Model 不存在 | `2` |
| `SelectionNotFound` | 命令行覆盖或最终组合无法解析 | `2` |

文本错误必须说明来源，例如：

```text
Workspace configuration '<workspace>/.madorin/config.json':
selection.model 'gpt-x' is not provided by Provider 'openai'.
```

机器输出继续使用现有统一失败信封，不输出交互提示或配置文件正文。

### 8.3 缺失与无效必须区分

- 文件缺失：正常回退。
- 字段缺失或 `null`：正常回退。
- `selection` 为空对象：正常回退。
- 字段为空白：配置错误。
- 显式 ID 不存在：配置错误。
- JSON 损坏、版本不支持、未知字段：配置错误。

禁止在无效配置时静默回退到全局值，否则拼写错误和恶意配置会被隐藏。

## 9. 安全边界

### 9.1 凭据与 Provider 定义

工作区通常可能来自 Git 仓库或外部压缩包，不能被视为与用户主目录同等级的可信配置源。因此：

- 工作区配置不得包含 API Key、Token、认证 Header 或环境变量值。
- 工作区配置不得定义或覆盖 Provider Base URL，避免项目将请求重定向到恶意服务。
- 工作区配置不得新增 Model 目录，只能引用用户已经在全局配置中接受的 Model。
- 配置展示、诊断和错误信息继续执行凭据脱敏。

### 9.2 选择覆盖的剩余风险

即使工作区只能引用全局 ID，它仍可能选择成本更高或数据策略不同的 Provider/Model。第一阶段的控制措施为：

- 欢迎语继续明确显示实际 Provider、Model 和 Agent。
- `config show --workspace` 显示每个有效值的来源。
- 非法或不存在的引用 fail closed，不猜测最接近的名称。
- 不允许工作区改变工具权限、网络权限、审批策略或凭据。

若后续允许工作区 Agent、Provider 或工具策略，必须新增独立的工作区信任机制；不能在本方案第一阶段顺带开放。

### 9.3 路径与保留目录

`.madorin` 继续是 Runtime 保留目录。新增的 `config.json` 是一个明确列出的声明式例外，不代表可以扫描或编辑其中其他文件：

```text
允许 CLI 读取：<workspace>/.madorin/config.json
禁止隐式读取：<workspace>/.madorin/**/*.json
禁止 Agent 工具：读取、修改或删除整个 <workspace>/.madorin
```

工作区配置文件不保存秘密，因此不要求与全局凭据文件相同的用户专属权限，但仍应拒绝目录穿越和超出工作区根目录的解析结果。

## 10. CLI 与 REPL 行为

### 10.1 无参数独立启动

```text
cd <workspace>
madorin
```

预期行为：

1. 当前目录被固定为 `WorkspaceRoot`。
2. 全局 `~/.madorin/config.json` 和 `agents/*.json` 始终作为基础配置加载。
3. `<workspace>/.madorin/config.json` 存在时读取允许的选择覆盖；不存在时不报错。
4. 欢迎语显示最终 Provider、Model、Agent 和 Workspace。
5. 不自动复制全局配置到工作区，不在工作区启动配置向导。

### 10.2 显式 `run`

```text
madorin run --workspace <path>
madorin run --workspace <path> --provider openai --model gpt-5 --agent default
```

第一条命令按“工作区覆盖 > 全局默认”解析；第二条命令的显式参数优先。

如果没有传 `--workspace`，继续使用命令开始时的当前目录，不允许配置加载过程或第三方代码后来改变当前目录并影响工作区配置定位。

### 10.3 REPL 选择命令

`/provider`、`/model`、`/agent` 继续操作当前 Session 的 Selection：

- 列表数据来自全局有效 Provider/Model/Agent 目录。
- 启动后的工作区配置只提供初始默认值。
- REPL 选择不写回全局或工作区配置。
- `/new` 创建新 Session 时使用当前 REPL Selection，不重新从磁盘读取工作区配置。

### 10.4 配置命令

为避免改变现有脚本，默认行为保持全局作用域：

| 命令 | 默认行为 | 增加工作区参数后的行为 |
| --- | --- | --- |
| `config init` | 创建全局配置 | 第一阶段不创建工作区配置 |
| `config edit` | 编辑全局配置和 Provider | 第一阶段不编辑工作区配置 |
| `config show` | 显示脱敏后的全局配置 | `--workspace <path>` 额外显示工作区覆盖和有效选择 |
| `config validate` | 验证全局配置 | `--workspace <path>` 同时验证工作区配置与有效选择 |

`config show --workspace` 的文本结果已明确区分来源：

```text
Global config     C:\Users\user\.madorin\config.json
Workspace config E:\Repo\.madorin\config.json

Agent             code-expert  [workspace]
Provider          openai       [global]
Model             gpt-5        [agent]
```

JSON 输出使用结构化字段，不依赖解析上述文本：

```json
{
  "globalConfigPath": "...",
  "workspaceConfigPath": "...",
  "workspaceConfigExists": true,
  "effectiveSelection": {
    "agent": { "value": "code-expert", "source": "workspace" },
    "provider": { "value": "openai", "source": "global" },
    "model": { "value": "gpt-5", "source": "agent" }
  }
}
```

### 10.5 Agent 管理命令

`agent list/create/edit/delete` 第一阶段继续只管理 `~/.madorin/agents/*.json`：

- 工作区配置可以引用这些全局 Agent。
- 删除一个被某些工作区引用的 Agent 时，不扫描所有工作区；相关工作区下次启动时得到明确引用错误。
- 后续若增加工作区 Agent，必须设计 `--scope global|workspace`、信任策略和同名覆盖规则，不在本修复中实现。

### 10.6 Doctor

`doctor --workspace <path>` 增加以下检查：

1. 全局配置文件存在、格式有效、权限符合凭据要求。
2. 工作区配置不存在时报告 `Skipped` 或 `Not configured`，不报告失败。
3. 工作区配置存在时验证 Schema、未知字段、大小和引用。
4. 输出最终 Selection 及其来源，不输出凭据。
5. 工作区引用错误归类为配置错误，而不是工作区存储错误。


```csharp
internal enum ConfigurationValueSource
{
    CommandLine,
    Agent,
    Workspace,
    Global
}
```

来源是诊断信息，不进入 Runtime 公共协议，也不写入 Provider 请求。Session Selection 继续持久化最终 ID 和版本，不需要持久化配置文件路径。

## 13. 配置与选择流程重构

最终实现已把加载、验证和选择逻辑从 `ServiceCommands.CreateRun` 收敛到配置层：

```text
ServiceCommands
  -> StandaloneRuntimeContext.Create(...)
  -> StandaloneConfigurationResolver.LoadAsync(workspaceRoot, ...)
       -> StandaloneConfigLoader.LoadAsync
       -> StandaloneConfigLoader.LoadAgentDocumentsAsync
       -> StandaloneConfigValidator.Validate
       -> WorkspaceConfigLoader.LoadAsync
       -> WorkspaceConfigLoader.Validate
       -> Build StandaloneConfigurationSnapshot
  -> StandaloneConfigurationResolver.ResolveSelection(command overrides)
  -> Start LocalRuntime
```

Resolver 不负责终端输出和退出码。它返回结构化错误，由 `ServiceCommands`、`ConfigCommands` 和 `DoctorCommand` 分别映射成人类文本或机器信封。

REPL 内部后续选择仍复用同一个 Selection Resolver，避免启动、`/provider`、`/model`、`/agent` 各自维护不同优先级。

## 14. 兼容与迁移策略

### 14.1 现有用户零迁移

没有工作区配置文件的用户行为完全不变：

- 继续读取 `~/.madorin/config.json`。
- 继续读取 `~/.madorin/agents/*.json`。
- 继续使用全局默认 Provider、Model 和 Agent。
- 不在工作区生成新文件。

因此不需要批量迁移现有全局配置，也不修改全局配置 Schema。

### 14.2 已存在的工作区文件

本功能首次引入前没有工作区合并契约。最终实现按以下规则处理已存在或新建的同名文件：

- 符合 Workspace Schema v1：正常加载。
- 是完整全局 `StandaloneConfig`：因 `providers` 等未知字段明确报错，并提示不要复制全局配置。
- 是 Runtime 其他 JSON：明确报错，不尝试猜测或自动转换。

### 14.3 `.gitignore` 与共享方式

仓库根 `.gitignore` 继续使用 `.madorin/` 忽略整个目录。最终选择是保持现有仓库规则不变，同时在文档提供两种团队策略：

1. 保持默认忽略：工作区配置只在本机生效，用户需要显式 `git add -f .madorin/config.json` 才能共享。
2. 调整模板忽略规则：忽略 `.madorin/*`，只允许提交 `.madorin/config.json`，继续忽略数据库、消息、Blob、日志和缓存。

团队需要共享选择时推荐第 2 种，但不得由 CLI 或本次修复强行改写已有用户仓库的 `.gitignore`。无论是否提交，工作区文件都不得含凭据。

### 14.4 首次配置向导

首次配置向导继续只创建全局配置。即使工作区文件存在，只要全局配置不存在，交互文本模式仍进入全局向导；向导完成后再重新验证工作区引用。

非交互、JSON 或 JSONL 模式不得启动向导，继续返回稳定错误。

## 17. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 把工作区文件当成完整配置覆盖全局 | 使用独立 DTO；禁止 `providers`、凭据和 Agent 数组 |
| 缺失字段把全局值清空 | 只对非 `null` 字段建立覆盖；缺失和 `null` 继承 |
| 空白或拼错字段被静默忽略 | 空白值和未知字段严格报错 |
| 工作区重定向 Provider 请求 | Base URL、协议和凭据只允许来自全局配置 |
| Agent 与工作区优先级发生回归 | 明确保留 `CLI > Agent > Workspace > Global` 并建立矩阵测试 |
| `MADORIN_CONFIG_DIR` 被误认为工作区来源 | 保持其仅覆盖 GlobalConfigRoot，并补充文档和测试 |
| 当前目录在运行中变化导致读取错误工作区 | 启动时规范化并冻结 WorkspaceRoot |
| 工作区文件修改导致 Session 中途切换模型 | 每次启动/Run 建立不可变快照，不启用热加载 |
| 完整全局配置被复制到工作区泄漏密钥 | 严格 Schema 拒绝；文档明确禁止；展示始终脱敏 |
| `.madorin` 保留目录边界被放宽 | 只允许 CLI 读取固定 `config.json`；Agent 工具仍拒绝整个目录 |
| 工作区配置因 `.gitignore` 无法共享 | 更新模板忽略规则或明确使用本地配置，禁止自动改写用户仓库 |
| 配置命令默认行为变化破坏脚本 | `config show/validate` 默认保持全局，只有显式 `--workspace` 才展示有效配置 |
| 工作区配置逻辑渗入 Server/Client | 所有加载和合并留在 CLI Config 层，Server 只接收最终快照 |
| Native AOT 缺少元数据 | 新 DTO 全部注册 `WorkspaceConfigJsonContext` 并执行 AOT 发布测试 |
