Runtime 本身支持多实例、多工作区并行与并发 Run。本文把这些并发能力纳入测试台，**定位为“并发作为被测场景”**：测试台自身仍是串行驱动的编排者，但能同时拉起多个进程、跨工作区并发发起命令，并观察并发下的正确性——尤其是工作区写锁冲突、实例隔离和数据安全。

本文不改变 00 定的进程模型，只在其上增加“同时管理多个长驻/一次性进程”的编排层。

---

## 1. Runtime 的并发能力（源码核实）

在设计测试场景前，先冻结从源码核实到的并发事实，作为断言依据：

| 事实 | 来源 | 对测试的意义 |
| --- | --- | --- |
| **工作区写锁按规范化工作区路径排他** | `WorkspaceWriteLock.AcquireAsync`：以 `NormalizeWorkspace` + `ComputeWorkspaceKey` 生成锁文件，置于系统临时目录 `madorin.ai.runtime/workspace-locks/` | 同一工作区**只能有一个写实例**；实例名、Pipe、data-dir 不能绕过。不同路径指向同一工作区（大小写、相对/绝对、符号链接）应归一到同一把锁 |
| **多 serve 实例可并行** | `MultiInstanceHost`：同时启动两个 serve，各自 `--instance`、`--pipe-prefix`、`--workspace`、secret | 多实例是设计内场景，前提是**工作区不同**或不同时持有写锁 |
| **每实例并发 Run 上限** | `serve --max-runs`（矩阵默认 `4`，SampleHost 用 `1`） | 可测“并发 Run 达到上限后的排队/拒绝行为” |
| **锁冲突退出码固定为 4** | 命令矩阵第 1 节 + 各维护命令退出码 | 并发写命令撞锁时的**权威断言值** |
| **ctl 按 `(runtimeInstanceId, runId)` 路由** | 命令矩阵 `ctl cancel` 行 | 多实例下 ctl 必须绑定正确实例，串扰即为缺陷 |
| **每实例独立 secret** | `RuntimeConfiguration.Secret`，随实例注入 | 测试台需按实例分别持有 secret，不能共用 |

## 2. 三类并发被测场景

### 2.1 同一工作区的写锁互斥（核心正确性）

验证“同一工作区只有一个写实例”这条不变量。

- **场景 A：双写实例抢锁**。对同一 `--workspace` 同时启动两个 serve，或在一个 serve 持锁时并发跑一个写命令（如 `db vacuum`）。**期望**：后到者拿不到锁，返回退出码 `4`，且**不修改数据**（配合[03 文档](./03-测试增强功能设计.md#1)的“零写入”快照断言）。
- **场景 B：路径别名归一**。用大小写不同、相对/绝对、尾部斜杠不同、符号链接等指向同一工作区的路径并发写。**期望**：仍归一到同一把锁，第二个返回 `4`。这是最容易出隔离漏洞的地方，必测。
- **场景 C：只读命令不被写锁阻塞**。写实例持锁时并发跑 `db check`/`storage check`/只读 `session`。**期望**：只读命令正常返回 `0`，不获取写锁、不被阻塞。

### 2.2 多工作区并行隔离（隔离性）

验证不同工作区互不干扰。

- **场景 D：N 工作区并发写**。为 N 个独立工作区各起一个 serve 并各自发 run。**期望**：全部成功，数据分别落在各自 `.madorin`，无交叉写入（用快照断言各工作区数据只被本实例改动）。
- **场景 E：实例发现不串扰**。多实例并存时，`ctl status/sessions/runs` 在未显式 `--instance` 时只解析**当前工作区的唯一实例**；显式 `--instance` 时只命中目标。**期望**：A 工作区的 ctl 绝不返回 B 实例的 Session/Run。
- **场景 F：跨实例取消路由**。对实例 1 的 `run-x` 发 `ctl cancel`，验证不会误伤实例 2 的同名/异名 Run。

### 2.3 单实例内并发 Run（吞吐与上限）

验证一个 serve 内的并发调度。

- **场景 G：并发 Run 达上限**。以 `--max-runs=N` 启动，向同一实例并发提交 > N 个 run。**期望**：至多 N 个并发执行，其余按实现排队或拒绝，行为稳定可预测，无崩溃、无数据错乱。
- **场景 H：并发下取消与凭据更新**。多 Run 并发时对其中之一 `ctl cancel` 或 `ctl credential update`，验证只影响目标 Run，其余不受扰。

## 3. 测试台的编排能力（串行驱动，并发执行）

测试台不做通用并发调度器，只提供“把上述场景一键拉起并观察”的**受控编排**。

### 3.1 场景剧本 `ConcurrencyScenario`

在[03 文档](./03-测试增强功能设计.md)的用例模型之上扩展一层“并发剧本”：

```jsonc
{
  "name": "same-workspace-lock-contention",
  "workspaces": [ { "id": "ws1", "fixture": "fixture:seeded-workspace" } ],
  "instances": [
    { "id": "inst-a", "workspace": "ws1", "role": "serve", "maxRuns": 1 }
  ],
  "concurrentSteps": [
    { "command": "db vacuum", "workspace": "ws1", "expectExit": 4, "assert": [ { "noDataChange": true } ] }
  ],
  "expectations": {
    "atMostOneExitZeroAmong": ["<持锁写命令组>"],
    "allOthersExit": 4
  }
}
```

要点：
- `workspaces` / `instances` 声明式拉起，测试台负责为每个实例生成并持有独立 secret，注入对应进程（见 00 文档 2.3 的 secret 闭环）。
- `concurrentSteps` 里的步骤**同时**启动（测试台用后台任务并行 spawn 一次性命令进程），各自采集独立 `ExecutionResult`。
- `expectations` 支持“聚合断言”：如“这组抢锁写命令里最多一个退出 0，其余必须退出 4”。

### 3.2 并发执行与采集
- 每个并发命令仍是**独立子进程**，各自独立采集 stdout/stderr/exit（复用 `ProcessRunner`），不共用输出流，避免交织。
- 测试台记录每个进程的启动时刻与退出时刻，用于判断“真的重叠执行了”（否则退化成串行，锁冲突测不出来）。剧本可设最小重叠窗口断言。
- 结果汇总成一张对照表：实例/工作区、命令、退出码、断言判定、时间线。

### 3.3 多进程生命周期
- 复用 00 文档的 `ServeHost`，扩展为 `ServeHostPool` 管理多个 serve 实例（各自 instance/pipe-prefix/workspace/secret，参照 `MultiInstanceHost`）。
- 剧本结束统一收敛：优雅停止全部 serve → 校验各自退出 → 释放各工作区写锁 → 触发夹具清理。任一实例异常退出，保留其 stderr 与所属工作区诊断。

## 4. 安全与边界

- **夹具隔离**：每个并发工作区都是测试台创建的临时目录，带 00/03 定义的归属哨兵；并发清理时逐个校验哨兵，绝不波及真实业务数据或测试台自有数据目录。
- **secret 不外泄**：每实例 secret 只在进程环境间传递，不入剧本文件、不入历史、不显示。剧本里只存“实例 id”，secret 运行时生成。
- **资源上限**：并发拉起的实例数、工作区数、Run 数设显式上限与超时，避免测试台把机器压垮；超限在剧本校验阶段拦截。
- **端口/Pipe 冲突**：多实例必须用不同 `--pipe-prefix` 或实例后缀，测试台自动分配唯一后缀，冲突则报错不启动。

## 6. 落地优先级

并发编排依赖单进程能力先就位，排在增强能力之后：

| 优先级 | 内容 | 依赖 |
| --- | --- | --- |
| P4 | `ServeHostPool` 多实例生命周期 + 并发 spawn 采集 | 00 的 ServeHost、ProcessRunner |
| P4 | 写锁互斥场景（A/B/C）+ 聚合断言（退出码 4、零写入、重叠窗口） | 快照断言、时间线采集 |
| P5 | 多工作区隔离（D/E/F）+ 单实例并发 Run（G/H） | 上一阶段 + ctl 实例路由 |

验收基线：能复现“同一工作区第二个写实例退出码 4 且零写入”；能并行 N 工作区互不串扰；ctl 在多实例下不路由串扰；全部并发进程可被统一收敛与清理。
