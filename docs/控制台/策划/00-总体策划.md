## 1. 背景与目标

`madorin` 有两种被使用的形态，测试价值和测试难度完全不同：

- **独立命令形态**：`run --input`、`version`、`doctor`、`config`、`agent`、`memory`、`skill`、`session`、`db`、`storage`、`ctl` 等。这些命令**自己就能单独测**——敲一条命令、看退出码和 JSON 信封即可，行为相对简单、边界清晰。
- **serve 宿主形态**：`madorin serve` 启动常驻 Runtime，由**宿主(host)通过 Client SDK / IPC 协议**连接并驱动。这才是控制台要充当的角色，也是整个系统里**最复杂**的部分：Session/Run 生命周期、事件流与 GSN 确认水位、5 类宿主回调（工具授权/审批/工具调用/结果查询/取消）、断线重连恢复、凭据续期、工具目录发布、多实例并发。

### 1.1 定位：控制台是宿主，重点测 serve

**控制台程序充当的是宿主。** 因此本策划的重心明确划分为两层：

| 层次 | 内容 | 分量 | 依据 |
| --- | --- | --- | --- |
| **重点** | serve 模式：以 Client SDK 连接常驻 Runtime，走完整宿主生命周期与协议交互 | **主体，功能与文档均重点处理** | 宿主角色的核心职责，最复杂，独立命令替代不了 |
| 次要 | 独立命令：进程调用真实 `madorin`，采集退出码/信封做辅助验收 | 从属，够用即可 | 这些命令本就能单独测，无需宿主也能验证 |

serve 深度测试是独立的一份文档（[05-serve 宿主深度测试设计](./05-serve宿主深度测试设计.md)），本文其余章节的“进程调用/菜单/断言/夹具/并发”既服务独立命令的次要测试，也为 serve 场景提供地基（拉起 serve 进程、造工作区、断言退出码等）。

### 1.2 命令面清点（供次要层参考）

以源码实际注册清点，独立命令共 **45 条可执行叶子路径**（含 `skill` 组 4 条；不含则 41 条），外加 8 个命令组节点和一套交互模式斜杠命令。`skill` 组超出冻结命令矩阵（矩阵为 51 条口径，含 `providers` 等文档命令），测试台以源码实际注册为准。

### 1.3 要解决的痛点

1. **serve 宿主交互无从下手**：宿主生命周期、事件确认、回调、重连是协议级行为，手工无法复现，是重点要攻克的。
2. **命令面太大（次要层）**：独立命令参数分散，人工逐条敲容易漏测、记错。
3. **验收无固定基线**：退出码和 JSON 信封是机器契约，人工执行后缺少“对不对”的自动判断。
4. **状态不可复现**：危险维护命令需在已知数据状态下反复测试，手工造数据和清理成本高。
5. **并发场景难验证**：多实例、多工作区并行与并发 Run 下的写锁互斥、实例隔离只在并发下暴露，手工难稳定复现。

### 1.4 总目标

把上述做成一个**以宿主 serve 测试为核心、菜单驱动、可断言、可复现**的人工测试台：

- **重点**：内建 Client SDK 宿主控制台，能连接/拉起 serve、提交 Run、消费事件流并按 GSN 确认、应答宿主回调、演练重连与凭据续期、编排多实例（见 05、04 文档）。
- 次要：用分层菜单 + 参数向导覆盖全部独立命令，带默认值、约束校验、Secret 不回显。
- 执行后自动采集退出码、stdout/stderr、JSON 信封并对照断言。
- 支持用例录制回放、数据夹具准备/清理、serve 实时监控。

程序定位是**测试工具**，不是新的产品入口。独立命令只调用真实 `madorin`；serve 层只通过公开 Client SDK 交互，不重新实现任何业务逻辑，不触碰 Runtime 内部。

## 2. 冻结的架构决策

| 决策项 | 冻结结论 | 理由 |
| --- | --- | --- |
| **serve 交互方式（重点）** | **引用 `Madorin.AI.Runtime.Client`，用 `RuntimeClient` 通过 IPC 连接 serve**，像真实宿主一样交互 | serve 的价值在协议级宿主行为（事件流、GSN、回调、重连），只有走 Client SDK 才能真实覆盖；`ctl` 子进程只能看表层状态 |
| 独立命令调用方式（次要） | **进程调用真实 `madorin` 可执行文件**，采集 stdout/stderr 和退出码 | 最贴近人工验收的真实产物；能真实验证退出码约定和进程边界，而不是绕过二进制直接调 `CliApplication.Run` |
| 依赖边界 | 宿主层只引用 `Client` + 必要 `Contracts`，**不引用** Provider/Server/Persistence/SQLite，不解析 Pipe 帧、不扫描数据目录 | 遵循[宿主集成指南](../../开发文档/04-宿主集成指南.md)第 1 节，确保测试台是合规宿主，不走后门 |
| 交互形态 | **分层菜单 + 参数向导** | 面向可能不熟悉命令集的测试者；数字/方向键选择命令组与命令，逐个提示必填与可选参数 |
| 结果处理 | 默认解析 `--json` 统一信封；对无 JSON 的命令按退出码和文本采集 | 与命令矩阵的 JSON 契约对齐 |
| Secret 处理 | 一律走环境变量或不回显输入，绝不作为明文命令行参数拼接 | 遵循规范：API Key 不得进入进程列表或 Shell 历史 |
| 危险命令 | 执行前二次确认，并默认优先走 `--dry-run` | 遵循规范的确认与备份边界 |
| 目标二进制定位 | 优先显式配置路径，其次 PATH 中的 `madorin`，再次仓库构建产物 | 兼顾已发布环境和本地开发环境 |

### 2.1 为什么是进程调用而不是进程内调用

`CliApplication.Run(string[] args, ...)` 可以在进程内直接调用并注入 `TextWriter`/`TextReader`，速度更快。但人工测试台的价值在于验证**真实交付产物的行为**：真实退出码、真实 stdout/stderr 分流、真实的非 TTY 行为、真实的锁与并发。进程内调用会绕过这些边界，让“测试台通过”与“真实命令通过”产生偏差。因此宿主统一用 `System.Diagnostics.Process` 启动目标二进制。

> 备选保留：若后续需要极快的冒烟回归，可增加一个“进程内驱动”开关，仅用于开发自测，不作为默认验收路径。本轮不实现。

### 2.2 两类进程模型（关键）

被调用的命令不是同一种进程形态，测试台必须区分两类，不能用一套“启动→跑完→采集”模型套全部命令：

| 形态 | 命令 | 生命周期 | 采集方式 |
| --- | --- | --- | --- |
| **一次性命令** | `run --input`、`version`、`doctor`、`config`、`agent`、`memory`、`skill`、`session`、`db`、`storage`、`ctl` | 启动 → 执行 → 退出 | 跑完一次性拿全 stdout/stderr + 终值退出码，产出 `ExecutionResult`（见[03 文档](./03-测试增强功能设计.md)第 0 节） |
| **长驻交互进程** | `run`（无 `--input` 的 REPL）、`serve` | 持续运行，边交互边输出 | 子进程常驻，stdin 持续喂、stdout 持续读；无“最终退出码”直到主动结束 |

两类长驻进程各自处理：

- **REPL（本轮定位：简单行交互）**：子进程常驻，测试台**按行**向 stdin 写入用户输入或斜杠命令，**按行**读取 stdout 回显。流式 token 只做整行呈现，不逐字渲染、不解析 ANSI/光标。提供斜杠命令速查面板一键发送（见[01 文档第 9 节](./01-命令层次与菜单树.md)）。`/exit`、`/quit` 或 EOF 结束会话后才采集退出码。REPL 会话内的每次往返**不产生** `ExecutionResult`，只记录到会话流水；需要可断言的验证请用 `run --input` 的一次性形态。
- **serve**：后台常驻，生命周期与监控在[03 文档第 4 节](./03-测试增强功能设计.md)。

> 结论：`ProcessRunner` 只服务“一次性命令”。REPL 与 serve 各有独立的长驻进程管理器（`ReplSession`、`ServeHost`），不复用一次性采集路径。

### 2.3 secret 与隔离数据目录（关键）

两条贯穿全局的约束，避免实现期返工：

- **secret 闭环**：`serve` 与连接它的 `ctl` 共用握手 secret（`MADORIN_AI_RUNTIME_SECRET`）。测试台是该 secret 的**唯一持有者**：启动 `serve` 时注入子进程环境，随后每次 `ctl` 调用也注入同一值，否则 `ctl` 返回退出码 `3`。secret 只在进程环境间传递，绝不显示、不入用例、不入历史。
- **测试台自有数据目录**：用例、执行历史、默认参数配置存在测试台**自有的稳定目录**（如 `~/.madorin-mconsole/`），**独立于**任何被夹具创建/销毁的 `--workspace`。夹具清理临时工作区时不得波及测试台自有数据。

## 3. 与现有 CLI 契约的对齐与差异

控制台宿主以**实际注册的命令**为准（源码 `CliApplication.CreateRootCommandCore`），而不是仅以文档为准。策划阶段发现两处文档与代码的差异，测试台需按代码实现，并在菜单上标注：

| 差异 | 说明 | 测试台处理 |
| --- | --- | --- |
| `providers` 命令组 | `04-CLI命令规范.md` 第 3 节描述了 `providers list/show/test/add/remove`，但根命令**未注册** `providers`。Provider 目前通过 `config` 管理 | 菜单不提供 `providers` 组；在“已知差异”页标注，避免测试者追不存在的命令 |
| `skill` 命令组 | 源码注册了 `skill list/show/validate/refresh`，但**未进入**冻结命令矩阵（矩阵为 51 条基线） | 菜单提供 `skill` 组，并标注“超出冻结矩阵，按源码实现测试” |
| REPL 斜杠命令 | 源码实际包含 `/memory`、`/remember`、`/skill`，规范文档第 8 节未列出 | REPL 速查表以源码为准 |

> 这些差异只做记录和提示，不在本项目内修改 CLI。如需统一，另立文档提交 CLI 契约变更评审。

## 4. 命令面快照（实际注册）

根命令下实际注册的命令组（源码为准）：

```text
madorin
├─ run              单次任务 / 进入 REPL
├─ serve            常驻 Runtime Server
├─ version          版本与构建信息
├─ doctor           环境与 Provider 体检（可 --fix）
├─ config           全局配置 init/edit/show/validate
├─ agent            Agent 定义 list/create/edit/delete
├─ memory           记忆 show/init/add/edit/clear（scope: global|project）
├─ skill            Skills list/show/validate/refresh（超出冻结矩阵）
├─ session          会话 list/show/export/archive/unarchive/compact/delete
├─ db               数据库 check/repair/rebuild/vacuum/backup/migrate
├─ storage          存储 check/gc
└─ ctl              在线控制 status/sessions/runs/cancel/credential update
```

全局参数（所有命令继承）：`--workspace`、`--data-dir`、`--log-level`、`--no-color`、`--json`。固定退出码：`0` 成功、`1` 通用错误、`2` 参数/配置错误、`3` 认证失败、`4` 工作区/数据错误、`5` Runtime 连接失败、`130` 用户中断。

详细分层与风险标注见[01-命令层次与菜单树](./01-命令层次与菜单树.md)。

## 5. 技术栈与项目结构

| 项 | 选择 |
| --- | --- |
| 运行时 | .NET 10（与主仓库一致，见 `global.json`） |
| 项目类型 | 控制台可执行 `Madorin.AI.Runtime.MConsole` |
| 建议位置 | `tools/Madorin.AI.Runtime.MConsole/`（与业务源码 `src/` 隔离，不进发布产物） |
| **serve 宿主（重点）** | 引用 `Madorin.AI.Runtime.Client`，用 `RuntimeClient` 连接/拉起 serve；参考 `samples/Madorin.AI.Runtime.SampleHost` |
| 进程调用（次要） | `System.Diagnostics.Process`，重定向 stdin/stdout/stderr |
| JSON 解析 | `System.Text.Json`，只读取 `success/data/error/warnings/diagnosticId` 信封字段 |
| 菜单渲染 | 纯 `Console` 实现即可；如需方向键选择可选用 Spectre.Console（可选依赖，需评审） |
| 用例存储 | 本地 JSON 文件，存于测试台**自有稳定目录**（如 `~/.madorin-mconsole/`），独立于夹具管理的任何 `--workspace`，不写入 `.madorin` 业务数据区 |

建议的内部分层：

```text
Madorin.AI.Runtime.MConsole/
├─ Program.cs                 入口，加载配置，进入主菜单循环
├─ HostClient/                【重点】serve 宿主层，引用 Madorin.AI.Runtime.Client
│  ├─ HostClientFactory.cs    构造 RuntimeClientOptions、按 StartPolicy 连接/拉起 serve
│  ├─ RunConductor.cs         提交 Run、消费事件流、按 GSN 确认、投影 Run 状态
│  ├─ HostCallbackPanel.cs    5 类宿主回调的人工应答（授权/审批/工具/结果查询/取消）
│  ├─ ToolCatalogPanel.cs     ReplaceToolCatalog/PatchToolCatalog 发布工具目录
│  ├─ ReconnectDrill.cs       断线重连、rehydrate/resume、游标重放演练
│  └─ CredentialPanel.cs      UpdateCredentials 凭据续期
├─ Hosting/                   进程管理（serve/独立命令共用）
│  ├─ MadorinLocator.cs       定位目标二进制（显式路径 > PATH > 构建产物；Windows 兼容 madorin 与 madorin.exe）
│  ├─ ProcessRunner.cs        一次性命令：启动、采集 stdout/stderr/exit code、超时与取消
│  ├─ ReplSession.cs          长驻交互进程：REPL 行输入/行回显、斜杠命令发送、结束采集
│  ├─ ServeHost.cs            长驻 serve 进程：启动、健康探测、停止、secret 注入
│  └─ JsonEnvelope.cs         解析统一 JSON 信封
├─ Menu/                      【次要】独立命令菜单
│  ├─ CommandCatalog.cs       独立命令组/命令/参数的静态定义（数据驱动菜单）
│  ├─ MenuLoop.cs             分层导航与返回/退出
│  └─ ParameterWizard.cs      逐参数提示、默认值、校验、Secret 不回显
├─ Testing/
│  ├─ Assertions.cs           退出码/JSON success/字段/文本 + 事件/回调断言
│  ├─ Recorder.cs             用例录制与回放
│  ├─ Fixtures.cs             数据夹具准备与清理（含前后哈希快照）
│  ├─ LiveMonitor.cs          serve 实例的状态看板（经 Client 或 ctl）
│  ├─ ServeHostPool.cs        多 serve 实例编排（各自 instance/pipe-prefix/workspace/secret）
│  └─ ConcurrencyRunner.cs    并发剧本：同时 spawn、独立采集、聚合断言与时间线
└─ appsettings.mconsole.json  目标二进制路径、默认 workspace、Provider env 名等
```

两个核心：`HostClient/` 是**重点**——把 Client SDK 的宿主生命周期做成可人工操作、可断言的面板（详见[05 文档](./05-serve宿主深度测试设计.md)）。`CommandCatalog` 是**次要层**的数据驱动核心：独立命令的菜单树、参数向导、约束校验从同一份定义生成，避免菜单和真实命令漂移。

## 6. 菜单驱动 UX 模型

主循环是一棵可返回的导航树：

```text
[主菜单]
  ==== serve 宿主测试（重点） ====
  1. 连接 / 拉起 serve 实例        → StartPolicy、绑定校验
  2. 会话与 Run 生命周期           → 提交 Run、事件流、GSN 确认
  3. 宿主回调应答台                → 授权/审批/工具/结果查询/取消
  4. 工具目录发布                  → Replace/Patch 工具目录
  5. 断线重连与恢复演练            → reconnect、rehydrate/resume、游标重放
  6. 凭据续期                      → UpdateCredentials
  7. 多实例并发场景                → ServeHostPool（见 04 文档）
  8. serve 实例状态看板            → 实时监控
  ==== 独立命令测试（次要） ====
  9. 单次任务 / 诊断 / 配置 / 会话 / 数据库 / 存储 / ctl（分层子菜单，见 01 文档）
  ==== 测试增强 ====
 10. 结果断言与执行历史
 11. 用例录制与回放
 12. 数据夹具准备与清理
  ==== 环境 ====
 13. 目标二进制、Client 选项与默认参数设置
  0. 退出
```

**重点层（serve 宿主）**：第 1–8 项由 `HostClient/` 驱动，每一步都是一次真实的 Client SDK 协议交互，可加事件/回调断言、可录成用例。详见[05-serve 宿主深度测试设计](./05-serve宿主深度测试设计.md)。

**次要层（独立命令）**：第 9 项进入独立命令的分层菜单与参数向导。选中命令后：

1. 套用全局默认（`--workspace`、`--data-dir`、`--json` 等）。
2. 逐个提示局部参数：名称、含义、默认值；必填不允许空；枚举列出可选值；Secret 不回显并引导用环境变量。
3. 校验互斥/条件必填（如 `run --input` 与 `--input-file` 互斥），展示最终命令行供确认。
4. 危险命令二次确认，默认建议先 `--dry-run`。
5. 执行 → 采集 → 展示退出码/信封/输出 → 可选保存为用例或加断言。

## 7. 实施阶段建议

重点层（serve 宿主）优先，次要层（独立命令）作为地基穿插并行：

| 阶段 | 内容 | 产出 | 层次 |
| --- | --- | --- | --- |
| P0 | 进程骨架 + 二进制定位 + JSON 信封 + `ServeHost`（拉起/停止 serve、secret 注入）+ `version`/`doctor` 打通 | 能拉起 serve、能跑只读命令，验证采集链路 | 地基 |
| **P1（重点）** | `HostClientFactory` 连接/拉起 serve + `RunConductor` 提交 Run、消费事件流、按 GSN 确认 | **能作为宿主完整跑一个 Run 并消费事件** | serve |
| **P2（重点）** | `HostCallbackPanel` 5 类回调人工应答 + `ToolCatalogPanel` 工具目录发布 | **工具授权/审批/调用闭环可人工演练** | serve |
| **P3（重点）** | `ReconnectDrill` 断线重连/rehydrate/游标重放 + `CredentialPanel` 凭据续期 | **重连恢复与凭据续期可复现** | serve |
| P4 | `CommandCatalog` 独立命令全量定义 + 参数向导 + 分层菜单 | 次要层命令可从菜单执行 | 独立 |
| P5 | 结果断言（退出码/信封/事件/回调）+ 执行历史 + 用例录制回放 + 数据夹具 | 单机可判定通过/失败，半自动回归 | 通用 |
| P6 | 多实例编排（`ServeHostPool`）+ 写锁互斥 + 多工作区隔离 + 并发 Run | 并发覆盖完整（详见[04 文档](./04-并发与多实例测试设计.md)） | serve |

验收基线（重点优先）：
- **serve**：能以宿主身份连接/拉起 serve，提交 Run 并按 GSN 确认消费完事件流；5 类回调可人工应答并断言；断线后能重连、rehydrate、从游标重放且不重复执行工具副作用；能复现多实例并发下同一工作区第二写实例退出码 4 且零写入。
- 次要：独立命令可从菜单覆盖，危险命令有确认与 dry-run 优先。
- 通用：Secret 全程不落明文；断言能区分退出码、JSON success、事件与回调结果。
