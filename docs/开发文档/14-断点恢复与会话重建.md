# 断点恢复与会话重建

> 当前生效版本：Madorin.AI.Runtime V1
>
> 本文描述 Runtime 的断点恢复机制：GSN 确认、Session 恢复与重水合、Run 重放和宿主升级流程。Runtime 支持崩溃、重启和断连后的会话续接。

## 1. 概述

Runtime 支持基于检查点的断点恢复。Session 可以在崩溃、重启或连接断开后继续执行。恢复机制覆盖三个层次：

- **Session Resume**：在已有 Session 中继续新的 Run，保持 `sessionId` 不变，分配新 `runId`。
- **Session Rehydrate**：从持久化数据重建会话状态，供重连的客户端使用。
- **Run Replay**：从上次确认的 GSN 开始重放事件，恢复实时流式状态。

三层协作确保：正常断连时完整续接，崩溃恢复时从最近检查点重建，事件流不丢失已确认的增量。

## 2. 恢复层次

### 2.1 Session Resume

在已有 Session 中启动新 Run，延续对话历史。

- 使用相同的 `sessionId`，分配新的 `runId`。
- 加载 CanonicalHistory 作为上下文。
- 上一轮的 Selection（Provider、模型、Agent、参数）自动继承。
- 不重建流式状态，只恢复对话历史。

### 2.2 Session Rehydrate

在服务端从持久化数据重建会话状态，适用于宿主升级或宿主重连。

- 服务端加载 Session 快照，重建选择状态（Selection），Meeting 模式下恢复会议调用。
- 校验客户端传入的 Agent 定义是否与持久化快照一致（比对 Prompt 模板版本与 Prompt 哈希）。
- 返回瘦结果：仅 `SessionId`、`Status`（`Ready` / `PartiallyReady` / `Failed`）与 `Mismatched`（不一致的 Agent 列表），不携带完整上下文（见 §4.5）。
- 客户端据 `Status` 与 `Mismatched` 判断能否继续，而非用于重建 UI 上下文；Agent 快照、Blob 引用、消息计数等丰富上下文由 Session Resume 的结果 `SessionResumeResult`（见 §4.4）提供。

### 2.3 Run Replay

在 Run 执行期间断连后，从上次确认的 GSN 重放未确认的事件。

- 重放 `lastConfirmedGsn + 1` 之后的所有事件。
- 已确认的事件不重发，发出 `delta.dropped` 事件标记跳过的范围。
- 以 `(runtimeInstanceId, gsn)` 去重，确保幂等消费。

## 3. GSN 确认机制

### 3.1 全局序列号

每个 Runtime 事件携带一个 `gsn`（Global Sequence Number），在 Runtime 实例内单调递增。事件信封结构见 [11-事件协议参考](./11-事件协议参考.md)。

### 3.2 确认与重放

```text
客户端                          Runtime
  │                               │
  │  ← event (gsn=42)             │
  │  → AcknowledgeEventsAsync(42) │
  │                               │  标记 gsn ≤ 42 已确认
  │                               │
  │  （连接断开）                  │
  │                               │
  │  → 重连                       │
  │  ← events from gsn=43         │
  │                               │
```

- 客户端消费事件后调用 `AcknowledgeEventsAsync(lastConfirmedGsn)` 确认。
- 重连时 Runtime 从 `lastConfirmedGsn + 1` 开始重放。
- 去重依据 `(runtimeInstanceId, gsn)` 对，Runtime 重启后 `runtimeInstanceId` 变化，客户端应重置确认状态。

### 3.3 增量丢弃

当重放时部分增量已被清理（例如确认过的流式 delta 不再保留），Runtime 发出 `delta.dropped` 事件：

```json
{
  "runId": "run-1",
  "fromRunSequence": 5,
  "toRunSequence": 12
}
```

表示 `runSequence` 5 到 12 之间的增量不再重放。客户端收到后应将对应范围的流式内容标记为不可恢复。

## 4. Client SDK 恢复 API

### 4.1 ResumeSessionAsync

```csharp
ValueTask<SessionResumeResult> ResumeSessionAsync(
    string sessionId,
    CancellationToken cancellationToken = default);
```

在已有 Session 中恢复并准备继续新的 Run。

### 4.2 RehydrateSessionAsync

```csharp
ValueTask<SessionRehydrateResult> RehydrateSessionAsync(
    SessionRehydrateParameters parameters,
    CancellationToken cancellationToken = default);
```

从持久化数据完整重建会话状态。

### 4.3 参数结构

`SessionRehydrateParameters`：

```csharp
public sealed record SessionRehydrateParameters(
    string SessionId,
    AgentDefinition[] AgentDefinitions);
```

| 字段 | 说明 |
| --- | --- |
| `SessionId` | 要恢复的 Session 标识 |
| `AgentDefinitions` | 当前可用的 Agent 定义列表 |

### 4.4 Resume 结果

`SessionResumeResult`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `SessionId` | string | Session 标识 |
| `Mode` | RuntimeMode | Session 运行模式 |
| `LatestSelectionVersion` | int? | 最新选择版本号 |
| `Selection` | NextTurnSelection? | 下一轮选择 |
| `NeededDefinitions` | NeededAgentDefinition[] | 需要的 Agent 定义 |
| `LatestRun` | RunQueryResult? | 最近的 Run 状态 |
| `LastGsn` | long | 最后的 GSN |
| `LastCheckpoint` | string? | 最后检查点标识 |
| `IsFullyRecoverable` | bool | 是否可完整恢复 |
| `RecoveryDiagnostics` | string[] | 恢复诊断信息 |
| `MessageCount` | long | 消息总数 |
| `LastMessageSeq` | long? | 最后一条消息的序号 |
| `LastMessageId` | string? | 最后一条消息的标识 |
| `AgentSnapshots` | AgentSnapshot[]? | Agent 快照列表 |
| `BlobReferenceCount` | int | Blob 引用计数 |
| `BlobIds` | string[]? | 引用的 Blob 标识列表 |
| `MeetingState` | MeetingResumeState? | Meeting 模式恢复状态 |
| `WorkState` | WorkResumeState? | Work 模式恢复状态 |

### 4.5 Rehydrate 结果

`SessionRehydrateResult` 是瘦结果，只报告重水合状态与差异，不返回会话上下文（上下文重建发生在服务端，丰富字段由 §4.4 的 `SessionResumeResult` 承载）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `SessionId` | string | Session 标识 |
| `Status` | string | 重水合状态：`Ready`（一致，可继续）/ `PartiallyReady`（部分 Agent 缺失定义）/ `Failed`（存在不一致或无可用快照） |
| `Mismatched` | string[] | Prompt 模板版本或 Prompt 哈希与持久化快照不一致的 Agent ID 列表 |

### 4.6 ReadEventsAsync

从指定游标开始流式读取事件，用于重放：

```csharp
IAsyncEnumerable<RuntimeEventEnvelope> ReadEventsAsync(
    long eventReplayCursor,
    CancellationToken cancellationToken = default);
```

- `eventReplayCursor` 是重放起点的游标（一般取 `lastConfirmedGsn`），Runtime 从该游标之后的事件开始返回。
- 返回值为 `IAsyncEnumerable<RuntimeEventEnvelope>`，事件按序异步流式产出，由消费方逐条拉取，无需显式的 `maxCount` 批量上限。

## 5. RecoveryService

内部服务，协调 Runtime 启动时的恢复流程。

### 5.1 启动恢复

`RecoverOnStartupAsync` 在 Runtime 启动时执行：

1. 恢复已发送但未收到结果的工具调用（`RecoverSentToolIntentsAsync`）。
2. 将所有非终态 Run 标记为 `Interrupted`（`MarkInterruptedAsync`）。
3. 清理不一致的中间状态。

### 5.2 工具调用恢复

`RecoverSentToolIntentsAsync` 处理宿主侧工具调用的恢复：

- 查询所有 `Sent` 状态的工具意图。此处的 `Sent` 属于持久化层的 `ToolIntentStatus` 枚举（`Pending`/`Sent`/`Succeeded`/`Failed`/`Cancelled`/`Unknown`），表示"意图已发往宿主但结果未回"，它与 [13-工具授权与同意机制](./13-工具授权与同意机制.md) §7 的 `ToolCallStatus` 是两个不同类型，映射关系见 §6.3。
- 通过 `ToolGateway.RecoverSentIntentAsync` 向宿主查询结果。
- 幂等工具可以安全重发。
- 非幂等工具且结果不明时标记为需要人工干预。

### 5.3 数据存储

恢复依赖以下持久化来源：

| 来源 | 路径 | 内容 |
| --- | --- | --- |
| SQLite 数据库 | `state.db` | Session 元数据、Run 状态、工具意图、Work 检查点（`work_steps.checkpoint_json`） |
| 消息文件 | `messages/<sessionId>.jsonl` | 权威消息正文 |

> Work 模式的检查点数据存于 SQLite `work_steps.checkpoint_json` 列，`LastCheckpoint` 由这些 step 行派生（取最近的非空检查点）。`checkpoints/` 目录当前未被使用。

## 6. Server 端恢复

### 6.1 可重连 RPC

`ReconnectableDuplexRpcPeer` 封装了宿主连接的重连逻辑：

- 透明重连：发送请求时连接断开，自动等待新连接后重试。
- 工具调用恢复：`tool.call.request` 发送后连接断开，重连后通过 `ToolResultQuery` 查询结果。
- 轮询等待：50ms 间隔轮询直到解析到新的有效连接。

### 6.2 宿主租约监控

Runtime Server 通过工作区写租约（`WorkspaceWriteLock`）监控宿主连接状态：

- 租约过期或释放时触发断连处理。
- 活跃的 Run 进入中断或等待状态。
- 新宿主连接后触发 Session Rehydrate。

跨进程互斥锁文件位于系统临时目录 `<临时目录>/madorin.ai.runtime/workspace-locks/<sha256>.lock`（`<sha256>` 为规范化工作区路径的 SHA-256 摘要），而非工作区内的 `.madorin/locks/`；后者虽会被创建，但不承担跨进程互斥职责。

### 6.3 终态 Run 协调

断连后恢复的 Run 需要与宿主侧状态一致：

- 已完成或已失败的 Run 不重放。
- 进行中的 Run 从最后检查点重放事件。
- 工具执行状态通过 `ToolCallStatus` 枚举协调（宿主执行器上报的持久化执行状态，定义见 [13-工具授权与同意机制](./13-工具授权与同意机制.md) §7）。

需要区分两个类型：`ToolIntentStatus`（持久化层意图状态，含 `Sent`，见 §5.2）描述"意图相对宿主的投递生命周期"，`ToolCallStatus`（无 `Sent`，含 `Running`）描述"工具在执行器上的执行进度"。恢复时二者按下表映射：

| `ToolIntentStatus` | 对应 `ToolCallStatus` | 恢复动作 |
| --- | --- | --- |
| `Pending` | `Pending` | 意图未发出，可安全重发 |
| `Sent` | `Running`（结果未回） | 向宿主查询结果，确认后归入终态 |
| `Succeeded` | `Succeeded` | 终态，不处理 |
| `Failed` | `Failed` | 终态，不处理 |
| `Cancelled` | `Cancelled` | 终态，不处理 |
| `Unknown` | `Unknown` | 结果不明，需人工干预或重试 |

## 7. 宿主升级流程

宿主升级时需要保持 Runtime 会话连续：

```text
1. Drain        停止接受新 Run，等待进行中的 Run 完成
2. New Instance 启动新 Runtime 实例
3. Verify       验证新实例健康
4. Rehydrate    通过 RehydrateSessionAsync 重建所有活跃 Session
5. Smoke Test   执行一轮简单对话验证端到端可用
6. Switch       切换流量到新实例，关闭旧实例
```

整个过程中客户端持有 `lastConfirmedGsn`，新实例从该位置重放事件。

## 8. 边界

- **跨进程恢复**：同一工作区同一时间只允许一个 Runtime 实例（通过系统临时目录 `<临时目录>/madorin.ai.runtime/workspace-locks/<sha256>.lock` 的跨进程锁互斥）。
- **全局记忆**：全局记忆（`~/.madorin/memory.md`）无跨进程强一致性保证，升级时应避免并发写入。
- **检查点时效**：`work_steps.checkpoint_json` 中的检查点数据与当前 Runtime 版本绑定，跨版本升级不保证格式兼容。
- **Blob 一致性**：Blob 以 SHA-256 寻址，恢复时只验证引用存在性，不重新校验内容（除非显式运行 `storage check --verify-hashes`）。
