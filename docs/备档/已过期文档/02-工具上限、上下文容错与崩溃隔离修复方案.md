## 1. 结论与冻结决策

本次问题不是一个单点 Bug，而是三个相互放大的边界缺口：默认的单轮工具调用上限会中断 Run，不完整的工具调用历史会污染后续 Provider 请求，而失败收口的二次异常又可能被升级成 Runtime Fatal，最终表现为响应中断、会话无法继续，甚至整个进程退出。

修复顺序冻结为：

1. **P0：先完成崩溃隔离**。任何普通 Provider、工具、审批、上下文或单个 Run 的持久化收尾错误，都不能直接触发整个 Runtime 退出。
2. **P0：再完成 Provider 请求上下文容错**。复用旧项目的工具协议重排算法，并按目标 Provider/模型能力过滤历史图片、音频、文件、Reasoning 等不兼容内容。
3. **P1：最后调整工具数量策略**。取消 Runtime 默认“每轮最多 8 次工具调用”的硬限制；Kimi 单独保留“最多暴露 128 个工具定义”的 Provider 规则，并允许配置。

冻结的行为如下：

| 事项 | 冻结决策 |
| --- | --- |
| Runtime 每轮工具调用数 | 默认不限制，不再把 `null` 回退成 8；保留显式正整数作为宿主可选安全阀 |
| Runtime 工具轮数 | 本次不取消，仍保留 `MaxToolRounds`，避免模型无限循环 |
| Runtime 工具结果大小 | 本次不取消，仍保留单 Invocation 结果大小、内联内容、上下文窗口、超时和取消限制 |
| Kimi 工具数量 | 限制的是发给模型的**工具定义数量**，默认 128；不是模型一轮返回的 tool call 数量 |
| Kimi 配置 | `providers[]` 条目新增 `maxTools`；未配置时 Kimi 使用 128，正整数为上限，`0` 关闭裁剪，负数配置非法 |
| 历史修复位置 | 只修复发往目标 Provider 的请求投影，不改写 Canonical History，不伪造 user/tool 消息 |
| 历史图片 | 目标模型无 Vision 时，仅从历史投影移除图片；切回视觉模型时仍可从 Canonical History 恢复图片 |
| 当前轮不兼容输入 | 不静默丢弃。当前轮图片发给非视觉模型时，当前 Run 明确失败，但 Session 必须可继续下一轮纯文本对话 |
| 工具协议错误 | 重排非相邻结果；缺失结果的 assistant tool call 降级为普通 assistant 文本；孤立 tool 结果丢弃 |
| Run 异常 | 失败当前 Invocation/Run，保存脱敏错误并继续服务其他 Run |
| Runtime Fatal | 只用于已确认的根任务故障、全局存储不可用或不可恢复的不变量破坏；即使触发也必须受控退出，不允许闪退 |

### 1.1 两类“工具数量”不得再混用

| 概念 | 统计对象 | 当前问题 | 修复后 |
| --- | --- | --- | --- |
| 工具调用数量 | 模型一次响应返回的 `ToolCallContentBlock` 数量 | 三种模式默认超过 8 就拒绝当前 Run | 默认不限；显式配置正整数时才限制 |
| 工具定义数量 | `RuntimeProviderRequest.Tools` 中暴露给模型的 `ToolDescriptor` 数量 | 当前 Kimi Adapter 没有 128 裁剪 | Kimi 默认稳定保留前 128 个，可配置或关闭 |
| 工具轮数 | Provider -> Tool -> Provider 的循环轮数 | 默认 8 | 本次保留，防止无限循环 |

Kimi 的 128 限制不能通过 `MaxToolCallsPerRound` 实现。前者发生在 Provider 请求发送前，后者发生在 Provider 已经返回响应后；两者的时机、对象和失败后果完全不同。

### 1.2 对前置文档的局部修订

[01-功能缺口与崩溃隔离待办](./01-功能缺口与崩溃隔离待办.md)中关于并发、状态查询、进度和根任务 fail-stop 的设计继续有效。本文只修订其中一条升级规则：

- 单次 `CompleteFailedRunAsync` / `CompleteCancelledRunAsync` 收尾失败，不再立即调用 `TriggerRuntimeFatal`。
- 收尾失败先进入 Run 级待对账状态并执行有界重试；只有独立健康探测确认数据库或 Runtime 根基础设施已全局、持续不可用时，才允许升级为受控 Runtime Fatal。
- “一个 Run 无法完成一次终态提交”与“整个 Runtime 已不可恢复”必须由不同事实判定，不能再用同一个 catch 直接等价。

- 旧工具调用历史的重排、孤立结果清理和缺失结果降级。

- 不承诺在 `StackOverflowException`、`Environment.FailFast`、严重 OOM、原生崩溃和系统强杀下进行同进程恢复。

## 3. 当前代码事实与根因

### 3.1 默认 8 次工具调用限制

`RuntimeLimits` 本身已把 `MaxToolCallsPerRound` 定义为可空值，但以下入口把 `null` 再次回退成 8，导致“未配置”无法表达“不限制”：

| 位置 | 当前行为 |
| --- | --- |
| `src/Madorin.AI.Runtime.Modes.Expert/ExpertModeOrchestrator.cs` | 默认 `MaxToolCallsPerRound: 8`，运行时使用 `?? 8` |
| `src/Madorin.AI.Runtime.Modes.Meeting/MeetingInvocationExecutor.cs` | 默认 8，运行时使用 `?? 8` |
| `src/Madorin.AI.Runtime.Modes.Work/WorkModeOrchestrator.cs` | 默认 8，运行时使用 `?? 8` |
| `src/Madorin.AI.Runtime.Server/LocalRuntimeOptions.cs` | LocalRuntime 默认写死 8 |
| `src/Madorin.AI.Runtime.Server/RuntimeServer.cs` | `CreateNegotiatedLimits` 把空值协商成 8 |

在 Expert 模式中，Provider 一次返回超过 8 个 tool call 后会生成 `LimitsIncompatible`。失败路径随后仍可能调用 `PersistPartialAssistantAsync`，把未完成的 assistant tool call 写入 Canonical History，但没有对应的 tool result。下一轮重新投影时，这段历史会变成 Provider 协议非法链条。

### 3.2 当前上下文投影只保证分组，不负责修复

`ContextProjectionBuilder.BuildAtomicUnits`、Meeting 和 Work 的相应投影逻辑主要用于避免在 token 截断时拆开已有工具调用组，但没有处理以下历史损坏：

- assistant tool call 与对应 tool result 不相邻；
- assistant tool call 缺少一个或多个结果；
- tool result 找不到前置 assistant tool call；
- 重复或空 CallId；
- 历史消息包含目标模型不支持的图片、音频、文件或 Reasoning；
- 不兼容块被移除后留下空消息或孤立的 tool role。

`ConversationStore` 和 `ConversationIntegrityInspector` 当前验证 JSON、角色和 ContentBlock 类型是否有效，但不会验证 Provider 工具协议的语义完整性。该职责不应强行加入存储层，因为不同 Provider 和模型的能力不同。

### 3.3 能力校验存在，但缺少发送前历史降级

`ProviderCapabilityValidator` 已能识别 `Vision`、`Audio`、`Files`、`ToolCalling`、`Reasoning` 和模型级能力覆盖，但当前行为是发现不兼容块后直接抛错。它无法区分：

- **历史内容**：曾经由视觉模型合法产生或接收，本轮切换到文本模型后应从 Provider 投影中移除；
- **当前轮输入**：用户正在要求非视觉模型识别新图片，不能静默移除，必须明确拒绝当前 Run。

因此，视觉模型 -> 文本模型 -> 纯文本继续对话的正常切换也会被历史图片永久阻断。

### 3.4 当前失败收口会主动触发 Runtime Fatal

`RuntimeServer.ExecuteRunAsync` 已有 Run 级 catch-all，但它调用的两个终态收口方法仍有更危险的二次异常路径：

```text
ExecuteRunAsync catch
    -> CompleteFailedRunAsync / CompleteCancelledRunAsync
        -> 终态数据库提交或 Outbox 派发再次抛错
            -> TriggerRuntimeFatal
                -> _fatalSignal fault + _shutdown.Cancel()
                    -> RuntimeServer.RunAsync 结束
                        -> CLI / Runtime 进程退出
```

`CompleteFailedRunAsync` 和 `CompleteCancelledRunAsync` 当前在 catch 中既调用 `TriggerRuntimeFatal` 又重新抛出。一个 Run 的收口失败因而可以直接变成整个 Runtime 的根故障。

`LocalRuntime.RunNewSessionAsync` 和 `RunExistingSessionAsync` 则直接枚举 `_executionCore.RunAsync`，只有容量释放的 `finally`，没有与 Server 对等的 Run 级失败终态边界。异常可一直传播到一次性 CLI 或 REPL 上层。

此外，[前置文档](./01-功能缺口与崩溃隔离待办.md)已确认 `RunRegistry.RunLease` 的 Timer 取消回调也可能让 `AggregateException` 越过回调边界。这条已知进程级崩溃路径必须与本次收口修复一起完成，不能只改 `RuntimeServer` 的 catch。

## 4. 旧项目复用结论

旧项目位于 `E:/Netor.me/Madorin/Netor.Madorin/Src/Netor.Cortana.AI`。本次复用的是已经验证过的策略和算法，不是复制旧项目的框架绑定。

### 4.1 Kimi 128 工具定义限制

旧实现的关键事实：

- `Drivers/Providers/Kimi/KimiProviderDriver.cs` 声明 `DefaultMaxTools: 128`。
- `Providers/ProviderToolLimitContextProvider.cs` 在 Provider 调用前裁剪工具定义。
- `maxTools <= 0` 表示关闭限制。
- 采用 `Take(maxTools)` 保留输入顺序中的前 N 个工具，行为稳定且可预测。
- 记录原始数量、保留数量、移除数量和被移除工具名摘要。
- `Agents/AIAgentFactory.cs` 允许环境变量、系统设置覆盖 Provider 默认值。

新 Runtime 的配置系统与旧项目不同：当前权威配置是 `~/.madorin/config.json` 的 `providers[]`，没有通用的 Provider 环境变量覆盖层。因此本次只迁移“Provider 默认值 + Provider 条目覆盖 + 请求发送前裁剪 + 结构化日志”设计，不照搬 `CORTANA_KIMI_MAX_TOOLS` 和 `AI.Provider.Kimi.MaxTools`。

### 4.2 工具调用历史协议重排

旧 `Providers/ChatHistoryDataProvider.cs` 的 `ReorderForToolCallProtocol` 已实现：

1. 第一遍按 CallId 建立 tool result 索引。
2. 第二遍保持 assistant 消息的原始顺序。
3. 遇到 assistant tool call 时，将匹配的 tool result 紧跟在其后。
4. 已消费的 tool result 不再重复输出。
5. 任一 tool call 缺少结果时，将整条 assistant tool-call 消息降级为普通 assistant 文本。
6. 找不到归属的孤立 tool 消息直接丢弃。
7. 记录 orphan、missing 和 non-adjacent 诊断数量。

旧 `Providers/TokenTrackingChatClient.cs` 还提供 `OrphanToolMessages`、`MissingToolResponses`、`NonAdjacentToolMessages` 诊断思路。新 Runtime 应复用这些诊断维度。

### 4.3 旧实现不能直接复制的部分

| 旧实现 | 新 Runtime 处理 |
| --- | --- |
| `AIChatMessage`、`FunctionCallContent`、`FunctionResultContent` | 改用 `RuntimeProviderMessage`、`ToolCallContentBlock`、`ToolResultContentBlock` |
| MAF `AIContextProvider` | 改成 Provider 请求边界的纯投影器 |
| Cortana 数据库实体和 `ChatMessageAssetService` | 继续使用 Runtime 的 JSONL Canonical History 与 BlobReference |
| EventHub 系统通知 | 首批使用 Runtime 结构化日志和现有诊断事件，不增加平行消息总线 |
| 历史图片无条件回灌 | 必须按目标 Provider/模型的有效能力过滤 |

旧 `BuildContentsWithAssets` 会把历史图片无条件恢复为 `DataContent`，没有检查目标模型的 Vision 能力。这正是本次必须补齐、不能照搬的缺口。

## 5. 目标结构与请求流程

### 5.1 总体数据流

```text
Canonical History（权威、不可因 Provider 差异改写）
    |
    v
模式 Context Projection（token、轮次、角色、摘要策略）
    |
    v
ProviderRequestCompatibilityProjector
    |- 只处理历史前缀
    |- 按目标模型能力递归过滤不兼容块
    |- 修复 tool call / tool result 协议
    |- 生成结构化诊断
    |
    +---- 当前轮消息保持原样 ----+
                              |
                              v
ProviderCapabilityValidator（验证最终请求，当前轮不兼容则失败当前 Run）
                              |
                              v
Provider Adapter
    |- Kimi：裁剪本轮暴露的工具定义，默认 128
    |- 其他 Provider：不应用 Kimi 限制
                              |
                              v
Provider HTTP / SDK
```

修复器必须是无存储副作用的纯投影：输入消息、目标能力和历史边界，输出新消息数组与诊断；不得在内部写 JSONL、数据库、Blob 或 Outbox。

### 5.2 区分历史与当前轮

仅靠消息角色推断“最后一条 user 就是当前轮”不够可靠，Meeting、Work、工具循环和摘要调用都可能生成不同的角色序列。实施时在 `RuntimeProviderRequest` 的 record body 增加一个仅运行时使用、带 `[JsonIgnore]` 的 `HistoryMessageCount` init 属性：

- `0..HistoryMessageCount-1` 是允许兼容修复的历史前缀；
- 其后的 system/user/assistant/tool 内容属于当前 Invocation，必须保持业务内容不变；
- 属性不进入 Provider JSON，不修改现有主构造函数，不影响协议快照；
- 未设置时默认为 `0`，表示不允许静默过滤任何消息，保持对第三方调用者的保守行为；
- Provider 重试和 `with` 克隆必须保留该值；进入当前工具循环后新增的 assistant/tool 消息不得被当成旧历史清理。

Expert、Meeting、Work 在完成各自 Context Projection 后、追加当前轮输入前记录历史消息数。`LocalRuntime.GenerateSummaryMessageAsync` 如果发送的是一个全新摘要请求，则历史数保持 0；不能为了让摘要成功而静默删除摘要输入。

### 5.3 唯一 Provider 调用边界

新增 `ProviderInvocationBoundary`，统一执行兼容投影、最终能力验证和 Adapter 调用。以下生产调用点必须改用该边界，禁止继续直接调用 Adapter：

- `ExpertModeOrchestrator.RunAsync`
- `WorkModeOrchestrator.ExecuteInvocationAsync`
- `ProviderAgentInvocationExecutor.ExecuteAsync`（Meeting 默认走该入口）
- `LocalRuntime.GenerateSummaryMessageAsync`

增加架构守卫测试：除 Provider Adapter 实现、测试辅助和 `ProviderInvocationBoundary` 外，生产源码中不得新增对 `IRuntimeProviderAdapter.CompleteStreamingAsync` 的直接调用。这样以后新增模式也不会绕过历史容错。

## 6. P0：Runtime 与 LocalRuntime 崩溃隔离

### 6.1 异常分类

| 分类 | 示例 | 处理 |
| --- | --- | --- |
| Invocation/Run 业务故障 | Provider 400/500、模型能力不支持、工具抛错、审批失败、上下文协议非法、单 Run 超时 | 失败当前 Invocation/Run；其他 Run 和 Runtime 继续 |
| 可恢复基础设施故障 | SQLite busy、一次终态提交失败、一次 Outbox 派发失败、临时文件 IO 错误 | 有界重试或进入待对账；不立即 Fatal |
| Runtime 根故障 | 控制/事件/租约关键根循环意外结束，工作区锁丢失，独立探测确认数据库全局持续不可用 | 记录根因、取消根任务、排空可排空工作并以非零码受控退出 |
| 进程外不可捕获故障 | FailFast、StackOverflow、严重 OOM、原生崩溃、系统强杀 | 由 Client/宿主进程监控、重启和查询对账兜底 |

“异常类型是 `SqliteException`”本身不足以判断 Runtime Fatal。必须结合故障范围、独立健康探测和连续失败次数判断，避免一个 Run 的事务冲突被误判成全局数据库死亡。

### 6.2 终态收口改为 no-throw 结果

将 `CompleteFailedRunAsync` 和 `CompleteCancelledRunAsync` 从“失败就抛出并 Fatal”改为返回内部结果，例如：

```text
Committed          终态和 Outbox 已原子提交
AlreadyTerminal    其他路径已经提交终态，幂等成功
DispatchPending    终态已提交，事件尚未派发，可由 Outbox 重放
RetryPending       终态尚未提交，已进入 Run 级待对账队列
```

具体规则：

1. 方法内部不得调用 `TriggerRuntimeFatal`，也不得把普通异常重新抛回 `ExecuteRunAsync` 的 Task 根部。
2. `TryCommitTerminalRunAsync` 继续保证 Run 终态与对应 Outbox 事件原子提交。
3. 终态已提交但即时派发失败时返回 `DispatchPending`；Outbox 是权威补偿，不回滚终态，也不失败 Runtime。
4. 终态提交失败时执行少量有界重试；仍失败则把 RunId、目标终态、脱敏错误、首次失败时间和重试次数放入 `_pendingTerminalRuns`。
5. 待对账 Run 在进程内查询时显示 `Persisting`/待对账，而不是继续伪装 `Running`；提交成功后切换到真实终态并移出队列。
6. Runtime 关闭前进行最后一次有界排空；未成功项目在下次启动时沿用现有恢复流程变为 `Interrupted`，不得伪造已提交的 `Failed`。
7. 只有后台对账持续失败，并且独立数据库健康探测确认全局读写不可用时，才由根生命周期触发受控退出。

待对账队列首批使用有界内存结构，不新建另一套持久化数据库。原因是底层终态存储不可写时，新建同源持久化队列并不能提高可靠性；重启后的 `Interrupted` 恢复已经是现有最终兜底。

### 6.3 `ExecuteRunAsync` 的边界

`RuntimeServer.ExecuteRunAsync` 保留现有 catch-all，但调整为：

- Provider、工具、投影和模式异常统一转换为脱敏 `RuntimeError`；
- 释放的只允许是当前 Run 的容量、租约和取消资源；
- 调用 no-throw 终态收口，并记录其结果；
- 无论终态即时提交、等待重试或事件等待 Outbox 派发，都不得让该执行 Task 以未观察异常结束；
- `_activeRuns` 移除与待对账登记必须有明确顺序，避免查询窗口中 Run 完全消失；
- 其他 Run 的取消令牌、Provider 容量、Session 容量和事件流不得受影响。

工具网关的意外异常不需要在每个工具实现中重复 catch。它可以冒泡到 Run 级边界，但必须保留 InvocationId、ToolCallId、ToolId 和 DiagnosticId，日志中不得记录未脱敏参数或密钥。

### 6.4 `LocalRuntime` 的对等隔离

`RunNewSessionAsync` 和 `RunExistingSessionAsync` 需要与 Server 一致的 per-Run catch-all：

- 已经发送 `run.accepted` 后发生异常时，尽力提交并返回 `invocation.failed` / `run.failed`，而不是让枚举器只抛一个无终态异常；
- 调用方取消继续按取消语义处理，不转换成普通失败；
- 收口自身失败时返回带 DiagnosticId 的本次命令错误，REPL 主循环保持可继续接收下一条命令；
- `_runGate` 始终释放，但不能把异常吞成成功退出码；
- LocalRuntime 与 Server 共用终态错误映射和安全取消辅助，不维护两套错误码。

### 6.5 Timer、信号和取消回调 no-throw

完成前置文档已识别的 `RunRegistry.RunLease.CancelForTimeout` 修复：

- Timer 回调调用 `CancellationTokenSource.Cancel(throwOnFirstException: false)`；
- 捕获并展开 `AggregateException`，逐项记录脱敏诊断；
- 不允许异常越过 Timer/Console/POSIX 信号回调边界；
- 回调异常不能改变“该 Run 已超时/已取消”的业务事实；
- 同一安全取消辅助可用于 Runtime 关闭、Ctrl+C 和 SIGTERM，但不能把普通 Run 取消升级为 Runtime Fatal。

### 6.6 Fatal 的唯一入口约束

`TriggerRuntimeFatal` 保留，但调用点必须收敛并逐一注释所属根故障：

- 允许：关键根循环 fault、工作区租约丢失、全局数据库健康探测确认不可恢复、Runtime 内部不变量破坏；
- 禁止：Provider/模型返回错误、工具异常、能力不支持、历史修复失败、单 Run 终态提交第一次失败、Outbox 即时发送失败、Client 断开；
- 增加测试或静态审计，确保 `CompleteFailedRunAsync`、`CompleteCancelledRunAsync`、模式编排器和工具网关不再直接引用它。

即使是合法 Fatal，也必须先写结构化根故障日志、停止接受新 Run、取消兄弟根任务并由 `serve` 返回非零退出码。这里的目标是受控 fail-stop，不是继续运行一个关键子系统已经死亡的半失效进程。

## 7. P0：Provider 请求上下文容错

### 7.1 新增纯投影器

在 `Madorin.AI.Runtime.Providers.Abstractions` 新增 `ProviderRequestCompatibilityProjector`。建议接口接收：

- `RuntimeProviderMessage[] Messages`
- `int HistoryMessageCount`
- Provider 级能力
- `ProviderModel` 列表和当前 ModelId
- CancellationToken

返回：

- 修复后的 `RuntimeProviderMessage[]`
- 有效 Provider/模型能力
- `ProviderRequestProjectionDiagnostics`

诊断至少包含：

| 字段 | 含义 |
| --- | --- |
| `RemovedImageBlockCount` | 因无 Vision 移除的历史图片块数量 |
| `RemovedAudioBlockCount` | 因无 Audio 移除的历史音频块数量 |
| `RemovedFileBlockCount` | 因无 Files 移除的其他历史 Blob 数量 |
| `RemovedReasoningBlockCount` | 因无 Reasoning 移除的历史推理块数量 |
| `RemovedToolBlockCount` | 因无 ToolCalling 移除的历史工具块数量 |
| `DroppedEmptyMessageCount` | 过滤后无内容而丢弃的历史消息数量 |
| `ReorderedToolResultCount` | 被移动到对应 assistant 后的结果数量 |
| `DroppedOrphanToolMessageCount` | 丢弃的孤立 tool 消息数量 |
| `DegradedAssistantToolCallCount` | 因缺少结果而降级的 assistant 消息数量 |

诊断只记录数量、ProviderId、ModelId、RunId、InvocationId 和有限的 CallId/工具名摘要；不得记录图片字节、完整工具参数、完整工具结果、用户正文或 API Key。

### 7.2 历史内容能力过滤

投影器先处理历史前缀中的 ContentBlock：

| 内容块 | 目标能力不足时的历史处理 |
| --- | --- |
| `BlobRefContentBlock`，MIME 为 `image/*` | 无 Vision 时移除 |
| `BlobRefContentBlock`，MIME 为 `audio/*` | 无 Audio 时移除 |
| 其他 `BlobRefContentBlock` | 无 Files 时移除 |
| `ReasoningContentBlock` | 无 Reasoning 时移除 |
| `ToolCallContentBlock` / `ToolResultContentBlock` | 无 ToolCalling 时移除，并继续做角色/空消息清理 |
| `TextContentBlock` | 始终保留 |

过滤必须递归进入 `ToolResultContentBlock.Content`，否则工具结果内部的图片或文件仍可能绕过顶层校验。递归过滤后如果 tool result 内容为空，可保留一个明确、固定且不含用户数据的文本占位，表示“历史工具结果包含目标模型不支持的内容”；这不是伪造工具执行结果，因为 CallId、成功状态和历史事实都保持不变。

普通 user/assistant 消息过滤后为空时直接从 Provider 投影丢弃，不向 Canonical History 写回，也不补假的 user 文本。system 消息不允许被整体静默丢弃；若未来 system 中出现唯一且不兼容的非文本块，应把当前 Run 判为投影错误。

### 7.3 工具协议修复顺序

能力过滤完成后，对历史前缀执行旧项目的两遍算法：

1. 按原始消息位置扫描所有 role=tool 的结果，以 CallId 建立索引；同一 CallId 多次出现时只允许消费首个有效结果，其余计为 orphan/duplicate。
2. 再按原始顺序扫描消息。
3. 普通 system/user/assistant 文本消息原序输出。
4. 遇到 assistant tool call，收集其全部非空且唯一 CallId。
5. 所有 CallId 都有未消费结果时，先输出 assistant，再按 tool call 在 assistant 中的顺序紧邻输出结果。
6. 任一 CallId 缺失、为空、重复或结果已被消费时，整条 assistant tool-call 消息降级为普通 assistant 文本。
7. 扫描到仍未被消费的 role=tool 消息时丢弃。
8. 最后拼接完全未修改的当前轮后缀，再执行最终能力与协议验证。

降级文本必须确定性生成，并优先保留 assistant 原有 `TextContentBlock`。如果原消息没有文本，则生成最小审计摘要，例如只包含“历史助手曾请求工具但执行链不完整”以及有限的工具名，不包含完整 Arguments。不得将 tool call JSON 整段塞回提示词。

### 7.4 当前轮失败与后续恢复

- 当前轮把图片发送给无 Vision 模型：`ProviderCapabilityValidator` 在 HTTP 前拒绝，当前 Run 失败；Session 保持可继续。
- 下一轮发送纯文本：历史前缀中的旧图片会被过滤，请求可正常发送。
- 再切回视觉模型：因为 Canonical History 未改写，旧图片重新进入 Provider 投影。
- 当前轮产生了部分 assistant tool call 后工具异常：当前 Run 失败；下一轮该段已成为历史，由协议修复器降级或重排。
- Provider 请求投影最终仍不合法：失败当前 Run 并提供 DiagnosticId，不允许触发 Runtime Fatal，也不把失败后的 Provider 请求覆盖回历史。

对“最后一条必须是 user”的错误不采用补写假 user 的方案。正常新 Run 的当前轮 user 消息会自然位于投影末端；如果某个内部调用确实没有当前输入而目标 Provider 要求 user 尾部，应在该调用入口明确构造合法业务提示，或失败该 Invocation，不能由通用修复器捏造对话。

### 7.5 Canonical History 写入约束

为减少继续制造不完整链条，模式编排器还应遵守：

- 因显式工具调用数上限、重复 CallId 或其他“尚未执行工具”的预检失败时，不持久化裸 assistant tool-call 组；只保留已产生的普通文本/Reasoning，或保存明确的失败元数据。
- 工具执行中途失败时允许保留真实审计记录，但不得伪造尚未执行工具的结果；后续 Provider 投影负责兼容修复。
- 已经成功执行并持久化的 tool result 不得因另一个 tool 失败而删除。
- Canonical History 自愈工具可以另行提供离线审计，但不作为本次请求成功的前置条件。

### 7.6 可观察性

首批不增加新的公共事件类型。使用现有结构化日志记录投影调整；Expert/Meeting/Work 已有上下文调整事件的地方可把 Strategy 追加 `provider-compatible`，但不得为了诊断修改必填协议字段语义。

日志事件建议固定名称：

- `ProviderHistoryCompatibilityAdjusted`
- `ProviderHistoryToolProtocolReordered`
- `ProviderHistoryUnsupportedContentRemoved`
- `ProviderRequestCompatibilityFailed`

只有实际发生调整时写 Warning；无调整的正常请求不逐次写噪声日志。

## 8. P1：Kimi 128 工具定义裁剪

### 8.1 配置契约

当前独立配置以 `ProviderEntry` 表示 `providers[]`。新增可空 `MaxTools`，JSON 名为 `maxTools`：

```json
{
  "name": "kimi",
  "protocol": "Kimi",
  "baseUrl": "https://api.moonshot.cn/v1",
  "apiKey": "***",
  "maxTools": 128,
  "models": ["moonshot-v1-8k"]
}
```

配置语义冻结为：

| 配置值 | Kimi | 非 Kimi |
| --- | --- | --- |
| 缺失 / `null` | 使用 Provider 默认值 128 | 不限制 |
| 正整数 N | 最多暴露 N 个工具定义 | 首批忽略并由配置校验提示该字段仅对声明了默认/支持上限的 Provider 生效 |
| `0` | 关闭裁剪，暴露全部工具定义 | 不限制 |
| 负数 | 配置校验失败，Adapter 不创建 | 配置校验失败 |

不在本批新增 `MADORIN_KIMI_MAX_TOOLS`。如果未来 Runtime 建立统一环境变量覆盖规范，再按统一优先级扩展，不能只为 Kimi 单独创造第二套配置来源。

### 8.2 Provider 默认值承载

扩展内部 `StandaloneProviderProtocolDefinition`，增加可空 `DefaultMaxTools`：

- Kimi 定义为 128；
- 其他 Provider 为 `null`；
- `StandaloneProviderFactory` 解析 `entry.MaxTools ?? definition.DefaultMaxTools ?? 0`；
- `StandaloneConfigValidator` 在创建 Adapter 前完成范围和适用性校验；
- `config show` 必须显示最终值及来源时，输出不能包含 API Key；如果当前命令只显示原始配置，则至少保证 `maxTools` 正常序列化与反序列化。

该设计对应旧项目的 `AiProviderDriverDefinition.DefaultMaxTools`，但适配当前 Runtime 的配置模型。

### 8.3 Kimi Adapter 最终防线

Kimi 限制必须位于 `KimiProviderAdapter.CompleteStreamingAsync` 的 Provider 发送边界，不能只放在 CLI 工厂，因为参考宿主或测试可能直接实例化 Adapter。

新增无框架依赖的 `ProviderToolDefinitionLimiter`，核心行为：

```text
输入：ToolDescriptor[]? tools, int maxTools
maxTools <= 0 或 count <= maxTools：原样返回
否则：按输入顺序保留前 maxTools 个，并返回移除项诊断
```

Kimi Adapter 使用规则：

1. `RuntimeProviderRequest.Tools` 不原地修改，生成 `effectiveTools`。
2. 只有 `ChatOptions.Tools` / 最终 HTTP 请求使用 `effectiveTools`。
3. 历史消息中的 tool call/tool result 做名称和 ToolId 映射时仍允许查询原始完整描述符，避免历史引用因本轮裁剪失去名称。
4. Skills 或工具执行网关仍持有完整 Tool Catalog；裁剪只影响本轮模型可见范围，不删除或禁用全局工具。
5. 被裁剪的工具不应被模型新调用；若 Provider 返回未暴露的工具名，现有工具网关按未知/未授权工具失败当前 Invocation。

### 8.4 顺序与可预测性

首批复用旧项目的 `Take(maxTools)` 策略，保留 `RuntimeProviderRequest.Tools` 的既有顺序，不在 Kimi Adapter 内随机选择或重新按名称排序。验收必须证明同一 Tool Catalog 快照和同一选择配置会得到相同的前 128 项。

如果上游 Tool Catalog 当前顺序不能保证确定性，应在 Tool Catalog 构建边界统一固定顺序，而不是只在 Kimi 内临时排序。排序策略必须保证内置工具、显式 Agent 工具和 Skills/MCP 工具的既有优先级不被无意改变；该事实需要实施时先用测试锁定。

### 8.5 Kimi 裁剪日志

仅在发生实际裁剪时记录 Warning：

- ProviderId、ModelId、RunId、InvocationId；
- `OriginalToolCount`、`MaxTools`、`KeptToolCount`、`RemovedToolCount`；
- 最多 20 个被移除工具名的摘要；
- 配置来源：ProviderDefault 或 ProviderEntry。

不向系统提示词注入“请告诉用户工具被裁剪”的说明。该说明会污染模型任务并消耗上下文；Runtime 日志和可查询诊断才是基础设施行为的权威记录。若产品 UI 后续需要提示，应基于明确的 Runtime 事件单独评审。

## 9. P1：移除默认 8 次单轮工具调用限制

### 9.1 推荐语义

`RuntimeLimits.MaxToolCallsPerRound` 保留以兼容现有 Contract 和宿主代码，但语义改为：

- `null`：不限制，也是 Runtime 默认值；
- 正整数：宿主显式启用的单轮安全阀；
- `0` 或负数：配置/参数非法，不与 Kimi 的 `0=关闭裁剪` 混用。

保留显式安全阀的原因是嵌入式宿主可能需要控制极端 fan-out，但独立 Runtime 不应再无配置地拒绝第 9 个正常工具调用。

### 9.2 代码调整

三个模式统一改为条件判断：只有 `MaxToolCallsPerRound is > 0` 时才比较 tool call 数量。必须移除所有 `?? 8` 和默认构造中的 `MaxToolCallsPerRound: 8`：

- `ExpertModeOrchestrator`
- `MeetingInvocationExecutor`
- `WorkModeOrchestrator`
- `LocalRuntimeOptions`
- `RuntimeServer.CreateNegotiatedLimits`

`RuntimeLimits` record 当前默认值已经是 `null`，无需删除属性或改主构造函数。Server 协商时直接传递实际可空值；Client 收到 `null` 应理解为无单轮调用数上限。

### 9.3 保留的保护措施

- `MaxToolRounds` 继续限制往返轮数；默认值本次不变。
- `MaxToolResultBytesPerInvocation` 和 `MaxInlineContentBytes` 继续防止结果膨胀。
- Run 超时和 CancellationToken 继续提供总时限。
- Tool Gateway 继续逐个执行权限、审批、幂等和副作用检查。
- 同轮 CallId 必须唯一；重复 CallId 仍失败当前 Invocation。
- 工具执行可按现有策略顺序进行；本次不顺带改成无限并行执行。

取消数量硬限制不等于取消资源治理。大量工具调用造成的时间和结果体积风险由轮数、超时、结果大小和现有工具权限边界承担。

## 11. 测试与验收矩阵

### 11.1 崩溃隔离

| 场景 | 必须断言 |
| --- | --- |
| Run A Provider 抛普通异常，Run B 同时执行 | A 为 Failed；B 继续流式输出并完成；Runtime 进程存活 |
| Run A 工具网关抛未预期异常 | A 带 ToolId/CallId 对应的脱敏诊断；其他 Run 不取消 |
| Run A 上下文投影器抛异常 | 只失败 A；Canonical History 未被投影结果覆盖；下一轮仍可运行 |
| `CompleteFailedRunAsync` 第一次提交失败、第二次成功 | 不调用 Fatal；最终状态与 Outbox 同时提交；只产生一个终态 |
| 终态提交持续失败 | Run 进入待对账；Runtime 继续接受不依赖故障资源的操作；查询不把它显示为正常 Running |
| 终态已提交、即时事件派发失败 | 查询已是终态；Outbox 重放后事件到达；Runtime 不退出 |
| `CompleteCancelledRunAsync` 收口失败 | 与 Failed 同样 no-throw，不因取消路径触发 Runtime Fatal |
| Timer 取消注册回调抛一个或多个异常 | Timer 回调不越界；Run 标记超时；Runtime 和兄弟 Run 存活 |
| 根控制/事件循环真实 fault | 停止接受新 Run；兄弟根任务取消；进程记录根因后非零受控退出 |
| LocalRuntime 单 Run Provider/工具异常 | 返回失败事实或本次命令错误；REPL 可继续执行下一条纯文本请求 |

进程存活断言必须在独立子进程端到端测试中完成，不能只用单元测试证明 catch 被调用。测试应等待一次心跳或执行第二个 Run，避免“进程尚未退出”造成假阳性。

### 11.2 工具协议修复

| 输入历史 | 期望 Provider 投影 |
| --- | --- |
| assistant(call A) -> tool(A) | 原样保持 |
| assistant(call A) -> user/assistant 文本 -> tool(A) | tool(A) 移到 assistant 后，其他消息相对顺序保持 |
| assistant(call A, B) -> tool(B) -> tool(A) | assistant 后按 call A、B 的声明顺序输出两个结果 |
| assistant(call A) 无结果 | assistant 降级为普通文本，不包含 ToolCallContentBlock |
| assistant(call A, B) 只存在 A 结果 | 整条 assistant 降级；A 结果随后因孤立被丢弃，不保留半条协议链 |
| 孤立 tool(A) | 丢弃并增加 orphan 计数 |
| 重复 tool(A) 结果 | 首个有效结果被消费，其余丢弃并记录 duplicate/orphan |
| assistant 中 CallId 为空或重复 | 降级为文本，不发送非法 tool_calls |
| 历史末尾是未完成 assistant tool call，当前轮追加 user | 历史 assistant 降级，最终请求自然以当前 user 结束 |

每条测试同时断言输入数组和 Canonical History 记录未发生修改，确保投影器没有原地写入。

### 11.3 模型能力切换

1. 使用视觉模型发送“文本 + 图片”，保存 Canonical History。
2. 切换到无 Vision 的文本模型并发送纯文本；断言历史文本保留、历史图片从本次 Provider 请求移除、Run 成功。
3. 再切回视觉模型；断言 Canonical History 中原图片仍存在并重新进入 Provider 请求。
4. 在无 Vision 模型的**当前轮**直接发送图片；断言 HTTP 前得到明确能力错误，当前 Run 失败而 Session 不损坏。
5. 失败后继续发送纯文本；断言新 Run 成功，证明一次不兼容输入不会永久废弃对话。

同样覆盖：

- 无 Audio 模型过滤历史 `audio/*`；
- 无 Files 模型过滤历史非图片/音频 Blob；
- 无 Reasoning 模型过滤历史 Reasoning；
- ToolResultContentBlock 内部嵌套图片的递归过滤；
- 无 ToolCalling 模型移除历史工具块后仍能继续纯文本；
- 当前轮不兼容内容不会被静默移除。

### 11.4 Kimi 工具定义限制

| 场景 | 期望 |
| --- | --- |
| Kimi 127/128 个工具，未配置 `maxTools` | 全部发送，无裁剪 Warning |
| Kimi 129 个工具，未配置 | 发送前 128 个；原请求数组不变；记录 1 个移除项 |
| Kimi 配置 `maxTools: 32` | 只暴露前 32 个 |
| Kimi 配置 `maxTools: 0` | 全部暴露，关闭裁剪 |
| Kimi 配置负数 | `config validate` 明确定位 `providers[i].maxTools` |
| 非 Kimi Provider 129 个工具 | 不应用 Kimi 128 默认值 |
| 相同 Catalog 快照重复请求 | 保留集合与顺序完全一致 |
| 历史引用第 129 个工具 | 历史名称映射仍可完成，但该工具不在本轮可调用定义中 |
| Adapter 被直接实例化，不经过 CLI 工厂 | Kimi 默认 128 仍生效 |

Fake HTTP Server 必须检查最终序列化请求中的 `tools` 数量，不能只断言内部 limiter 返回值。

### 11.5 取消默认 8 次调用限制

- Expert Fake Provider 一轮返回 12 个唯一 tool call，12 个均进入 Tool Gateway，不产生 `LimitsIncompatible`。
- Meeting 和 Work 重复相同场景，行为一致。
- 显式配置 `MaxToolCallsPerRound=8` 时，第 9 个仍触发宿主安全阀，但不得把裸 assistant tool call 污染后续 Provider 投影。
- `MaxToolRounds` 仍能在超出轮数时终止循环。
- 12 个调用累计结果超过大小限制时，仍按结果大小失败，而不是因为调用数量失败。
- Server/Client 协商得到 `MaxToolCallsPerRound=null`，不得在任一端还原成 8。

### 11.6 回归与工程门禁

- `dotnet build .\Madorin.AI.Runtime.slnx -c Debug` 零警告、零错误。
- Provider、Modes、Protocol、EndToEnd 相关测试项目全部通过。
- 完整解决方案测试通过；若耗时过长，先跑聚焦测试再跑全量门禁。
- `dotnet publish` 的 Windows `win-x64` Native AOT 保持零 trimming/AOT 警告。
- `RuntimeJsonContext` 不回退到反射序列化。
- `git diff --check` 通过，配置样例和文档中的字段名与实际 camelCase JSON 一致。
- 真实 Kimi 冒烟只在已有凭据和明确启用真实 Provider 测试时执行；没有凭据不能阻断离线协议测试。

## 13. 回滚与兼容策略

### 13.1 分批回滚

- 崩溃隔离、上下文投影、Kimi 裁剪分别作为独立实施批次，避免一个开关同时改变三类行为。
- 上下文投影器必须保留“无调整时输出与输入等价”的性质；发现 Provider 兼容回归时，可临时关闭特定过滤策略，但不能回滚 Run 崩溃隔离。
- Kimi 可通过 `maxTools: 0` 关闭裁剪，用于 Provider 已提高限制后的临时验证。
- Runtime 默认调用数不限不设置隐藏环境变量回滚；需要限制的宿主应显式传入正整数 `MaxToolCallsPerRound`。

### 13.2 数据兼容

- 不修改 Canonical History 格式，不需要迁移已有 JSONL。
- 不修改数据库 Schema；待对账为进程内补偿，重启沿用现有 `Interrupted` 恢复。
- `ProviderEntry.MaxTools` 是可空新增字段，旧 `config.json` 缺失时可正常读取。
- `HistoryMessageCount` 不序列化，不改变 Provider 请求持久化或公开协议。
- 旧的不完整 tool call 历史无需批量离线迁移，首次发送给 Provider 时即时修复。

### 13.3 风险控制

| 风险 | 控制措施 |
| --- | --- |
| 过滤历史图片造成语义丢失 | 只过滤目标模型无法处理的历史块；保留同消息文本；Canonical 不变；记录诊断 |
| 工具调用降级文本泄漏参数 | 只保留原文本和有限工具名，不包含完整 Arguments/Result |
| Kimi 前 128 个不是最相关工具 | 首批保持旧算法和稳定顺序；后续另行设计任务相关排序，不在本 Bug 中猜测优先级 |
| 默认不限导致模型大量调用 | 保留轮数、超时、结果大小、权限和宿主显式安全阀 |
| 终态提交失败后状态短暂不一致 | 待对账状态、有界重试、查询覆盖、Outbox 和重启 Interrupted 恢复 |
| 过度吞异常造成半失效 | 仅 Run 级异常 no-throw；根任务和经独立探测确认的全局故障仍受控 Fatal |

## 14. 完成定义

只有同时满足以下条件，任务才可标记完成：

1. 普通 Provider、工具、审批、上下文和单 Run 收尾异常不会终止 Runtime 或 REPL。
2. Run A 故障时，同 Runtime 的 Run B 能继续输出并完成。
3. `CompleteFailedRunAsync` 和 `CompleteCancelledRunAsync` 不再直接触发 Runtime Fatal。
4. Timer/信号取消回调异常不会越过系统回调边界。
5. 旧项目的 CallId 索引、稳定重排、缺失结果降级和 orphan 丢弃行为已基于 Runtime 类型复用。
6. 历史图片等不兼容内容只从目标 Provider 投影移除，Canonical History 未改写。
7. 当前轮不兼容输入明确失败当前 Run，下一轮纯文本仍可继续。
8. Expert、Meeting、Work 和 Local 摘要的所有生产 Provider 调用都经过统一边界。
9. Runtime 默认不再限制一轮最多 8 个 tool call；显式宿主安全阀仍可测试。
10. Kimi 默认只暴露 128 个工具定义，`maxTools` 正整数、0、null 和负数语义全部有测试。
11. 非 Kimi Provider 不受 Kimi 128 默认值影响。
12. Provider 请求、工具参数、工具结果、图片内容和密钥没有写入新增日志。
13. 聚焦测试、全量测试、协议快照和 Native AOT 门禁通过。
14. 开发文档和执行步骤已按实际实现同步，没有把待评审设计写成已完成功能。
