# V1 Runtime 并发故障隔离与宿主任务状态闭环

> 文档状态：已按当前代码复核，待实施
>
> 前置文档：[总体方案](../README.md) · [架构修订 V1](../方案设计/02-架构修订-V1.md) · [架构评估与竞品参考](../方案设计/06-架构评估与竞品参考.md)
>
> Skills 加载与调用链路正在独立实施，不在本文重复安排。本文面向宿主管理多个 `serve` Runtime、每个 Runtime 并发执行多个 Run 的场景，处理 Run 故障隔离、错误/状态/进度回传、主动查询、断线对账和 Runtime 进程故障兜底。

收敛原则：

1. **复用现有链路**：扩展 `QueryRunAsync`、`ListRunsAsync`、`GetRuntimeStatusAsync`、`run.stage.changed` 和 Outbox，不另建一套查询协议或消息总线。
2. **推送和查询分工**：事件推送负责低延迟，主动查询负责当前真值，Outbox replay 负责补事件，重启后的查询负责最终对账。
3. **隔离业务故障与进程故障**：单个 Run 的普通托管异常应只终止该 Run；Runtime 已死亡时由进程外 Client 报告生命周期故障，宿主不得伪造 Run 终态。
4. **宿主负责聚合**：单个 Runtime 只报告自身实例和 Run；宿主继续使用现有 Client / Process 数组和配置标识组织多个进程，不向 Runtime 协议增加跨实例概念。
5. **不强制伪进度**：只有能计算总量的任务才报告百分比；模型等待、工具等待、审批等待等任务只报告阶段、当前步骤和更新时间。
6. **协议联动不可拆分**：公共 Contract 一旦修改，Runtime、Client、源生成、协议快照、兼容测试和开发文档必须按同一变更清单同步关闭。

已有测试也证明了部分隔离基础：取消一个并发 Run 不会取消另一个（`RuntimeControlTests.cs:197`），10 个流式 Run 不阻塞心跳和取消（`EventPressureTests.cs:17`），不同 Runtime 实例之间已有隔离测试。当前缺少的不是“能否并发”，而是 **Run A 遇到未预期 Provider / 工具异常后，Run B 是否仍能继续执行并持续上报进度**。

### A3. 已确认的真实故障缺口

| 优先级 | 位置 | 代码事实 | 实际后果 |
| --- | --- | --- | --- |
| P0 | `RunRegistry.RunLease`（`RunRegistry.cs:150,212`） | Timer 回调调用 `_cancellation.Cancel()`，只捕获 `ObjectDisposedException`；取消注册回调可抛 `AggregateException` | 已确认可让一个 Run 的超时回调终止整个 Runtime 进程 |
| P0 | `ExecuteRunAsync`（`RuntimeServer.cs:2510`） | catch-all 内再次等待数据库、Outbox 和事件发送；`ActiveRun.Attach` 只保存 Task，移出 `_activeRuns` 后没有独立观察者 | 失败收尾二次失败时 Run 可静默停在非终态，错误和进度都无法可靠回传 |
| P0 | 终态提交（`RuntimeServer.cs:3498,3559`） | `RunStatus.Failed` 转换与 `run.failed` Outbox 追加使用不同连接，正常终态路径也没有覆盖状态与事件的同一事务 | 查询可能已是终态但事件缺失，或事件与查询无法形成同一提交事实 |
| P0 | 进度与查询 | 没有跨 Expert、Meeting、Work 的统一持久化进度字段；`run.list` 依赖进程内活动字典 | 宿主断线、主动刷新或 Runtime 重启后不能恢复“所有任务当前做到哪里” |
| P1 | `RuntimeServer.RunAsync`（`RuntimeServer.cs:278`） | 多个常驻根任务用 `Task.WhenAll` 等待；一个任务 fault 后其他常驻任务仍可能继续运行 | Runtime 可能保持进程存活但控制、事件或租约子系统已半失效 |
| P1 | `FramedControlChannel`（`FramedControlChannel.cs:264-430`） | 请求/Blob 后台 Task 对非白名单异常没有统一响应和观察 | 普通 Task fault 通常不会杀进程，但对端可能无响应且错误丢失 |
| P1 | `RuntimeClient.HeartbeatLoopAsync`（`RuntimeClient.cs:1347`） | 非白名单异常会 fault `_heartbeatTask`，只在 Dispose 时观察 | Client 可能仍显示 `Connected`，宿主不知道心跳已经停止 |
| P1 | owned Runtime 生命周期 | `RuntimeClient` 没有持续 `WaitForExitAsync` 监控；`IRuntimeClient` 未公开 `State` 或可等待的生命周期完成信号 | Runtime 空闲时死亡，宿主可能直到下一次调用才发现 |
| P1 | 多 Runtime 宿主视图 | SampleHost 已用 `RuntimeProcess[]` 和 `RuntimeClient?[]` 管理两个实例（`MultiInstanceHost.cs:27-32`），但没有展示并发查询和独立事件消费的完整流程 | 宿主不知道如何基于现有数组获得全部当前任务，容易各自实现出不同语义 |

### A4. 评审边界修正

- 普通未观察 `Task` 异常在当前 .NET 默认策略下通常不会直接终止进程，但会造成半失效、无响应或状态丢失，仍必须被观察。
- 当前最明确、已可复现的“一个回调带崩整个进程”路径是 `RunLease` Timer 调用 `CancellationTokenSource.Cancel()` 时让取消回调异常越过 Timer 边界。`StackOverflowException`、`Environment.FailFast`、严重 OOM、原生故障和系统强杀无法靠同进程 catch-all 绝对隔离。
- `serve` 在宿主管理环境中不依赖 Ctrl+C。Ctrl+C / SIGTERM 风险只属于手工独立启动或外部信号场景，降为次要补充项，不进入多并发主线。
- 进程死亡不等于某个 Run 业务失败。死亡后宿主先标记“等待恢复确认”，重启后以持久化查询结果确定 `Interrupted` 或已提交终态。

## B. 最小实施方案

### B0. P0：同 Runtime 内的 Run 故障隔离

#### B0.1 封住已确认的进程级崩溃路径

- `RunLease.CancelForTimeout` 必须是 no-throw 边界。调用 `CancellationTokenSource.Cancel()` 时处理取消注册回调抛出的聚合异常，记录脱敏诊断，但不得让异常离开 Timer 回调。
- 保留 `Cancel()` 默认执行全部取消回调的行为，不改成遇到首个异常立即停止。Timer 只负责触发取消；Run 的 `RunTimedOut` 终态仍由 `ExecuteRunAsync` 正常收尾。
- 只增加局部可复用的安全取消方法，不引入全局异常总线。

#### B0.2 让 Run 失败收尾成为一个可靠提交

- 只要求 `Completed`、`Failed`、`Cancelled` 等业务终态和对应终态 Outbox 事件在同一 SQLite 事务中提交。失败事件继续复用现有 `RuntimeError`，查询返回脱敏后的同一错误事实，不能只留下 `TerminalText`。
- 普通阶段/步骤进度先写数据库，再追加 `run.stage.changed`；事件发送失败由主动查询补偿，不把每次进度都升级为跨模块事务。
- 现有 `SqliteEventOutbox.AppendAsync` 会自行开启事务，终态写入不能简单套在仓储外层事务里。只为终态增加一个可接收调用方事务的 SQLite 内部写入方法，不引入通用 Unit of Work 或事件提交框架。
- `ExecuteRunAsync` 的 catch-all 继续承担 Run 级隔离：Provider、工具、模式编排器的普通未预期异常只结束当前 Run，不触发整个 Runtime 关停。
- 对失败收尾增加第二层观察。如果数据库或 Outbox 已无法完成终态提交，不能静默吞掉，也不能继续把 Runtime 报为健康；应把该故障提升到 Runtime 根生命周期，由 P1 的受控退出和重启对账处理。
- `ActiveRun.Attach` 保存的执行 Task 在移出 `_activeRuns` 后也必须有明确观察者。观察者只传播无法可靠收尾的基础设施故障，不把普通 Run 失败升级为进程故障。

#### B0.3 补上真正缺失的并发隔离证明

- Run A 的 Provider、工具和取消回调分别注入未预期异常时，Run B 必须继续推进、发送进度并正常完成。
- Run A 能可靠收尾时，查询和事件都必须得到同一个 `Failed` / `Cancelled` / `RunTimedOut` 事实；只有终态提交本身失败时才允许 Runtime 受控退出。
- Run A 完成或失败释放容量时，不得误释放 Run B 的 Provider、Session 或全局容量租约。

### B1. P0：最小进度字段、实时事件和主动查询

#### B1.1 直接扩展现有 Contract，不新增快照类型

本轮不增加 `RunProgressSnapshot`，也不增加独立 `Revision`。现有 `RuntimeEventEnvelope` 已有 GSN 和 RunSequence：GSN 用于事件 ACK / replay，RunSequence 用于单个 Run 内的事件顺序。注意 `runs.run_sequence` 当前表示 Session 内 Run 的创建顺序，不得改成进度版本；查询中的 `LastRunSequence` 需要单独持久化。

三个 positional record 的现有主构造函数保持不变；新增字段写成 record body 内带默认值的可选 `init` 属性。这样旧 JSON 缺失字段时保持当前行为，也避免因为修改构造函数签名破坏已编译 Client 的二进制调用。

| 现有 Contract | 追加的可选 `init` 属性 | 不增加的内容 |
| --- | --- | --- |
| `RunQueryResult` | `Mode`、`Phase`、`CurrentStep`、`CompletedUnits`、`TotalUnits`、`UpdatedAt`、`LastRunSequence`、`Error` | 不删除 RunId、SessionId、Status、TerminalText |
| `RunListItem` | `Mode`、`Phase`、`CurrentStep`、`CompletedUnits`、`TotalUnits`、`UpdatedAt`、`LastRunSequence` | 不嵌套新的 Snapshot DTO |
| `RunStatusChangedEvent` | `Mode`、`Phase`、`CurrentStep`、`CompletedUnits`、`TotalUnits`、`UpdatedAt` | 不复制 GSN、RunSequence；它们继续来自 Envelope |

`Phase` 是稳定、机器可读的粗粒度字符串，`CurrentStep` 是可显示摘要。`CompletedUnits` / `TotalUnits` 只有可计算时才填写，宿主自行计算百分比。终态错误继续复用脱敏 `RuntimeError`，不在进度事件中复制完整 Provider 响应。

持久化只在现有 `runs` 表增加完成查询所需的最少列；Mode 从现有 Session 读取，UpdatedAt 复用现有列，Work / Meeting 的详细状态继续保留在各自表中。不增加新的进度表、快照仓储或状态机。

#### B1.2 复用现有模式数据

- Expert：把现有 invocation 和 `run.stage.changed` 投影为 Phase、CurrentStep 和更新时间。
- Work：复用已持久化步骤计算 CurrentStep 及 CompletedUnits / TotalUnits，不复制 WorkPlan、尝试记录或 checkpoint。
- Meeting：复用已持久化轮次、参与者和等待审批状态，并补发与 Expert / Work 一致的 `run.stage.changed`。
- 只在阶段、步骤、轮次、等待原因或终态发生变化时更新；文本 Delta 继续走现有流式事件，不持久化成进度。
- 普通进度先写 `runs` 中的查询字段，再追加事件。事件失败时查询仍是当前真值；终态则按 B0.2 使用原子提交。

#### B1.3 只修现有查询缺口

- `QueryRunAsync` 继续按 RunId 查询，返回追加的进度和结构化错误字段。
- `ListRunsAsync` 改为从数据库读取全部当前非终态 Run，不再以 `_activeRuns` 为唯一来源；保留现有可选 SessionId 过滤。
- 本轮不增加状态过滤、分页、批量 RunId 或历史列表。当前任务受 Runtime 并发容量约束；崩溃后宿主对已记录的 RunId 逐个调用 `QueryRunAsync`。
- `GetRuntimeStatusAsync` 保持现有单 Runtime 身份和计数语义，不增加跨 Runtime 查询方法。

#### B1.4 推送、重放和查询的最小对账规则

- 宿主继续按 Runtime InstanceId 校验事件世代，按 GSN ACK / replay，并按 Envelope.RunSequence 防止单个 Run 的旧事件覆盖新进度；不增加 Revision。
- 主动查询结果直接覆盖该 Run 的当前显示值，并把 LastRunSequence 作为后续事件下限；之后只应用更大 RunSequence 的事件，避免延迟事件回写旧进度。
- `ReplayPendingEventsAsync` 使用 `event_outbox.created_at` 中已有的原事件时间，不能用重放时的 `UtcNow` 冒充进度发生时间。这里只映射现有列，不新增审计系统。
- 事件消费恢复后执行一次 `ListRunsAsync`，并对宿主已记录但列表中不存在的未确认 Run 调用 `QueryRunAsync`。事件负责低延迟，查询负责最终真值。
- `MarkInterruptedAsync` 当前不会生成新的 Outbox 终态事件，因此 Runtime 重启后必须主动查询，不能等待一条可能不存在的 `Interrupted` 事件。

### B2. P1：宿主直接使用现有数组汇总

- 不在 Client SDK 增加 Fleet、聚合器、RuntimeKey 或中央缓存类型。单个 `IRuntimeClient` 仍只负责一个 Runtime。
- 宿主继续使用现有 `RuntimeProcess[]` / `RuntimeClient?[]`；数组索引或宿主已有配置 ID 负责稳定标识，不进入 Runtime 线协议。
- 每个 Client 独立运行 `ReadEventsAsync` 消费循环。宿主主动刷新时，对现有 Client 并发调用 `GetRuntimeStatusAsync` 和 `ListRunsAsync(new RunListParameters())`。
- 每个并发查询在自身边界捕获连接错误并返回该实例的失败结果，再统一等待全部查询；一个 Runtime 超时或退出不得丢掉其他 Runtime 已成功返回的状态。
- Runtime 暂时失联时，宿主保留该数组槽位的最后显示值并标记“等待确认”，不得把其中全部 Run 改为 `Failed`。重连或重启后再以查询结果覆盖。
- SampleHost 只补充上述调用示例和端到端测试，不把示例提升为新的公共调度框架。

### B3. P1：Runtime 半失效与进程退出兜底

#### B3.1 常驻根任务受控 fail-stop

- `RuntimeServer.RunAsync` 必须在控制监听、事件监听、租约监控等关键根任务意外 fault 时立即观察故障，取消其余根任务、清理连接，并让 `serve` 以非零退出码结束。关键子系统已经死亡时，不允许进程继续伪装健康。
- `FramedControlChannel` 的 JSON-RPC handler 对非取消异常返回脱敏 `-32603`；Blob handler 无法形成合法错误帧时明确终止通道。所有请求和清理 Task 都必须被观察。
- Run 执行 Task 如果连终态都无法持久化，只通过一个 Runtime 内部 fatal `TaskCompletionSource` 通知根任务退出；不增加公共异常总线。
- 这里只增加 Runtime 根生命周期门闩，不自动重启各循环，也不引入通用监督树。

#### B3.2 Client 向宿主暴露统一生命周期事实

- owned Runtime 连接成功后，用 `Process.WaitForExitAsync` 持续监听退出，不增加轮询线程。
- `IRuntimeClient` 只新增 `RuntimeClientState State { get; }` 和 `Task Completion { get; }`。正常 Dispose 时 Completion 正常完成；确认 owned process 异常退出时 Completion fault，State 为 `Faulted`。
- 只新增一个 `RuntimeProcessExitedException`，直接携带 InstanceId、PID、ExitCode、退出时间和最后确认 GSN，不再增加 CompletionResult、Reason 枚举或生命周期快照 DTO。
- RPC、`ReadEventsAsync` 和 `Completion` 在已确认 owned process 退出时复用同一个退出异常事实；调用者主动取消仍返回 `OperationCanceledException`。
- `_heartbeatTask` 的不可恢复异常必须立即被观察，使 Client 进入 `Faulted`，并让 Completion 以现有 `RuntimeClientConnectionException` 结束，不能等到 Dispose。
- 心跳或 attach 模式的连接故障继续使用现有 `RuntimeClientConnectionException`；没有可靠进程句柄时不得伪造 ExitCode 或断言目标进程已死亡。

#### B3.3 进程死亡后的对账

- 收到生命周期故障后，宿主把该 Runtime 的非终态 Run 标为“等待恢复确认”，同时继续展示其他 Runtime 的实时状态。
- 新 Runtime 使用同一 DataDirectory 启动后，保留崩溃前已提交的终态，将遗留执行态转为 `Interrupted`，并按现有规则保留 `WaitingForApproval`。
- 新 Client 连接后，宿主先恢复事件游标，再主动查询故障前记录的 RunId 和当前非终态列表。只有查询结果可以确定最终业务状态。
- `StackOverflowException`、`FailFast`、原生崩溃、严重 OOM 和系统强杀无法在共享进程内绝对隔离；在不引入 PerRun Worker 的前提下，进程外监控、重启和查询对账就是兜底边界。

### B4. 次要场景：独立 CLI 的 Ctrl+C / SIGTERM

手工运行 `serve` 或 REPL 时，Console / POSIX 信号回调同样应使用 no-throw 安全取消，避免取消回调异常越过系统回调边界。该修复可以复用 B0.1 的局部辅助方法，但不作为宿主管理、多并发 `serve` 场景的 P0 验收主线。

### B5. 协议、Client 和开发文档联动门禁

本方案会修改公共 JSON Contract、Client SDK 和数据库 Schema，不能只修改 RuntimeServer。实施前必须复制并填写[协议变更清单模板](../执行步骤/协议变更清单模板.md)，同一批次逐项完成以下联动；任一必需项未完成时，不得把本任务标记为完成。

## C. 验收矩阵

### C0. 并发 Run 故障隔离

1. 同一 Runtime 同时启动 Run A 和 Run B；Run A 的 Provider 抛出未预期异常，Run B 继续收到阶段/进度事件并完成。Run A 的查询和 `run.failed` 事件包含相同状态、错误码和 DiagnosticId，查询中的 LastRunSequence 等于终态事件 Envelope 的 RunSequence。
2. 将 Run A 改为工具调用异常、超时和调用者取消，重复上述断言；Run B 的取消令牌、容量租约和状态不得变化。
3. 在独立子进程中让 Run A 的取消注册回调抛异常，再触发 Timer 超时；断言 Runtime 进程仍存活、Run B 仍可执行、Run A 最终为 `RunTimedOut`。这条测试必须真实经过 Timer 回调，不能只直接调用辅助方法。
4. 分别在终态事务开始前和提交前注入持久化失败；断言执行 Task 不会静默 fault。成功提交时终态、错误和 Outbox 同时可见；无法提交时 Runtime 受控退出，重启后查询返回 `Interrupted` 或已提交的真实终态。

### C1. 三种模式的实时进度与主动查询

| 场景 | 推送断言 | 查询断言 |
| --- | --- | --- |
| Expert 正在请求模型 / 工具 | 收到相应 `run.stage.changed`，Envelope.RunSequence 单调递增 | `QueryRunAsync` 返回相同或更新的 Status、Phase、CurrentStep |
| Work 执行多个步骤 | 步骤开始、完成、失败或重试时收到更新 | CompletedUnits / TotalUnits 与持久化步骤一致，不因重连归零 |
| Meeting 执行轮次并等待审批 | 轮次和等待审批均收到统一进度事件 | 主动查询返回当前轮次 / 参与者摘要和等待状态 |
| 无法计算总量的任务 | CompletedUnits / TotalUnits 至少一个为空 | 宿主不显示虚假百分比，只显示阶段和更新时间 |
| Run 执行 Task 已离开 `_activeRuns` 但数据库仍非终态 | 不要求伪造事件 | `ListRunsAsync` 仍能列出该异常记录，不能从总览消失 |

另需验证：

- `ListRunsAsync` 不传 SessionId 时返回数据库中的全部当前非终态 Run，传 SessionId 时只返回该 Session；执行 Task 离开 `_activeRuns` 后记录不能消失。
- 同一进度经事件和查询到达两次时，宿主按 RunSequence 防止旧事件覆盖查询到的新状态；事件重复投递必须幂等。
- 终态 `Failed` 查询必须包含脱敏结构化错误，不能要求宿主依赖恰好收到 `run.failed` 才看到错误原因。

### C2. 断线、重放与查询对账

1. 宿主收到 RunSequence N 后断开事件通道；Runtime 继续产生 N+1、N+2 进度并写入 Outbox。
2. 重连后从最后确认 GSN 重放，事件保持原发生时间和原顺序；重复投递不会重复推进宿主状态。
3. 重放结束后主动查询，查询 LastRunSequence 不小于最后收到的 RunSequence，字段与数据库一致。
4. 模拟事件已提交但尚未发送、已发送但尚未 ACK、已 ACK 后再次重连三种窗口，分别验证不丢最终状态且重复可幂等处理。

### C3. 多 Runtime 宿主总览

1. 启动两个 Runtime，每个 Runtime 同时运行多个 Run；宿主使用现有 Client 数组并发查询后能看到全部 Runtime 及其全部当前 Run，数组槽位互不混淆，事件仍校验当前 InstanceId。
2. Runtime A 的一个 Run 失败时，Runtime A 的其他 Run 和 Runtime B 的全部 Run 继续实时更新。
3. Runtime A 事件通道断开时，Runtime B 的事件消费和主动查询不受阻塞；A 保留最后快照并显示为 Stale / 等待确认。
4. 主动刷新时各 Runtime 的查询并发完成；单个 Runtime 超时只记录对应数组槽位错误，仍保留其余实例的成功结果。

### C4. Runtime 半失效和异常退出

- 注入一个立即 fault 的 Runtime 根任务和一个只响应取消的兄弟任务；兄弟任务被取消，`RunAsync` 在限定时间内结束，`serve` 返回非零，不能继续保持半失效进程。
- JSON-RPC handler 抛非白名单异常时，对端在限定时间内收到 `-32603`；Blob handler 同类异常让请求以明确通道错误结束。
- 心跳循环抛非白名单异常时，Client 立即进入 `Faulted`，`Completion` 结束，宿主不需要等到下一次业务调用。
- owned Runtime 在空闲、RPC 挂起和事件读取中三种时机被终止后，`Completion`、RPC 和事件流得到属性一致的 `RuntimeProcessExitedException`；不得永久等待或只暴露无上下文 `IOException`。
- 正常 Dispose / 主动关闭得到 `Closed`，不得误报异常退出；attach 模式无进程句柄时 ExitCode 为空。

### C5. 重启后的最终对账

- 崩溃前仍为 `Running` 等执行态的 Run，重启后主动查询为 `Interrupted`；宿主此前的“等待确认”被替换。
- 崩溃前已原子提交的 `Completed` / `Failed` / `Cancelled` 保持原终态，不得被覆盖为 `Interrupted`。
- `WaitingForApproval` 按现有恢复规则保留；进程退出本身不新增伪造的 `run.failed`。
- Outbox replay 补发未确认事件后，主动查询仍是最终裁决；延迟到达的旧事件不得覆盖更大的 LastRunSequence。
- 同一数组槽位的 Runtime 重启且 InstanceId 改变后，宿主用故障前记录的 RunId 查询并替换“等待确认”状态，不得因 InstanceId 改变重复显示同一 Run。

### C6. 协议与文档联动

- 新增字段缺失时，新 Client 能读取旧 Runtime 响应；旧 Client 能忽略新 Runtime 响应和事件中的可选字段。
- `RuntimeJsonContext` 源生成、协议快照、Fake Host / Fake Runtime 兼容用例全部通过，且快照差异只包含本方案列出的可选字段。
- 数据库 Schema 版本已提升，旧数据目录升级后能够查询现有 Run；迁移失败时不会留下半升级 Schema。
- `IRuntimeClient.State`、`Completion` 和异常语义已同步到宿主集成指南；错误恢复步骤已同步到自动化与故障排查文档。
- 若 CLI JSON 输出发生变化，命令矩阵和机器快照同步通过；若未变化，协议变更记录明确说明没有 CLI 输出影响。

## E. 本轮明确排除的过度设计

以下事项不是永远不做，而是不属于“并发 Run 隔离 + 状态/进度闭环 + 进程故障兜底”的最小实现。

### E1. 自动重启和监督树

Client 本轮只报告退出并解除挂起操作，不自动拉起新 Runtime。是否重启、退避和熔断由宿主产品策略决定；Runtime 内只做关键根任务 fail-stop，不建设通用监督树。

### E2. PerRun / PerSession Worker

独立 Worker 能缩小故障域，但会引入跨进程工具调用、审批、事件归并、Provider 连接和资源回收协议。它属于 V2 架构选择，不是本轮状态回传的前置条件。

### E3. 强制百分比和 token 级进度持久化

不可计算的 AI 任务不伪造百分比；文本 Delta 继续走现有流式事件，不把每个 token 写进 `runs` 进度字段。公共进度只覆盖宿主可操作的阶段、步骤、轮次、等待和终态。

### E4. Fleet 聚合框架、RuntimeKey 或全局查询服务

宿主直接组合现有 `IRuntimeClient[]`。不增加 FleetMonitor、RuntimeKey 公共模型、中央注册中心、跨进程广播或新的网络服务；单个 Runtime 不查询其他 Runtime。

### E5. 新快照 DTO、独立 Revision 或平行状态机

不增加 `RunProgressSnapshot`、独立 Revision、进度表或完整事件溯源。现有 DTO 的可选字段和 `runs` 当前值负责查询，Outbox 负责投递；不复制 Work / Meeting 完整状态，也不新增持久化 `OutcomeUnknown`。恢复前的“等待确认”只属于宿主瞬时状态。

### E6. 依赖进程内全局异常钩子完成回传

可以另行增加崩溃前的尽力日志，但不得等待它写业务状态或 IPC 消息。真正的进程死亡确认必须来自进程外的 Client / 宿主。

### E7. 宿主伪造 `run.failed` 或直接修改 Runtime 数据库

进程可能在终态提交后、事件送达前退出。宿主若直接写 `Failed` 会覆盖真实的 `Completed`，破坏单一写入者和 Outbox 一致性。宿主只能记录 Client 生命周期故障，并在 Runtime 重启后通过公开查询接口对账。

### E8. 与本闭环无关的功能捆绑

Skills、LocalRuntime 调度器重构、Provider RPM/TPM、完整 Unix TOCTOU、安装器和 PATH 管理均不进入本轮实施范围。Work 进度只读取现有持久化步骤，不借本任务修改 Work 的业务调度策略。
