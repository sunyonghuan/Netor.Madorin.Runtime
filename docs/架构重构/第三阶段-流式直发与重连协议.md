# 第三阶段：流式直发与宿主重连协议

## 目标

1. 修复第一阶段遗留的回归：Delta 退出 Outbox 后必须仍能实时到达宿主。
2. 消除第二个结构性根因：`Cache=Shared` 让 WAL 失效、把写冲突变成不可等待的表锁。
3. 固化重连协议：Outbox 只回放关键事件；历史内容由宿主按需从 JSONL 拉取；Delta 不回放。

---

## 代码推演发现的问题

### 问题 1：第一阶段后 Delta 根本没有送达宿主

`RuntimeServer` 的 Run 循环不直接发送 orchestrator 产出的 envelope，而是每收到一条就调用
`DispatchPendingEventsAsync`，从 `event_outbox` 读取 pending 行再发给宿主：

```
orchestrator.RunAsync ──yield envelope──► RuntimeServer 循环
                                              └─ DispatchPendingEventsAsync ─► LoadPendingAsync(DB) ─► 事件通道
```

第一阶段把 Delta 从 Outbox 移除后，这条链路对 Delta 完全失效：envelope 被丢弃，宿主再也收不到
`output.delta` / `reasoning.delta`。此外客户端 SDK 两处按 GSN 过滤的逻辑也会丢弃 GSN=0 的事件：

- `FramedEventChannel.ReadAllAsync`：`if (envelope.Gsn > eventReplayCursor)`
- `RuntimeClient.ReadEventsAsync`：`if (envelope.Gsn <= _lastConfirmedGsn) continue;`

宿主 `EventConsumeLoop` 的去重器以 `(instanceId, gsn)` 为键，第二条 GSN=0 起全部判为重复。

新增端到端测试 `StreamingDeltaDeliveryTests` 在修复前的结果：**期望 25 条 Delta，实际 0 条**。

### 问题 2：`Cache=Shared` 是锁错误的直接机制

`DataDirectoryInitializer` 与 `ConversationStore.OpenIndexConnectionAsync` 都以
`SqliteCacheMode.Shared` 打开 `state.db`，而整个进程通过 `OpenDatabaseConnectionAsync` 开了 20+ 个连接。

| 模式 | 锁粒度 | 冲突返回 | `busy_timeout` 是否生效 |
|------|--------|----------|--------------------------|
| Shared cache | 表级锁（进程内共享页缓存） | `SQLITE_LOCKED_SHAREDCACHE` | 否，只能靠驱动层自旋重试到 `DefaultTimeout` |
| Private cache + WAL | 文件级，读写互不阻塞 | `SQLITE_BUSY`（仅写-写） | 是，SQLite 内部休眠等待 |

SQLite 官方把 shared-cache 列为不推荐的历史特性，推荐用 WAL 替代；本仓库 WAL 早已开启，
只是被 Shared cache 抵消了。`DatabaseMaintenanceService`、`StorageMaintenanceService` 已经使用 Private，
生产连接却仍是 Shared，属于初始提交遗留（`git log -S` 可查）。

### 结论：重连协议无需新接口

- 服务端已有 `session.history.read`（按 sequence 分页）与 `session.history.rounds.read`（按轮次）RPC，
  都直接读 JSONL，宿主"最近 N 条/N 轮"可以直接调用，不需要新增 `ReadRecentAsync`。
- `ReplayPendingEventsAsync` 只回放 `event_outbox` 中未确认的行；Delta 不在表里，天然不回放。

## 流式事件协议语义（宿主实现约定）

| 维度 | 关键事件（GSN > 0） | 流式事件（GSN = 0） |
|------|---------------------|---------------------|
| 持久化 | `event_outbox` + `.evt` 镜像 | 无 |
| 去重 | 按 `(instanceId, gsn)` | 不去重（`RunSequence` 仍单调，可用于同 Run 内排序） |
| ACK | 必须，推进 `lastConfirmedGsn` | 禁止 ACK，禁止写入游标 |
| 断连 | 重连后由 Outbox 回放 | 丢弃；最终消息从 `session.history.*` 读取 |
| 队列满 | 分离通道，等待重连回放 | 丢弃该条 |
| 类型 | `run.*`、`invocation.*`、`tool.call.completed`、`expert.plan.*`、`credentials.*` 等 | `output.delta`、`reasoning.delta` |

宿主重连流程：

1. `initialize(lastConfirmedGsn)` → Runtime 回放 Outbox 中 GSN 更大的关键事件（数量级：每 Run 5–10 条）。
2. 宿主清空当前会话界面，调用 `session.history.rounds.read`（或 `session.history.read`）取最近 N 轮/N 条。
3. 继续消费实时流；进行中的 Run 其 Delta 从当前位置开始渲染，`invocation.completed` / `run.completed`
   触发宿主用历史记录中的最终消息替换流式缓冲。
