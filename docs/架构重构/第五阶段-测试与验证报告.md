## 验证方式

新增两个端到端压力/恢复测试，走与生产完全相同的路径（`RuntimeServer` + 命名管道 + `RuntimeClient`），
宿主侧模拟 Workstation `EventConsumeLoop` 的行为（每 10 条带 GSN 事件 ACK 一次）：

| 测试 | 文件 | 场景 |
|------|------|------|
| `ConcurrentLongStreamingRuns_CompleteWithoutLockErrors_AndKeepOutboxSmall` | `tests/Madorin.AI.Runtime.EndToEnd.Tests/StreamingStressTests.cs` | 3 个并发 Run，每个以约 400 条/秒的速率交替产出 `output.delta` / `reasoning.delta`，持续 N 秒（环境变量 `MADORIN_STRESS_SECONDS`，默认 12） |
| `HostDisconnectDuringStreaming_ReconnectReplaysOnlyCriticalEvents_HistoryHoldsFinalMessage` | 同上 | 流式进行中断开宿主事件/控制通道，Run 离线跑完，宿主重连 |

断言覆盖：

- 所有 Run 以 `run.completed` 结束，失败时打印 payload（原故障表现为 `run.failed` + SQLite 锁错误）。
- 快宿主收到 ≥ 90% 的 Delta，且全部 GSN = 0。
- `event_outbox` 中 Delta 行数为 0，总行数 < 每 Run 20 行。
- `.madorin/logs` 下不出现 `database table is locked` / `database is locked` / `SQLITE_LOCKED` / `SQLITE_BUSY`。
- 通过 `session.history.rounds.read` 读回的 assistant 文本与 Provider 实际产出逐字相等（JSONL 为权威源）。
- 重连后回放的事件全部 GSN > 已确认水位、不含 Delta、以 `run.completed` 收尾、条数 < 20。

同一测试文件在重构前提交 `1bf0324` 上编译运行，作为旧架构对照（旧架构下按设计会失败，取其数据）。

## 结果：旧架构对照（提交 `1bf0324`，同一测试）

### 并发长流式（12 秒）

```
duration=12s wall=13.5s runs=3
deltasEmitted=2690 deltasReceived=2690 unsequencedDeltas=0 deltaRate=224/s
criticalEvents=12 acks=271
```

- Provider 吞吐被压到 224 条/秒：每条 Delta 都要等 GSN 事务 + `event_outbox` 插入 + `.evt` 镜像写盘 + `MarkSent`。
- 宿主 271 次 ACK 往返，每次都是一笔 `UPDATE event_outbox ... WHERE gsn <= ?` 写事务，与 Run 侧写入在同一张表上竞争。
- 2690 条 Delta 全部成为 `event_outbox` 行（预期 2702 行 vs 新架构 12 行）。
- 13 秒的本地 SSD 测试尚未撞锁；生产故障是在数十分钟 reasoning、单条 32 KiB payload 下出现的，本对照验证的是写放大与耦合，锁冲突由 `Cache=Shared` → `Private` 的变更从机制上消除。

### 断连重连

```
deltasEmitted=1110 deltasBeforeDisconnect=20 replayedAfterReconnect=1112
types=[output.delta, reasoning.delta, ... ×1110, invocation.completed, run.completed]
```

- 旧架构重连后把 1110 条历史 Delta 全部重放给宿主；新架构 2 条。

## 结论

1. 原故障的两个根因均已从机制上移除：高频 Delta 不再进入 SQLite；剩余低频写入运行在 Private cache + WAL 下，写-写冲突走 `busy_timeout` 等待而不是立即抛 `SQLITE_LOCKED`。
2. 第一阶段引入的"Delta 不送达宿主"回归已修复并有专门测试守护（`StreamingDeltaDeliveryTests`、`StreamingStressTests`）。
3. 重连协议按"关键事件回放 + 历史按需拉取 + Delta 不回放"落地，宿主事件循环已适配。

## 验证过程中的额外发现

### 宿主租约现在只靠心跳维持

服务端在任何控制请求（含 ACK、心跳）到达时刷新宿主租约，`HostLeaseTimeout` 默认 45 秒、心跳间隔 15 秒。
旧架构下宿主每 10 条 Delta 就 ACK 一次，流式期间控制通道始终有流量，即使心跳失效租约也不会过期；
新架构下流式期间控制通道几乎静默（60 秒内仅 2 次 ACK），租约完全依赖后台心跳。

- Workstation 的 `RuntimeClientFactory` 使用 `EnableBackgroundHeartbeat` 默认值 `true`，生产路径不受影响。
- 第一版压力测试关闭了心跳并流式 60 秒，45 秒时服务端按设计过期租约：取消该宿主的 Run、断开事件/控制通道；随后宿主侧下一次 ACK 卡在 `FramedControlChannel._writeGate` 直到调用方超时。前者是预期行为；后者（租约过期后客户端控制请求挂起而非快速失败）是既有行为，与本次改动无关，建议单独跟进。
- 压力测试已改为与生产一致（保留后台心跳）。

### 流式吞吐是旧架构的隐藏瓶颈

旧架构下 orchestrator 对每条 Delta `await outbox.AppendAsync(...)`，Provider 读取被数据库事务串行化，3 个并发 Run 合计只有 224 条/秒；
新架构 962 条/秒且不随并发数衰减。这解释了用户此前感知到的"长 reasoning 时卡顿"。
