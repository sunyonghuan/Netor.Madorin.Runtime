## 2. 验收依据与固定数据

依据用户本次要求，以及旧项目 [工作模式方案](../../../Netor.Madorin/Docs/工作模式/策划/工作模式方案策划/README.md)、[会议模式方案](../../../Netor.Madorin/Docs/会议模式/策划/会议模式方案策划/README.md)。核心标准是：工作先讨论、形成计划、用户确认、执行全部步骤、总结；中途可补充需求并修订计划；会议由主持人组织讨论，总结并征询老板，老板同意后才正式结束。

每个场景采用独立工作区，初始数据一致：

```csv
# sales.csv
orderId,market,amount
A001,CN,1200
A002,US,800

# refunds.csv
refundId,amount
R001,150
```

预期：订单 2 笔，销售 2000 元，退款 150 元，净额 1850 元；增加退款 100 元后，退款 250 元，净额 1750 元。退款文件不含市场或订单关联字段，不能据此断言 US 无退款。

## 4. 工作模式

完整记录：[讨论后确认的独立复测](../../artifacts/real-smoke-20260915/work-confirm/transcript.md)、[初始讨论及版本冲突证据](../../artifacts/real-smoke-20260915/work/transcript.md)、[已确认三步任务](../../artifacts/real-smoke-20260915/work-execute/transcript.md)、[中断与自然重规划](../../artifacts/real-smoke-20260915/work-interrupt/transcript.md)、[显式新版计划](../../artifacts/real-smoke-20260915/work-revision-valid/transcript.md)。

### 4.1 讨论阶段错误启动执行

输入：“目前只讨论，未批准计划；禁止调用写入工具或开始执行步骤。”

总经理正常回答讨论内容后，Runtime 把非 JSON 回答转换成单步回退计划，发出 `work.plan.updated`，并启动 `worker`，最终将 Run 标为完成。该轮没有写文件，但**已经越过计划确认边界，启动了执行步骤**，不符合预期。

原因：[WorkModeOrchestrator.cs](../../src/Madorin.AI.Runtime.Modes.Work/WorkModeOrchestrator.cs#L262) 对无法解析的回答无条件生成可执行回退计划，保存后立即调度，没有“继续讨论/等待计划确认”的分支。

### 4.2 多轮修改与自然确认不能稳定衔接

第二轮输入：“增加按市场拆分，并把退款率放进去。先给我修订后的步骤，等待我明确批准。现在不要执行。”

一次实测正常输出修订建议后 `run.failed`。服务端日志明确为：

```text
Work plan revision '1' is already published for session '0ce33bce16e749758e75f94bf6d46a0f'.
```

中断后的 W6、W7 也重复出现该冲突。失败后还出现 `LatestRun.Status=Failed`、`WorkState.Status=Planning` 的不一致状态，不能据工作状态判断还在正常规划。

独立 WC1→WC2 复测使用最短两轮：第一轮只讨论、禁止工具；第二轮明确“确认执行”。WC1 仍自动产生回退执行步骤，WC2 输出合法 JSON 计划后 `run.failed`，未生成 work-confirmed.md。这排除了“用户尚未确认”的解释，也没有依赖超时或取消竞争。

### 4.3 已经确认的三步任务可以完成，但步骤仍串行

输入明确批准三步：s1 读取销售并写 work-sales.md；s2 读取退款并写 work-refunds.md；s3 依赖前两步，读取产物、核算并写 work-final.md，再读回总结。设置 `MaxConcurrentSteps=2`，s1/s2 无依赖，并明确要求并发。

实际：15 次工具执行均成功，三个步骤全部 `Completed`，最终输出销售 2000、退款 150、净额 1850，并真实生成 [work-final.md](../../artifacts/real-smoke-20260915/work-execute/workspace/work-final.md)。**步骤执行、依赖和验收通过；并发不通过。**

s1 执行区间为 00:17:31.104–00:17:38.751 UTC；s2 为 00:17:38.752–00:17:45.327，互不重叠。源码也明确使用顺序循环：[WorkModeOrchestrator.cs](../../src/Madorin.AI.Runtime.Modes.Work/WorkModeOrchestrator.cs#L391)。最终总结由验收员工 reviewer 产出。

### 4.4 中断后重新讨论、重规划

按三步串行计划运行，在第一步完成事件后调用公开 `CancelRunAsync`：Run 变为 `Cancelled`，工作会话为 `Interrupted`；第一步文件保留，第二步中断，第三步待执行。这是当前 SDK 的取消路径，**不是已经实现了独立暂停协议**。

随后输入：“退款额还要增加100元，最终文件改为interrupt-revised.md。先讨论修订计划，保留第一步成果，不要重做、不要执行，等待确认。”总经理正确理解到退款 250、净额 1750，但整轮仍因重复版本 1 失败。再输入“确认新计划，继续执行剩余步骤”也失败，最终新文件不存在。

补充的协议级对照测试：明确提供 `planVersion="2"`、`previousPlanVersion="1"`，仅列出剩余写入和核验步骤后，**成功生成新文件并完成版本 2**。第一步文件哈希保持不变。这说明持久化层支持修订，现有自然对话编排没有自动完成正确的版本衔接。只指定版本 2、漏掉 PreviousPlanVersion 的对照请求会被校验器正确拒绝，未把该拒绝计为产品缺陷。

真实产物：[interrupt-revised.md](../../artifacts/real-smoke-20260915/work-revision-valid/workspace/interrupt-revised.md)。用户不应需要手工维护这些协议字段，才能完成“讨论后继续执行”的正常流程。

版本 2 对照用例共出现 13 次工具执行，其中一次对不存在的新文件使用 overwrite 被拒绝（`The overwrite target was not found.`），模型随后修正并完成写入。该用例属于“发生可恢复工具错误后成功”，不是所有工具调用一次成功。

## 5. 会议模式

完整记录：[明确调度格式的完整会议](../../artifacts/real-smoke-20260915/meeting-controlled/transcript.md)、[首个四轮成功会议](../../artifacts/real-smoke-20260915/meeting-strict/transcript.md)、[ACK 修正版 pro](../../artifacts/real-smoke-20260915/meeting-acked-pro/transcript.md)、[ACK 修正版 flash](../../artifacts/real-smoke-20260915/meeting-acked-flash/transcript.md)、[运行中插话与取消后继续](../../artifacts/real-smoke-20260915/meeting-interrupt/transcript.md)、[主持人自然征询触发的格式失败](../../artifacts/real-smoke-20260915/final-meeting/transcript.md)。

### 5.1 开会、工具、讨论与总结

配置两个参会者 finance/risk，主持人 host，HostDriven 调度，四轮发言，FinalOnly 总结，开启 HITL。初始输入要求讨论 sales/refunds 中的跨境推广收益与风险，至少四次发言，最后询问老板是否结束。会前 HITL 仅补充预算 100 元，并明确“现在没有批准结束”。

实测可以完成：主持人选择 finance → risk → finance → risk；财务读取两份真实文件；各角色围绕 2000 元销售、150 元退款、预算和市场字段缺失讨论；单独调用 Summarizer 生成总结。

**这些基础环节通过。但不能判定整个会议流程通过。**

### 5.2 尚未同意结束，会议已经 Completed

首个四轮成功用例及 ACK 修正版 M1 的总结都明确写着：

```text
老板已补充预算上限100元；会议尚未结束，等待老板明确答复是否结束。
```

同一次运行的 `session.resume` 却返回：

```json
{
  "LatestRun.Status": "Completed",
  "MeetingState.Status": "Completed",
  "MeetingState.CurrentRound": 4,
  "MeetingState.PendingApproval": null
}
```

模型说“等待老板”不等于 Runtime 真的在等待。HITL 发生在首轮开始前，不是会议结束确认门。配置中默认/可选结束条件也没有专门表达“总结后由老板确认结束”的状态闭环。ACK 修正版确认了这不是日志背压假象：flash 的 M1、M2 均在老板未同意时已返回 `Completed`；随后 M3 明确输入“认可结论，可以结束会议”后也能正常完成归档。也就是说最终确认输入可被处理，但确认前的中间状态仍提前结案，完整协议仍不符合旧方案。

### 5.3 老板补充需求与运行中插话

主流程第二轮输入：“先不要结束，退款额增加100元，预算上限改为50元，请继续讨论、修订总结，再征求是否结束。”对照宿主在该轮 HITL 继续提交相同的 50 元/250 元约束，避免测试端输入自相矛盾。第三轮输入为“认可结论，可以结束会议，请归档，不再启动讨论”。每轮真实结果保存在完整会议记录中。

默认 pro 模型的复测最终也完成了 M2、M3；此前 7 分钟超时和紧接着的 Run capacity 拒绝属于旧测试端未等待取消收敛的记录，**不单独把它们归因于产品缺陷**。修正版宿主按公开 SDK 在事件达到批量阈值或终态时调用 `AcknowledgeEventsAsync`，并在取消后等待终态；同一全局配置中的 flash 对照三轮均完成。ACK 后仍观察到上节所述的“确认前 Completed”。

另一个运行中插话探测在第一位参会者开始时，尝试使用现有公开 `StartExistingSessionRunAsync(InputOverride)` 提交补充，实际拒绝：

```text
Runtime RPC failed (-32003): Session 'ec90ae0c7be74e14ada993d7167a7dfd' has reached its Run capacity.
```

当前公开 SDK 没有独立 pause/interrupt/supplement/resume 控制链路，因此这条普通 Run 提交不能替代旧项目的输入队列。随后显式取消旧 Run，再以同一 Session 提交新输入，可以继续模型讨论并吸收 50 元/250 元约束。该对照**不是运行中插话能力通过**：它取消了旧 Run，第二轮也没有保证财务和风控都实际发言，仍提前把会议标为完成。

### 5.4 主持输出与协议边界脆弱

- 初次测试中，主持人输出带 Markdown 围栏的 `{"participantId":"finance","conclude":false}`，触发 `host_decision_invalid`。
- 另一次已经明确要求裸 JSON 的测试中，主持人正确表达业务上的“总结并征询老板”，输出自然语言总结和问题，仍因没有 participantId/conclude 被判 `host_decision_invalid`。
- 默认 HostFailure=Pause 下，该轮没有形成正常会议结束。记录中保留了失败调用、错误码和恢复快照。

这包含模型的协议遵循问题，也暴露了产品层面“主持人需要征询老板”和调度协议“只接受点名/结束”之间缺少明确衔接。加强“调度阶段只输出 JSON、总结交给独立 Summarizer”的提示后能跑完基础讨论，仍不能修复结束确认状态。

### 5.5 内容质量也不能仅看成功状态

一次完整会议中财务提出“US收入800、毛利率假设30%，销售增长12%即可产生约96元毛利并覆盖100元预算”，总结直接沿用了这个结论。正确计算应为 `800×12%×30%=28.8` 元毛利；若按这个毛利率覆盖100元投放，新增销售额需要约333.33元，约增长41.67%。毛利率本身也只是模型假设，原始数据没有提供。

还观察到部分参会者在自己的发言里代写“风控回应/主持人总结”。报告按实际 invocation 身份标注输出，因此可以识别“某角色真的被调用”和“另一个模型替它写了发言”的区别。金融业务验收应增加数字复核及角色边界，不能把 `run.completed` 当作内容正确的证明。

## 6. 问题优先级与建议处理顺序

| 优先级 | 问题 | 建议 |
| --- | --- | --- |
| P1 | 讨论回答被回退成可执行工作步骤，跳过计划确认 | 将讨论、计划草稿、等待确认、执行分开；仅对可执行意图采用计划回退 |
| P1 | 工作多轮自然修改/确认重复发布版本1 | 从持久化状态向总经理提供当前计划、前版和已完成成果，正确生成修订；失败时同步工作状态 |
| P1 | 会议未经老板同意即 Completed | 增加总结后的真实等待状态，用户继续讨论和确认结束走不同状态迁移 |
| P1 | 运行中暂停/补充/恢复控制未实现 | 按现有 [中断重规划实施计划](../工作流暂停与恢复/06-会议与工作模式中断重规划执行计划.md) 落地；该文档明确标注“实施未开始” |
| P2 | 专家同轮工具、独立工作步骤串行 | 在副作用、权限、事件顺序和取消语义明确后实现并发；保留本次内部时间戳测试作为验收 |
| P2 | 主持人协议失败/代写其他角色发言 | 拆开调度、发言、总结、征询的协议职责，增加明确校验与重试/恢复路径 |
| P2 | 金融数字与假设未校验 | 为计算提供真实工具/校验结果，摘要不得直接继承错误推算 |

## 7. 证据与复现说明

所有文件位于 [artifacts/real-smoke-20260915](../../artifacts/real-smoke-20260915/)。每个有效轮次包含 `.input.json`、`.run.json`、原始 `.events.jsonl`、`.result.json`、`.resume.json`、按角色分组的 `.assistant.txt`；每组的 `transcript.md` 将输入、完整输出、实际工具结果和关键流程事件合并展示。`.hitl-response.json` 记录测试宿主真实提交的用户补充/确认。

原始日志保留模型推理增量，人工报告只整理公开回答和工具结果。输入、角色提示词与模式策略完整保留，便于复现和区分提示词约束与运行时状态。
