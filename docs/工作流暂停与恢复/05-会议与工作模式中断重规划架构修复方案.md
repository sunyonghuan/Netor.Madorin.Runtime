# 会议与工作模式中断重规划架构修复方案

> 文档状态：待架构评审，未开始生产代码改造
>
> 编制日期：2026-08-08
>
> 适用范围：`Madorin.AI.Runtime` 的 Meeting、Work、Server、Contracts、SQLite 持久化、Client SDK 和端到端测试
>
> 旧版行为基线：`E:\Netor.me\Madorin\Netor.Madorin\Src\Netor.Cortana.AI`
>
> 对应实施计划：[06-会议与工作模式中断重规划执行计划](./06-会议与工作模式中断重规划执行计划.md)

## 0. 决策摘要

这是一次运行控制架构修复，不是给现有 `run.cancel` 增加一个别名，也不是将启动前 HITL 的 `Supplement` 扩展到运行中。

目标是在当前 Runtime 的 Session、Run、JSONL 权威消息、SQLite 索引和 Outbox 架构内，恢复旧版已具备的两类能力：

1. 会议：运行中由用户暂停或插话，持久化补充内容；恢复后主持人必须先吸收补充、决定影响范围，再调度下一轮。
2. 工作：运行中暂停当前步骤，持久化补充内容；恢复后保留已完成成果，生成新的计划版本，并只执行新计划中仍需执行的步骤。

“保证绝对没有任何 Bug”不是工程上可以诚实承诺的结果。本方案以状态机、事务边界、幂等键、崩溃恢复和分层发布门禁来消除已知失效路径；只有所有门禁通过，才能开放该能力并进入发布验收。

### 0.1 核心决策

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 控制面 | 新增独立的 `Run Control` 控制面 | 暂停、补充和恢复不能复用取消、审批或凭据等待状态。 |
| Run 生命周期 | 用户暂停结束当前 Run Segment，状态写为既有的 `Interrupted`；恢复创建新的 Continuation Run | `RunStatus.Interrupted` 已是终态；不把终态伪装为可继续状态，保证审计和事件序列单调。 |
| Session 生命周期 | Session 始终是可持续会话；控制状态单独持久化 | 会议与工作恢复都依赖完整上下文，不能以 Run 终态推断 Session 是否可继续。 |
| 用户输入 | 先持久化到控制输入账本，再以确定性 Message ID 写入 Canonical History | JSONL 与 SQLite 不是同一事务；先确保输入不丢失，再以可重放方式物化历史消息。 |
| 重规划 | Meeting 由主持人输出结构化恢复决议；Work 由总经理生成 `N + 1` 版本计划 | 不能仅依靠自然语言提示或把旧 Plan 原地改写。 |
| 兼容性 | 新增 JSON-RPC 方法和能力协商，不改变 `run.cancel`、`meeting.hitl.response`、`run.existing_session` 原语义 | 已有宿主和自动化脚本必须继续可用。 |

### 0.2 旧版行为与新版缺口

| 模式 | 旧版已验证行为 | 当前新版行为 | 本次恢复目标 |
| --- | --- | --- | --- |
| Meeting | `PauseAsync` 取消当前轮但保留会议；`EnqueueInterruptAsync` 入队用户插话；下一轮主持人消费 pending 输入并重评执行计划。 | `MeetingHitlAction.Supplement` 仅在首轮前；`PauseInvocationAsync` 仅由调用失败策略触发。 | 运行中暂停、输入入账、主持人恢复决议、下一轮安全调度。 |
| Work | `InterruptCurrentStepAsync` 将 running 步骤回退为 pending，追加用户输入并重新启动编排。 | `Paused` / `Interrupted` 枚举与故障恢复已存在，但没有用户控制入口或计划修订路径。 | 运行步骤安全停靠、输入入账、版本递增、已完成步骤复用、后续步骤重新调度。 |

旧版关键证据：

- `MeetingExecutor.PauseAsync` 与 `EnqueueInterruptAsync`：取消当前 token，但保留会议并写入 pending 输入。
- `MeetingHostManager.UpdateHistoryAsync` 与 `AnalyzeFlow`：把 pending 输入写入主持人上下文，并强制主持人判断恢复点。
- `RunningStepInterruptService.InterruptCurrentStepAsync`：重置当前步骤、写入用户中断日志、取消执行并恢复编排。
- `WorkTaskFileService.ResetRunningStepForInterrupt`：将当前运行步骤重置为 pending 后再注入补充内容。

### 0.3 旧版资产复用原则与清单

旧版是行为基线和可复用资产来源，但不是新 Runtime 的架构模板。实施时按下列优先级处理每项资产：

1. **直接迁移**：与基础设施无关的场景定义、断言顺序、恢复决策规则和提示词约束，原样保留其业务含义，并在新版测试或强类型组件中落地。
2. **受控适配**：可证明正确的 SQL 事务组织、FIFO 消费模式和步骤停靠算法，在保留新版 Repository、版本化 Plan、Outbox 与幂等语义的前提下改写实现。
3. **行为迁移**：旧代码依赖 EF、YAML、旧 Workflow 或内存取消注册表时，只迁移可观察行为、运行步骤和回归场景，不迁移类层级或基础设施代码。
4. **不复用**：任何会破坏新版 Run 终态、可恢复账本、外部副作用去重、AOT 或宿主协议边界的实现，即使旧版可运行也不引入。

每项复用必须在阶段 0 的资产审查表中标记为“直接迁移、受控适配、行为迁移或淘汰”，写明新版落点和测试证据；未完成审查的旧代码不得进入生产分支。新版 Session / Run / JSONL / SQLite / Outbox / Plan Revision 的既有业务语义优先于旧版实现细节。

| 旧版资产 | 可复用内容 | 复用方式与新版落点 | 不可照搬的部分 |
| --- | --- | --- | --- |
| `Tests/Netor.Cortana.MeetingMode.Tests/MeetingRuntimeControlTests.cs` | 用户插话入队、暂停后会议仍可继续、取消注册表竞争的场景和断言顺序。 | 直接迁移场景定义，改写为 `Modes`、`Server` 和真实进程 E2E 测试；保留“暂停不等于取消、补充只入账一次”的断言。 | 旧实体、旧测试基架和内存取消注册表。 |

旧版还暴露出两个必须在迁移时消除的问题：Meeting 不得以文本内容 HashSet 去重，否则连续提交相同补充会被错误吞掉；Work 不得在中断后 fire-and-forget 恢复，必须由持久化账本、幂等键和 Continuation claim 决定唯一后续动作。

## 1. 目标、范围与非目标

### 1.1 必须满足的功能契约

1. 用户在 Meeting 或 Work 运行中发起暂停时，运行不会被误判为用户取消或失败。
2. 用户补充在进程崩溃、连接断开、重复请求后仍不丢失、不重复进入上下文。
3. 同一个控制请求重放时返回同一逻辑结果；同一幂等键携带不同载荷必须被拒绝。
4. 已经发出的非幂等工具调用不得因恢复而重复发出。
5. Meeting 恢复后的首个模型决策必须是主持人恢复决议，不得直接重放被中断的参与者。
6. Work 有补充输入时必须创建不可变的 `planVersion = N + 1`；旧计划和旧步骤只读保留。
7. Work 无补充、纯暂停恢复时允许从稳定检查点续跑，但不得重新生成 `planVersion = 1`。
8. 旧版与新版公共路径的取消、HITL、工具授权、凭据刷新和 Session 恢复行为必须保持各自独立。

### 1.2 本次范围

- Server JSON-RPC 控制协议、能力协商、事件、错误码与 Client SDK。
- Run 控制状态机、并发仲裁、ActiveRun 停止原因和 Runtime 重启恢复。
- SQLite schema 迁移、控制请求账本、控制输入账本、续跑关联和模式级原子停靠。
- Meeting 恢复决议和 Work 计划版本重规划。
- 单元、持久化、Server 集成、真实进程、崩溃恢复、并发和 Native AOT 回归测试。
- 命令矩阵、宿主集成、会话恢复和发布验收文档同步。

### 1.3 非目标

- 不改变 `run.cancel` 的取消语义，不把取消后的 Run 恢复为活跃状态。
- 不把 `meeting.hitl.response`、工具审批或凭据刷新视作用户运行中断的替代接口。
- 不使用内存队列作为用户补充的唯一存储；重启后必须可恢复。
- 不原地覆盖历史 Work Plan、历史步骤、会议调用或 Canonical History。
- 不在本次改造中引入运行时任意更换 Provider、Agent、Model 的能力；续跑仍使用冻结的 Session Selection 快照。
- 不承诺取消已提交到外部系统且不可取消的副作用；此类调用必须先收敛到安全点后才宣布已暂停。

## 2. 修复前现状与根因

### 2.1 当前运行对象不具备暂停语义

`RuntimeServer.ActiveRun` 当前只公开 `Cancel()`，它直接取消 `RunLease` 的 token，没有保存停止原因。Server 的 `run.cancel` 也只尝试从 `_activeRuns` 找到 Run 后调用该方法。此路径无法区分：

- 用户主动终止；
- 用户要求暂停；
- Runtime 关机；
- 超时；
- Provider 或工具调用发生异常。

同时，`RunStateMachine` 将 `Interrupted` 定义为终态。因此，把暂停简单写成 `Interrupted -> Running` 会破坏既有状态机、Outbox 序列、工具去重和审计语义。

### 2.2 当前持久化的暂停是故障策略，不是用户控制

`SqliteMeetingRepository.PauseInvocationAsync` 会把 `meeting_invocations` 记为 `Interrupted`，把 `meeting_sessions` 记为 `Paused`，并将 `runs` 写为 `WaitingForApproval`。它只从主持人或参与者失败策略进入，既没有输入账本，也没有恢复主机决议。

`SqliteWorkRepository.MarkSessionInterruptedAsync` 会将运行中步骤、尝试和后台任务标为 `interrupted/cancelled`，用途是凭据刷新或崩溃收敛。它没有用户补充、当前步骤检查点、版本递增或重规划触发条件。

### 2.3 当前恢复接口只返回快照

`session.resume` 会读取 Session、Meeting 或 Work 快照后返回；它不声明恢复意图，也不会创建续跑 Run。`run.existing_session` 接受 `InputOverride`，但对 Work 会再次进入 `RunAsync` 的初始规划流程，当前实现固定从 `planVersion: "1"` 开始，不能表达“基于执行到一半的任务重规划”。

## 3. 目标架构

### 3.1 分层与职责

```text
Host / Client SDK
    -> JSON-RPC Run Control API
    -> RuntimeServer RunControlCoordinator
    -> RunControlRepository + Mode-specific checkpoint repository
    -> SQLite control ledger / mode aggregates / event outbox
    -> Continuation factory
    -> MeetingModeOrchestrator or WorkModeOrchestrator
```

| 层 | 新增或调整职责 | 禁止承担的职责 |
| --- | --- | --- |
| Contracts | 控制命令、结果、事件、错误码、能力名、恢复上下文 DTO。 | 不直接访问 SQLite 或 ActiveRun。 |
| Server | 鉴权、宿主所有权校验、命令幂等、停机信号、创建 Continuation Run、派发 Outbox。 | 不根据字符串猜测 Meeting / Work 的业务恢复点。 |
| Core | 控制状态机、合法迁移、冲突优先级、请求哈希校验。 | 不修改模式表或生成 Plan。 |
| Persistence | 事务化控制账本；模式表与 Run 状态的原子停靠；恢复查询。 | 不执行模型调用。 |
| Meeting Mode | 物化待消费输入，主持人输出恢复决议，按决议调度新轮次。 | 不调用 Server 字典或自行取消 Lease。 |
| Work Mode | 加载检查点、构造重规划上下文、校验并持久化新版本 Plan。 | 不覆盖旧版本 Plan 或重复已提交工具调用。 |

### 3.2 不可变事实与可变控制状态

不可变事实：Canonical History、`meeting_invocations`、`meeting_rounds`、`work_plan_revisions`、`work_step_attempts`、已完成 Work Step、Outbox 事件。

可变控制状态：当前控制代次、暂停请求、暂停确认、待消费输入、Continuation Run 归属。可变状态仅保存在新增控制表中，并通过 `generation` 做乐观并发控制。

这一区分保证重新规划不会修改历史，也让崩溃恢复能够从“事实 + 当前控制状态”重建下一步，而不是依赖某个已失效的内存对象。

### 3.3 Run Segment 与 Continuation Run

一次用户暂停会结束当前 Run Segment：

1. 当前 Run 到达安全点后落为 `Interrupted`，错误结构为 `UserPaused`，不写 `run.cancelled`。
2. Session 和模式聚合落为 `Paused`，控制账本记录当前 `generation`、已接受输入和断点。
3. `run.resume` 为该暂停代次创建新的 Run，写入 `run_continuations`，并从 `run_id` 到 `resumed_from_run_id` 建立只追加的审计关联。
4. 新 Run 获得自己的 `run_sequence`，旧 Run 的 Outbox 永不追加新的业务事件。

采用新 Run 而非复活旧 Run，可同时保持 `RunStateMachine` 的终态不变、使 Outbox 可重放、避免将旧工具调用和新调用放入同一幂等空间。

## 4. 控制状态机与并发规则

### 4.1 控制状态

控制状态不复用 `RunStatus`、`MeetingSessionStatus` 或 `WorkSessionStatus`。新增内部枚举 `RunControlStatus`：

| 状态 | 含义 | 可接受命令 |
| --- | --- | --- |
| `Running` | 当前 Run Segment 正常执行。 | `pause`、`interrupt`、`cancel` |
| `PauseRequested` | 已持久化暂停意图，正在等当前调用或工具副作用到达安全点。 | `supplement`、`cancel` |
| `Paused` | 当前 Segment 已安全结束，等待输入或恢复。 | `supplement`、`resume`、`cancel` |
| `ResumeStarting` | 已独占取得恢复权，正在建立 Continuation Run。 | `cancel`；重复 `resume` 返回已关联 Run。 |
| `RunningContinuation` | Continuation Run 已启动。 | 以新 Run 再次进入 `pause`、`interrupt`、`cancel`。 |
| `Cancelled` | 用户取消 Session 的当前可继续流程。 | 只接受同幂等键重放。 |
| `Completed` / `Failed` | 模式聚合已终结。 | 只接受只读查询。 |

`PauseRequested` 是关键中间态：Server 只能确认“请求已耐久化”，不能在 Provider、工具或后台任务尚未收敛时谎称已经暂停。

控制状态图：[05-运行控制状态机.html](./05-运行控制状态机.html)（可交互导出）和[源文件](./05-运行控制状态机.lifecycle.json)。

### 4.2 优先级与互斥

所有状态迁移通过同一 SQLite 连接上的 `BEGIN IMMEDIATE` 串行化，并以 `session_id + generation` 比较更新。

1. `cancel` 对任何非终态控制状态具有最高优先级；它可覆盖尚未完成的 `pause` 或 `resume`。
2. `interrupt` 等价于“原子接受 supplement + 请求 pause”；不得出现补充已丢失但暂停已生效，或暂停已取消但补充错误消费的状态。
3. `pause` 只请求停靠，不携带用户内容；`supplement` 可在 `PauseRequested` 或 `Paused` 入账。
4. `resume` 只允许在 `Paused` 执行。输入为空时表示纯续跑；存在未消费补充时按模式进入恢复决议或重规划。
5. 任一请求必须携带客户端生成的 `controlRequestId`。重复 ID 且请求哈希相同返回首次结果；哈希不同返回冲突，不得覆盖原请求。
6. 可选 `expectedGeneration` 不匹配时返回版本冲突，客户端必须刷新 `session.resume` 再决定下一步。

### 4.3 ActiveRun 停止原因

`ActiveRun` 必须从单一的 `Cancel()` 扩展为“第一个获胜原因不可变”的停止模型：

```text
RunStopReason = UserCancel | UserPause | Timeout | HostShutdown | RuntimeFailure
```

`RequestStop(reason)` 用原子比较交换写入首个原因，再取消既有 `RunLease` token。`ExecuteRunAsync` 捕获 `OperationCanceledException` 后必须先读取该原因：

- `UserPause`：进入模式级 `PauseForUserControlAsync`，写 `run.paused`，不发送终态取消事件。
- `UserCancel`：保持既有取消收敛和 `run.cancelled` 行为。
- `Timeout` / `HostShutdown` / `RuntimeFailure`：保持当前故障恢复语义，不伪造为用户暂停。

禁止依靠“异常消息中包含 pause”或 `CancellationToken.IsCancellationRequested` 来推断原因。

### 4.4 安全点与外部副作用

| 执行位置 | 暂停策略 | 成为 `Paused` 的前提 |
| --- | --- | --- |
| 尚未发出 Provider 请求 | 立即停止。 | 当前 Invocation 未开始或已持久化为 interrupted。 |
| 流式 Provider 响应中 | 取消 token，保留已落盘分片，不将半条响应标为完成。 | Invocation、Round / Step 和 Run 已原子停靠。 |
| 工具请求尚未发送 | 不发送该请求。 | 对应 Invocation / Step 停靠。 |
| 工具已发送或外部副作用处理中 | 设置 `PauseRequested`，禁止启动新工作；等待 `tool_intents` 收敛或通过既有恢复机制确认结果。 | 工具最终状态已知，且不会在 Continuation 中重复派发。 |
| Work 后台任务 | 阻止新任务启动；已运行任务按可取消性取消或收敛。 | 所有关联 Job 进入可审计终态或保存可恢复检查点。 |
| HITL / 工具审批 / 凭据等待 | 使旧等待请求失效并标记为被用户中断；迟到响应返回稳定冲突。 | 等待器已释放、旧请求不能再次唤醒原 Segment。 |

暂停能力不承诺回滚第三方已经完成的副作用。对于没有补偿动作的外部工具，正确性标准是“不会重复提交”，不是“假装没有发生过”。

## 5. JSON-RPC、事件与能力协商

### 5.1 新增能力

Server 握手和 Client SDK 协商新增能力名 `run-control-v1`。只有 Server 与 Client 均声明该能力时，UI 才展示运行中暂停、补充与恢复控制；旧 Client 和旧 Server 均保持原行为。

### 5.2 新增命令

| 方法 | 用途 | 前置状态 | 关键参数 |
| --- | --- | --- | --- |
| `run.pause` | 仅请求安全暂停。 | `Running` | `sessionId`、`runId`、`controlRequestId`、`expectedGeneration?`、`reason?` |
| `run.interrupt` | 原子提交补充并请求暂停。 | `Running`、`PauseRequested` | `run.pause` 参数 + `content`。 |
| `run.supplement` | 向已请求或已完成暂停的 Session 追加补充。 | `PauseRequested`、`Paused` | `sessionId`、`controlRequestId`、`expectedGeneration?`、`content`。 |
| `run.resume` | 启动 Continuation Run。 | `Paused` | `sessionId`、`controlRequestId`、`expectedGeneration`。 |
| `run.control.get` | 返回控制状态、代次、待消费输入和关联 Run。 | 任意 | `sessionId`。 |

参数 `content` 使用既有 `ContentBlock[]`，而不是只接受字符串；首期执行仍对文本块制定大小、数量和 Blob 引用限制，沿用 Runtime 现有内容与 Blob 安全边界。

`run.existing_session` 保持“新一轮普通输入”的既有定义，不承担控制恢复。实现中不得根据 `InputOverride` 是否为空偷偷将其转换为 `run.interrupt` 或 `run.resume`。

### 5.3 请求与响应示例

```json
{
  "jsonrpc": "2.0",
  "id": 41,
  "method": "run.interrupt",
  "params": {
    "sessionId": "session-123",
    "runId": "run-456",
    "controlRequestId": "7b2528df-3021-416b-b5f8-1d51d8611d61",
    "expectedGeneration": 3,
    "content": [{ "kind": "text", "text": "补充：预算上限改为 20 万，重新评估供应商。" }]
  }
}
```

```json
{
  "jsonrpc": "2.0",
  "id": 41,
  "result": {
    "sessionId": "session-123",
    "controlStatus": "PauseRequested",
    "generation": 4,
    "acceptedInputId": "control-input-789",
    "activeRunId": "run-456"
  }
}
```

`PauseRequested` 不是错误，也不代表已可恢复。Client 必须等待 `run.paused` 事件或轮询 `run.control.get` 至 `Paused` 后才可发送 `run.resume`。

### 5.4 新增事件

| 事件 | 必含字段 | 何时写入 Outbox |
| --- | --- | --- |
| `run.pause_requested` | `sessionId`、`runId`、`generation`、`reason` | 控制请求及输入账本事务提交后。 |
| `run.supplement_accepted` | `sessionId`、`inputId`、`generation`、`contentHash` | 补充持久化后。 |
| `run.paused` | `sessionId`、`runId`、`generation`、`mode`、`checkpoint` | 模式级停靠事务完成后。 |
| `run.resume_started` | `sessionId`、`previousRunId`、`continuationRunId`、`generation` | 新 Run 已持久化并获得执行容量后。 |
| `meeting.recovery_resolved` | `sessionId`、`runId`、`controlRequestId`、`decision` | 主持人结构化恢复决议已校验并持久化后。 |
| `work.plan_replanned` | `sessionId`、`runId`、`previousPlanVersion`、`planVersion`、`controlRequestId` | 新计划、步骤和映射事务完成后。 |

新增事件只能通过现有 Outbox 写入；不得从 Server 内存直接推送后再补库。

### 5.5 稳定错误码

| 错误码 | 条件 |
| --- | --- |
| `RunControlNotSupported` | 对端未协商 `run-control-v1`。 |
| `RunControlNotFound` | Session、Run 或控制状态不存在。 |
| `RunControlOwnershipDenied` | 当前 Host 不拥有活跃 Run 或恢复权。 |
| `RunControlConflict` | 代次过期、状态不允许、同一请求 ID 载荷不同或迟到响应。 |
| `RunControlTerminal` | Session 已取消、完成或失败。 |
| `RunControlUnsafePoint` | 已接受暂停但仍有不可安全中断的外部操作；只用于诊断，不丢弃请求。 |
| `RunControlRecoveryRequired` | 崩溃恢复发现无法判定的外部副作用，必须人工确认。 |

错误必须同时保留既有 JSON-RPC 信封格式和稳定的 `code` / `message` 字段；不得回显用户补充正文、凭据或工具参数。

## 6. 持久化模型、事务与恢复

### 6.1 Schema 迁移

当前 SQLite Schema 已到版本 16。本次只能追加 `ApplyVersionSeventeenAsync`，不得重写既有迁移、删除列或修改历史记录。迁移必须是幂等、可从任意已支持版本升级、可在已有用户数据上重复启动。

建议新增以下表：

```text
run_control_states
  session_id PK / FK sessions
  mode
  active_run_id
  status
  generation
  pause_reason
  pause_requested_at
  paused_at
  continuation_run_id
  updated_at

run_control_requests
  control_request_id PK
  session_id / run_id
  action
  request_hash
  expected_generation
  accepted_generation
  result_status
  result_json
  created_at / resolved_at
  UNIQUE(session_id, control_request_id)

run_control_inputs
  input_id PK
  session_id
  generation
  control_request_id FK
  payload_json
  payload_hash
  canonical_message_id NULL
  ordinal
  state: pending | materializing | consumed
  consumed_by_run_id NULL
  created_at / consumed_at
  UNIQUE(session_id, generation, ordinal)
  UNIQUE(session_id, control_request_id)

run_continuations
  continuation_run_id PK / FK runs
  session_id
  paused_run_id
  generation
  mode
  created_at
  UNIQUE(session_id, generation)

meeting_recovery_resolutions
  session_id
  generation
  control_request_id
  run_id
  resolution_message_id
  decision_json
  created_at
  PRIMARY KEY(session_id, generation)
```

`payload_json` 是控制输入的耐久来源，允许由现有 Blob 引用表达大内容；它不是第二份可随意编辑的会话历史。`canonical_message_id` 使用由 `sessionId + inputId` 计算出的稳定 ID，保证崩溃重放时同一补充只会物化一次。

### 6.2 原子停靠事务

暂停完成必须由模式专属仓储方法在一个 SQLite 事务中写入，不能让 Server 先改 Run、模式编排器再改 Session，或反过来。事务最低包含：

| Meeting | Work |
| --- | --- |
| 断言 `run_control_states` 仍为目标代次的 `PauseRequested`。 | 断言 `run_control_states` 仍为目标代次的 `PauseRequested`。 |
| 将当前 `meeting_invocations` 标为 `Interrupted`，保存结构化 `UserPaused` 原因。 | 将当前 `work_step_attempts` 标为 `Interrupted`，保存检查点和结构化原因。 |
| 将当前 `meeting_rounds` 标为 `Interrupted`；不删除已完成轮次。 | 将当前 Work Step 写为 `Interrupted`；不修改已完成步骤；后台任务收敛或栅栏化。 |
| 将 `meeting_sessions` 写为 `Paused`。 | 将 `work_sessions` 写为 `Paused`，清理或失效旧审批请求。 |
| 将旧 `runs` 从合法非终态写为 `Interrupted`。 | 将旧 `runs` 从合法非终态写为 `Interrupted`。 |
| 写 `run_control_states = Paused` 与 checkpoint 摘要。 | 写 `run_control_states = Paused` 与 checkpoint 摘要。 |
| 追加 `run.paused` Outbox 记录。 | 追加 `run.paused` Outbox 记录。 |

若其中任一比较更新影响行数不是 1，整个事务回滚，调用方读取控制账本决定是重复请求、被取消覆盖还是运行状态已经变化。禁止“最佳努力”地继续下一步。

### 6.3 Canonical History 物化协议

SQLite 与 JSONL 不能共享数据库事务，因此输入采用可恢复的两阶段物化：

1. `run.interrupt` / `run.supplement` 在 SQLite 事务中写入 `run_control_inputs(payload_json, hash, pending)` 和对应 Outbox。
2. Continuation 创建前，`ControlInputMaterializer` 按 `ordinal` 读取 `pending` 输入，以稳定 `canonical_message_id` 调用 `ConversationStore`。
3. `ConversationStore` 必须支持按 Message ID 的幂等追加：消息已存在且内容哈希相同视为成功；相同 ID 内容不同视为数据损坏并停止恢复。
4. JSONL 成功后，SQLite 事务将该输入更新为 `consumed` 并写入 `canonical_message_id`、`consumed_by_run_id`。
5. 进程任意时刻崩溃后，恢复器重新扫描 `pending/materializing`；不得从 UI 请求正文重新构造补充。

在上一代输入未全部物化之前，不得启动新的模型 Invocation。这是防止“恢复已开始但补充未进入主持人 / 总经理上下文”的硬门禁。

### 6.4 Continuation 创建事务

`run.resume` 在 `Paused` 状态下取得恢复权时执行：

1. 以 `session_id + generation` 将控制状态从 `Paused` 比较更新为 `ResumeStarting`，并记录请求幂等结果占位。
2. 完成待消费输入物化；若失败，状态回到 `Paused`，不创建 Run。
3. 通过现有 `CreateRunAsync` 创建新的 Run；新增 `run_continuations` 关联旧 Run、Session 和代次。
4. 由模式事务更新 `meeting_sessions.run_id` 或 `work_sessions.run_id`，控制状态更新为 `RunningContinuation`。
5. 在同一恢复流程内写入 `run.resume_started` Outbox，随后才将 Continuation 交给 `RunRegistry` 执行。

若步骤 3 后进程崩溃，`UNIQUE(session_id, generation)` 可找到既有 Continuation Run；重放请求必须继续该 Run，而不是创建第二个 Run。

### 6.5 启动恢复与 Host 断线

新增 `RunControlRecoveryService`，在 Runtime 启动、Host 重新绑定和 `session.resume` 查询时执行只读诊断或受控收敛：

- `PauseRequested` 且原 Run 已无内存实例：读取 Invocation Snapshot、工具意图和后台任务，完成模式级停靠或标记 `RunControlRecoveryRequired`。
- `ResumeStarting` 且已存在 Continuation 关联：恢复关联结果，不再创建新 Run。
- `ResumeStarting` 且未创建新 Run：安全回退到 `Paused`，保留已接受输入。
- `RunningContinuation` 但 Run 非正常中断：按既有崩溃恢复规则写结构化断点，不把它错误转换为普通用户暂停。
- Host Lease 失效不会丢弃控制请求；恢复动作仍须遵守当前 Host 所有权和 `session.rehydrate` 规则。

`session.resume` 扩展返回 `RunControlResumeState`，用于展示控制代次、待消费输入数、旧 Run、Continuation Run 和是否需要人工干预；它仍然是只读查询，绝不隐式启动恢复执行。

### 6.6 回滚与数据兼容

- 迁移只新增表、索引和可空/带默认值列；旧二进制忽略新表后仍可读取已有 Session。
- 用户暂停仍使用已有 `MeetingSessionStatus.Paused`、`WorkSessionStatus.Paused` 和 `RunStatus.Interrupted`，避免为回滚路径引入未知枚举值。
- 新 JSON-RPC 方法仅在协商 `run-control-v1` 后调用；旧宿主不会收到未知必需事件。
- 发布前必须执行真实旧数据库副本升级、升级后恢复、二进制回退后只读查询和再次升级测试。

## 7. Meeting 模式恢复设计

### 7.1 停靠规则

Meeting 收到 `UserPause` 后，当前 Provider Invocation 被取消并在安全点写为 `Interrupted`。当前 Round 同样结束为 `Interrupted`，但不回退 `current_round`，不删除部分历史、不再次执行已中断的参与者调用。

Continuation 的第一轮一律调度主持人，而不是 selector 或普通参与者。主持人收到以下显式上下文：

- 原 Run、暂停代次、最后完整 Round、被中断的 Invocation 与可见副作用摘要。
- 按顺序物化的全部用户补充。
- 上次已完成的主持人结论、参与者输出和摘要投影。
- 允许的恢复策略与必须遵守的安全边界。

### 7.2 结构化恢复决议

不能只提示“请继续讨论”。新增内部强类型 `MeetingRecoveryResolution`，由主持人首个恢复 Invocation 返回并严格解析：

```json
{
  "decision": "continue_remaining | revise_remaining | restart_topic | request_clarification | end_meeting",
  "affectedFromRound": 4,
  "reason": "预算上限变化影响供应商比较范围",
  "nextParticipantIds": ["researcher", "finance"],
  "requiresUserReply": false
}
```

解析和持久化规则：

1. `affectedFromRound` 不得小于 1，也不得指向未来 Round。
2. `nextParticipantIds` 必须是当前 `selection_version` 中的 Active Participant。
3. `continue_remaining` 不允许重放被中断 Invocation；必须从新的主持人决议后开始新的调度。
4. `request_clarification` 将 Meeting 写为明确的等待用户状态，使用独立恢复请求 ID；它不是旧 Run 的 HITL 请求。
5. 解析失败、参与者不存在或策略不合法时，Continuation Run 失败并保留 `Paused` 会话可重新恢复，不能静默回退到 Round Robin。
6. 决议 JSON 和主持人消息 ID 写入 `meeting_recovery_resolutions`，随后才写 `meeting.recovery_resolved` 事件。

### 7.3 与现有 Meeting 策略的边界

- `MeetingSelectorPolicy` 仍决定普通轮次的下一位发言者；恢复首轮强制主持人优先。
- `MeetingHitlAction.Supplement` 继续仅服务启动前 HITL；不得复用其 Approval ID 或响应表来存运行中补充。
- 主持人 / 参与者 / selector 的失败策略保持原语义；只有 `RunStopReason.UserPause` 进入本设计的停靠路径。
- 会议总结只能在恢复决议后基于新的 Round 边界生成；被中断 Invocation 的不完整结果不得进入正式总结。

## 8. Work 模式恢复与重规划设计

### 8.1 停靠规则

Work 收到 `UserPause` 时，停止当前执行单元并记录精确检查点：

- 当前 `work_step_attempts` 以 `Interrupted` 结束，保留 `invocation_id`、开始时间、已知工具调用和错误 JSON。
- 当前 `work_steps` 标为 `Interrupted`，保存 `checkpoint_json`；不得伪装为 `Completed` 或将结果清空。
- 已完成或已跳过步骤永不修改；其产出继续是下一版 Plan 的可复用输入。
- 依赖当前步骤的 pending 步骤不启动，直到 Continuation 的新计划明确映射。
- 已发出的工具和后台 Job 必须由 `tool_intents` / Job 记录收敛；不能因新 Plan 重复派发同一 call ID。

这不同于旧版“把当前步骤原地写回 pending”。新版已有不可变计划修订和尝试记录，因此应保留被中断步骤作为历史事实，在下一版本中显式替换它。

### 8.2 纯恢复与重规划的分支

| 恢复条件 | 行为 |
| --- | --- |
| 仅 `run.pause`，没有待消费补充，当前步骤的检查点声明可续跑 | 不生成新 Plan；创建新的 Attempt，在同一 `planVersion` 从检查点继续。 |
| 仅 `run.pause`，检查点不可续跑或存在未知外部副作用 | 返回 `RunControlRecoveryRequired`，等待用户确认或补充。 |
| 存在一个或多个用户补充 | 总经理必须生成 `planVersion = N + 1`，并基于已完成产出、被中断步骤、补充内容和工具状态重规划。 |
| 用户明确要求改变目标、范围、优先级或资源 | 强制 `N + 1`，禁止“纯恢复”。 |

“是否可续跑”只能由结构化 `checkpoint_json` 和工具状态判断，不能由自然语言或时间阈值猜测。

### 8.3 总经理重规划输入

总经理的恢复上下文必须由 `WorkContextProjectionBuilder` 以结构化投影生成，至少含：

```text
sessionId / continuationRunId / pausedRunId / controlGeneration
previousPlanVersion / previousPlanMessageId
completed and skipped steps with result references and hashes
interrupted step, attempt, checkpoint and outstanding tool/job summaries
pending control inputs in ordinal order
available agents, policy, selection version and tool catalog snapshot
explicit rule: emit PlanVersion = previous + 1 and do not mutate previous plan
```

总经理返回 `WorkPlanDraft` 后，校验器除现有 DAG、Agent、深度和工具策略校验外，新增以下约束：

1. `PlanVersion` 必须严格等于上一版本加一，`PreviousPlanVersion` 必须等于当前版本。
2. 新版本的每个依赖都必须存在于新版本；跨版本已完成结果以新版本中的 completed reuse proxy 表达。
3. `ReusesStepId` 必须同时提供 `ReusesPlanVersion`，且只能引用可验证的 `Completed` / `Skipped` 源步骤。
4. 复用的 Agent、目标、输入哈希和结果哈希必须匹配；否则只能用 `ReplacesStepId` 创建新的 pending 步骤。
5. `ReplacesStepId` 必须同时提供 `ReplacesPlanVersion`，并且只能指向 interrupted、pending 或明确声明重新执行的历史步骤。
6. 新计划不得引用已经发送但尚未收敛的工具调用作为可重复工作；它必须引用现有 `tool_intents` 结果或等待人工恢复。
7. 空计划、循环依赖、丢失关键交付步骤、覆盖已完成步骤或版本跳跃均为验证失败。

为消除跨版本歧义，`WorkPlanStepDraft`、`WorkStepSnapshot` 和相应 JSON Source Generator 元数据新增可空的 `ReusesPlanVersion`、`ReplacesPlanVersion`；旧字段不删除，保持向后兼容。

### 8.4 新计划持久化规则

新版本 Plan 的持久化必须是一个事务性整体：

1. 使用稳定 Message ID 写入 Plan 与每个 Step 的 Canonical History；失败可幂等重试。
2. 写 `work_plan_revisions`，`previous_plan_version = N`。
3. 写新版本的所有 `work_steps`、本版本依赖和 completed reuse proxy。
4. 将 `work_sessions.plan_version / plan_message_id / run_id / status` 更新为新值和 `Executing`。
5. 将已物化的控制输入标记为由 Continuation Run 消费。
6. 写 `work.plan_replanned` Outbox；事务提交后才允许 Scheduler 选择 ready Step。

旧 `work_steps`、`work_step_attempts`、`work_plan_revisions` 和原 Plan 消息全部只读保留。任何“为简化调度而删除旧计划”均为阻断级缺陷。

### 8.5 Scheduler 与工具幂等

`WorkStepScheduler` 必须只调度 Continuation 当前 `planVersion` 的 `Pending` 步骤，并以 `run_control_states.generation` 作为调度栅栏。每次准备启动 Child Invocation 前再次验证：

```text
control status = RunningContinuation
AND active run id = this continuation run id
AND generation = invocation control generation
```

验证失败时不创建 Invocation、不派发工具、不增加尝试次数。这样能够阻止“暂停在 Scheduler 选择与 Provider / 工具调用之间到达”造成的幽灵执行。

工具调用继续使用既有 `tool_intents.call_id` 去重。Continuation 需要创建新的逻辑工作时，call ID 的输入必须包含 `continuationRunId + planVersion + stepId + attempt + argumentsHash`；需要恢复旧调用时则必须复用原 call ID，不能生成相同参数的新调用。

## 9. 代码组织与改动边界

### 9.1 新增类型和组件

| 项目 | 类型 / 文件职责 |
| --- | --- |
| `Madorin.AI.Runtime.Contracts` | `RunControlAction`、`RunControlStatus`、命令参数/结果、事件 DTO、`RunControlResumeState`、Meeting / Work Continuation DTO、JSON Source Generator 注册、`MessageTypes` 常量。 |
| `Madorin.AI.Runtime.Core` | `RunControlStateMachine`、请求哈希和合法迁移规则；扩展 `RunStateMachine` 的合法 `Running -> Interrupted` 用户暂停路径，但不允许终态复活。 |
| `Madorin.AI.Runtime.Persistence.Abstractions` | `IRunControlRepository`、模式级暂停/恢复查询契约；所有公开接口带 XML 文档。 |
| `Madorin.AI.Runtime.Persistence.Sqlite` | V17 迁移、`SqliteRunControlRepository`、Meeting / Work 原子停靠方法、输入物化状态和 Continuation 关联查询。 |
| `Madorin.AI.Runtime.Server` | `RunControlCoordinator`、RPC handler、`ActiveRun.RequestStop`、启动恢复、能力协商和 Outbox 派发。 |
| `Madorin.AI.Runtime.Modes.Meeting` | `MeetingContinuationContext`、恢复主持人调度、`MeetingRecoveryResolution` 验证与持久化。 |
| `Madorin.AI.Runtime.Modes.Work` | `WorkContinuationContext`、检查点恢复、重规划投影、跨版本复用校验、代次栅栏调度。 |
| Client SDK / CLI / Host | 新控制 API、事件消费、能力缺失降级、明确的 paused / resume UI 状态。 |

### 9.2 现有组件的明确约束

- `RuntimeServer` 只持有活跃 Run 的短生命周期引用；任何可恢复事实必须在 Repository 中存在。
- `MeetingModeOrchestrator` 与 `WorkModeOrchestrator` 不直接访问 `_activeRuns`，只接收强类型执行 / Continuation 上下文。
- `SqliteMeetingRepository.PauseInvocationAsync` 和 `SqliteWorkRepository.MarkSessionInterruptedAsync` 继续服务故障路径；用户暂停应使用新命名的原子方法，避免再次混淆语义。
- `session.resume` 只查询；`run.resume` 才有副作用。
- `run.cancel` 使用原有端点和含义，但改为经控制协调器仲裁，保证取消可以正确覆盖暂停竞争。

### 9.3 禁止的实现捷径

1. 不在 `RuntimeServer` 增加未持久化的 `ConcurrentQueue<string>` 保存用户补充。
2. 不通过 `run.existing_session(InputOverride)` 假装恢复 Work Step。
3. 不以 `Task.Delay` 或“等流式输出结束”作为唯一暂停确认条件。
4. 不用提示词文字约束替代 `MeetingRecoveryResolution` 或 Work Plan 版本校验。
5. 不为了复用旧代码把 `RunStatus.Interrupted` 改成非终态。
6. 不覆盖、删除或原地修改旧版本 Plan、已完成 Step、已发工具意图或会议调用记录。
7. 不跳过协议、SQLite、AOT、真实进程和崩溃恢复测试就直接打开能力开关。

## 10. 风险、门禁与完成定义

### 10.1 风险控制矩阵

| 风险 | 失效后果 | 架构控制 | 必测证据 |
| --- | --- | --- | --- |
| 暂停与取消竞争 | Session 被错误恢复或错误取消。 | 控制代次、`BEGIN IMMEDIATE`、取消优先级。 | 并发 RPC 与重复请求测试。 |
| 输入先写 JSONL 或先写内存 | 崩溃后补充丢失或重复。 | SQLite 输入账本 + 稳定 Message ID 物化。 | 每个两阶段写入点故障注入。 |
| Provider / 工具取消竞态 | 重复调用、半完成结果被当作完成。 | ActiveRun 停止原因、工具意图去重、安全点栅栏。 | Provider 流、已发送工具、不可取消工具场景。 |
| 旧 Run 被复活 | Outbox 序列和终态约束损坏。 | `Interrupted` 永久终态 + Continuation Run 关联。 | 事件重放与 Run 状态机测试。 |
| Work 原地修改计划 | 已完成结果、依赖或审计丢失。 | `N + 1` 不可变修订、reuse / replace 显式映射。 | 多版本 DAG 与结果复用测试。 |
| Meeting 直接续参与者 | 用户补充没有被主持人吸收。 | 恢复首轮强制主持人 + 结构化决议。 | 主持人决议与下一轮调度测试。 |
| Host 断线 / Runtime 崩溃 | 控制请求悬空、重复 Continuation。 | 恢复扫描、唯一 Continuation、Outbox。 | Kill-process 后重启与重放测试。 |
| AOT 序列化缺失 | 发布制品运行时失败。 | 所有新增 DTO 注册 Source Generator。 | `win-x64` Native AOT 真制品测试。 |

### 10.2 能力开关与灰度

新增配置 `RunControl.Enabled`，初始默认关闭，且只有握手协商成功时才广告 `run-control-v1`。关闭时新增 RPC 返回 `RunControlNotSupported`，原有 Run 路径零行为变化。

启用顺序：开发环境 -> 自动化真实进程环境 -> 内部预发布宿主 -> 发布候选。能力开关不是跳过测试或带病发布的理由；发布候选必须默认开启并通过全部门禁。

### 10.3 完成定义

仅当以下条件全部满足，才可将本修复标记为完成：

- Meeting 与 Work 均已通过旧版行为基线定义的中断、补充、恢复场景。
- 所有控制命令、事件和错误码已冻结并同步 Client SDK、宿主集成与命令文档。
- 任意暂停点、输入物化点、Continuation 创建点发生崩溃后，输入不丢失、不重复执行外部工具、不重复创建 Run。
- Work 重规划始终产生可追溯的 `N + 1` Plan，旧计划与已完成结果未被改写。
- Meeting 首个恢复决议可审计、可解析，且下一轮不会重放中断调用。
- 定向测试、解决方案全量测试、Debug / Release 构建、Native AOT 发布、真实进程和升级回退演练均通过。
- `git diff --check`、文档链接检查、CodeMap overlay 刷新和人工架构评审均通过。

未满足任一项时，该能力不得进入正式发布范围；如发布窗口不能调整，必须保持能力开关关闭并在发行说明中明确该限制。
