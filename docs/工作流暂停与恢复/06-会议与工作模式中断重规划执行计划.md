# 会议与工作模式中断重规划执行计划

> 对应架构方案：[05-会议与工作模式中断重规划架构修复方案](./05-会议与工作模式中断重规划架构修复方案.md)
>
> 当前状态：策划完成，实施未开始
>
> 实施原则：以旧版 `Netor.Cortana.AI` 已存在的用户行为为验收基线；以当前 Runtime 的 Session / Run / Outbox / JSONL / SQLite 架构为实现边界。

## 0. 实施总则

### 0.1 不可跳过的约束

- 任何 C# 修改前，先读取目标目录的 `README.md`，并通过 CodeMap 查询符号、调用链和引用关系。
- 每批 C# 修改后刷新 CodeMap overlay；不得用过时索引判断调用关系。
- 任何数据库变更只能追加 V17 迁移，不修改已发布迁移。
- 每个可以持久化状态的步骤都必须先有失败重放测试，再接入 UI 或能力开关。
- 任何阶段的定向测试失败、状态机不闭合、外部副作用去重不明确时，停止后续阶段，不以“后面再补”继续扩散改动。
- 生产代码、迁移、Contracts、SDK、测试和文档必须同一变更集评审；不允许先合并接口、后续再补持久化语义。
- 旧版资产按“直接迁移、受控适配、行为迁移、淘汰”四级审查；只要与当前 Runtime 的 Run 终态、账本、Outbox、Plan Revision 或宿主协议冲突，即使旧版可运行也不得复用。
- 复用的目标是减少行为分析、测试设计和可靠性实现的重复劳动，不是把旧项目的 EF、YAML、Workflow 或内存状态依赖带入新 Runtime。

### 0.2 实施顺序

```text
旧版资产审查 / 冻结行为 -> 新协议与状态机 -> SQLite 账本 / 恢复 -> Server 控制协调
-> Meeting 恢复 -> Work 重规划 -> SDK / CLI / 文档 -> 全量验证与发布演练
```

Meeting 和 Work 的模式实现可在 Server 控制协调器稳定后并行开发，但 Contracts、迁移、控制状态机和失败注入框架必须先合并，避免两个模式各自发明暂停语义。

- [ ] 重启后从 `PauseRequested`、`Paused`、`ResumeStarting` 三种状态恢复均无丢失或重复。

## 6. 阶段 5：Work 检查点与版本化重规划

### 目标

恢复旧版“中断当前步骤、补充、继续”的用户体验，但使用新版不可变 Plan Revision、步骤尝试、工具意图和 DAG 调度机制实现。

### 工作项

- [ ] 定义 Work Step 的结构化 checkpoint，明确哪些 Provider / 工具状态可纯续跑、哪些必须重规划、哪些需要人工恢复。
- [ ] 迁移旧 `RunningStepInterruptService` 的业务顺序：定位当前步骤 -> 保存用户补充 -> 停止执行 -> 恢复可调度状态 -> 重新进入编排；将其适配为不可变 Step / Attempt 历史和 `N + 1` Plan，而非回写 YAML 或原 Step。
- [ ] 实现纯暂停恢复：只在没有输入且 checkpoint 明确可续跑时创建新的 attempt。
- [ ] 扩展 `WorkContextProjectionBuilder` 生成总经理重规划投影。
- [ ] 扩展 `WorkPlanDraft` / `WorkStepSnapshot` 的跨版本 `ReusesPlanVersion` / `ReplacesPlanVersion` 字段和序列化元数据。
- [ ] 扩展 `WorkPlanValidator` 验证版本递增、本版本 DAG、reuse proxy、replace 映射、工具意图和结果哈希。
- [ ] 实现 `N + 1` 计划、步骤、依赖、revisions、Session 指针、输入消费和 Outbox 的原子持久化。
- [ ] 修改 `WorkStepScheduler`：只选择当前 Continuation Run 与当前控制代次的一致步骤。
- [ ] 验证 Background Job、工具审批、凭据等待和循环检测在新版本计划下不退化。

### Work 验收

- [ ] 中断 running Step 后旧 Step 与 Attempt 保留为 Interrupted，新计划以 `N + 1` 生成替换步骤。
- [ ] 已完成步骤在新版本中按可验证 reuse proxy 复用，结果、哈希、来源版本与依赖均可追溯。
- [ ] 修改输入或 Agent 时 reuse 被拒绝，创建明确 replace Step。
- [ ] 新 Plan 不能依赖已省略的旧版本 Step；所有依赖在当前版本闭合。
- [ ] Scheduler 在暂停竞争中不创建新的 Child Invocation 或工具调用。
- [ ] 模型、工具或 Job 在暂停点崩溃后不会重复执行；状态未知时进入人工恢复而不是猜测继续。
- [ ] 多次重规划产生 `1 -> 2 -> 3...` 连续修订链，历史全部可查询。

## 9. 阶段 8：发布验收、灰度与回滚演练

- [ ] 所有新增和受影响的测试项目定向通过，零失败。
- [ ] `dotnet test Madorin.AI.Runtime.slnx --no-restore` 通过；真实凭据测试仅可按现有明确条件跳过。
- [ ] `dotnet build Madorin.AI.Runtime.slnx -c Debug --no-restore` 与 Release 均为零警告、零错误。
- [ ] `dotnet publish src\Madorin.AI.Runtime.Cli\Madorin.AI.Runtime.Cli.csproj -c Release -r win-x64 --self-contained true -p:PublishAot=true --no-restore` 通过，且候选制品完成控制流程真实进程测试。
- [ ] `git diff --check` 通过；没有改写无关文件、历史迁移或用户已有改动。
- [ ] C# 修改后的 CodeMap overlay 已刷新，新增 RPC、Repository、状态机和模式调用链可查询。
- [ ] 协议、SDK、命令矩阵、宿主文档、发布说明和本修复方案一致。

### 9.2 数据库升级与回滚演练

| 演练 | 预期 |
| --- | --- |
| V16 数据库升级到 V17 | 表、索引、默认值正确；原会话和消息可读取。 |
| 升级后不使用新能力 | 现有 Meeting / Work 运行不改变。 |
| V17 运行一次暂停 / 恢复后回退旧二进制 | 旧二进制仍可只读查看历史 Session；不访问新表时不失败。 |
| 再升级新二进制 | 控制账本、已暂停 Session、输入和 Continuation 关联完整可恢复。 |
| 迁移中断后重启 | 迁移幂等完成，无半张表、半个索引或重复 schema version。 |

### 9.3 灰度步骤

1. 合并后保持 `RunControl.Enabled = false`，运行现有回归与升级演练。
2. 仅内部测试宿主协商 `run-control-v1`，执行 Meeting / Work 全场景 E2E 和故障注入。
3. 预发布环境开启能力，观察控制代次冲突、停靠耗时、工具意图去重和人工恢复指标。
4. 发布候选默认开启能力，在干净数据目录和旧数据升级目录各完整跑一轮。
5. 发布后继续保留能力开关和结构化诊断；发现恢复不确定性时关闭开关并保留控制账本供分析，禁止删除数据掩盖问题。

### 9.4 发布阻断清单

- [ ] 任意一个暂停点仍可能丢失用户补充。
- [ ] 任意一个暂停点可能重复发出外部工具调用。
- [ ] `run.cancel`、HITL、审批或凭据等待被新的控制语义误回归。
- [ ] Meeting 可跳过主持人恢复决议直接恢复参与者。
- [ ] Work 重规划可以覆盖旧 Plan 或绕过版本递增。
- [ ] 任何 V17 升级、重启、回退或再升级路径不确定。
- [ ] Native AOT 或真实进程控制场景未通过。

只要任一项未关闭，正式发布必须阻断；不得因“功能已经能演示”降低门禁。
