# 工作模式架构重构策划

> 文档状态：Work 模式架构重构草案，已按固定工作流程重新整理，待方案确认后再拆分实施任务；本文不是当前源码行为说明，也不授权直接改码。
> 适用范围：仅重新定义 Work（工作/计划）模式的业务流程、Agent 协作、数据权威和运行边界。
> 核心目标：在保留模型动态决策能力的同时，保证“需求确认、计划确认、两级步骤执行、执行报告”始终形成可恢复、可验收的闭环。

> 设计依据：本次确认的“总经理—项目组长—工人”流程及两次独立用户确认。本文件定义目标行为；其中新增工具名、字段和事件均为拟议契约，不表示源码、CLI 或 SDK 已实现。本文替代本文件旧版的“可不发布计划直接执行、扁平工具循环”方案，不改变其他现行文档的源码现状口径。

---

## 1. 方案结论

Work 模式采用**固定生命周期 + 模型驱动内容 + Runtime 强制安全门禁**的架构。

固定生命周期如下：

```text
用户输入需求
  -> 总经理理解需求并讨论
  -> 生成需求理解结果
  -> 用户确认需求
  -> 总经理读取 Agent 清单并选择/创建 Agent
  -> 生成两级结构化计划
  -> 用户确认计划
  -> 项目组长按计划执行二级步骤
  -> 项目组长验证、重试、汇总或上报
  -> 总经理生成结构化执行报告
  -> 用户收到最终总结
```

模型负责业务内容和判断建议，Runtime 负责流程门禁、状态转换、权限、持久化、取消、重试上限和恢复。模型不能通过自然语言回复跳过必经阶段，Runtime 也不能替模型决定需求内容、步骤内容或失败后的业务取舍。

### 1.1 原始要求与本方案的对应关系

| 原始要求 | 本方案实现 |
| --- | --- |
| 需求理解 | Manager 生成版本化 `Requirement` |
| 需求确认 | 用户确认 `RequirementPublished` 版本，进入 `RequirementConfirmed` |
| 策划步骤 | Manager 基于 Agent 快照生成 `Plan`，只允许两级步骤 |
| 确认步骤 | 用户确认 `PlanPublished` 版本，进入 `PlanConfirmed` |
| 循环步骤执行 | Supervisor 按一级步骤、二级步骤循环派发 Worker |
| 执行结果验证 | 程序验证 + Supervisor 模型验证 |
| 超时和重试 | 每个二级步骤使用 `maxAttempts` 和超时策略 |
| 失败处理 | Supervisor 形成失败证据，Manager 提出方案，用户裁决跳过、改计划或取消 |
| 执行报告 | Supervisor 汇总事实，Manager 生成并持久化结构化报告 |
| 两种运行入口 | 独立应用程序模式和主程序调用模式使用同一核心执行闭环 |

### 1.2 不再采用的原则

以下做法不属于本方案：

- 不允许模型在 Work 模式中无计划直接执行；
- 不允许未确认需求或未确认计划时启动 Worker；
- 不允许 Worker 创建第三级步骤或直接修改计划；
- 不允许 Supervisor 绕过统一 ToolGateway 执行工具；
- 不允许仅依据模型一句“已完成”标记步骤成功；
- 不允许用主程序回放事件或 SQLite 索引反向覆盖工作区事实；
- 不允许把总经理、项目组长和工人三个角色的业务职责混为一个不可追踪的循环。

## 2. 目标、范围与非目标

### 2.1 目标

1. 需求理解和用户确认有独立、可追踪的版本与状态。
2. 计划包含一级步骤和二级步骤，最大深度固定为 2。
3. Agent 选择结果、临时 Agent 定义和权限随计划版本冻结。
4. Supervisor 只执行已经确认的计划，统一处理派发、验证、超时、重试和汇总。
5. Worker 只执行一个二级步骤，不拥有全局计划裁决权。
6. 每个步骤都有结构化状态、尝试记录、验证证据和产物引用。
7. 失败可以暂停并交回 Manager 和用户决策，不会悄悄跳过或伪装成功。
8. 最终报告是可持久化、可回放的权威产物；结构化统计可从执行事实重建，模型原始总结需保留，不能假设重新生成的措辞相同。
9. 进程重启、主程序断线、重复响应和未知副作用不会破坏工作事实。

### 2.2 范围

- Work 会话生命周期；
- Manager、Supervisor、Worker 的协作协议；
- 需求、Agent、计划、步骤、结果、报告的数据模型；
- 用户确认、计划修订、失败决策和暂停恢复；
- ToolGateway、ReverseRpc、事件和本地工作区；
- 独立运行和主程序调用的验收流程；
- 旧 WorkMode 的迁移边界。

### 2.3 非目标

- 不重新设计 Expert、Meeting 或无关 Provider；
- 不在本文件冻结最终 C# 类型、数据库表和 UI 页面实现；
- 不把主程序改造成 Work 计划数据库；
- 不承诺旧 Work Session 无损继续执行；
- 不取消权限、路径隔离、资源限制、审计或副作用保护；
- 不允许“模型全权处理”成为绕过 Runtime 安全边界的理由。

## 3. 术语与核心不变量

### 3.1 术语

| 术语 | 含义 |
| --- | --- |
| `workId` | 一个可恢复 Work 工作项的唯一标识 |
| `sessionId` / `runId` | 会话标识 / 一次可恢复执行批次标识；多轮讨论和重启不重新创建 workId，恢复原批次保留 runId |
| `requirementVersion` | 用户已确认或待确认的需求理解版本 |
| `planVersion` | 与一个需求版本关联的不可变计划版本 |
| `stateRevision` | 每次权威状态提交递增的修订号，用于同一计划版本内的并发控制 |
| 一级步骤 | 计划中的业务阶段，负责聚合二级步骤结果 |
| 二级步骤 | 实际派发给 Worker 执行的最小工作单元 |
| Agent Catalog | 当前可用 Agent 的能力、版本、权限和运行配置清单 |
| Agent Snapshot | 计划生成时锁定的 Agent 清单快照 |
| 临时 Agent | 为当前 Work 创建、只在授权范围和生命周期内有效的 Agent |
| Manager | 总经理 Agent，负责用户沟通、需求、计划和最终报告 |
| Supervisor | 项目组长/执行器，负责计划执行编排和结果汇总 |
| Worker | 工人 Agent，负责执行一个二级步骤 |
| ToolGateway | 所有本地工具、宿主工具和 Agent 调用的统一安全执行入口 |
| 执行报告 | 对确认需求、确认计划和实际执行结果的结构化总结 |

### 3.2 必须始终成立的不变量

1. 每个 `workId` 至多有一个当前需求版本、一个当前计划版本和一个活动执行批次；计划尚未生成时引用为 null。
2. 需求正文、计划正文、步骤结果、工具结果和报告正文以工作区文件为权威。
3. 需求/计划正文和 Agent Snapshot 一经发布即不可覆盖；确认、废止和执行状态写入追加记录，查询时组合为当前状态。
4. 只有 `RequirementConfirmed` 的需求才能进入计划确认流程。
5. 只有 `PlanConfirmed` 的计划才能启动 Supervisor 执行。
6. 只有二级步骤才能派发给 Worker；一级步骤只负责聚合。
7. `depth > 2` 的步骤必须被 Runtime 拒绝。
8. 只有经过 ToolGateway 的 Worker 调用才算有效执行。
9. Supervisor 不能把未验证的 Worker 输出标记为成功。
10. 所有二级步骤都有结局、没有活动执行或未裁决副作用、全部步骤成功且报告完成持久化后，才能发布 `work.completed`。
11. SQLite、主程序回放和内存对象都是索引或投影，不得反向覆盖工作区事实。
12. 重复响应不能重复提交；迟到响应可补充实际副作用的审计与恢复证据，但不能复活已取消步骤或自动推进工作。

## 4. 角色模型与职责边界

### 4.1 总经理（Manager Agent）

**职责**：

- 接收用户输入并与用户讨论需求；
- 生成需求理解结果，识别目标、范围、约束和验收标准；
- 在需求确认后读取 Agent Catalog；
- 选择合适 Agent，或申请创建临时 Agent；
- 生成一级/二级结构化计划；
- 根据用户反馈修订需求或计划；
- 接收 Supervisor 的步骤和阶段汇总；
- 在失败、阻塞、部分完成时向用户询问业务决策；
- 在事实汇总完成后生成最终执行报告和用户可读总结。

**输入**：

- 用户需求、补充信息和决策；
- 当前需求版本和计划版本；
- Agent Catalog 或 Agent Snapshot；
- Supervisor 的步骤结果、验证证据、失败信息和产物引用。

**产出**：

- `Requirement`；
- `Plan`；
- 用户交互请求；
- 计划修订版本；
- 最终执行报告和总结说明。

**禁止**：

- 在未确认需求或计划时直接派发 Worker；
- 伪造 Supervisor 的执行结果；
- 直接修改已提交的步骤结果；
- 通过普通文本回复绕过确认工具；
- 修改 Runtime 的安全限制、工具权限或最大深度。

### 4.2 项目组长（Supervisor / 执行器）

Supervisor 是“确定性执行器 + 受限模型验证器”的组合，不是第二个可自由改计划的 Manager。循环、计数、提交和暂停由执行器实现；语义质量由验证模型判断。验证模型只有读取当前步骤证据并返回结构化结论的能力，不能派发 Worker、执行写工具或审批权限。三个业务角色固定存在，不要求三个常驻进程，也不强制使用三个不同基础模型。

**职责**：

- 接收已确认的计划快照；
- 按一级步骤顺序调度二级步骤；
- 为每个二级步骤构造完整上下文并派发目标 Agent；
- 管理单步骤超时、最大尝试次数和取消信号；
- 进行程序验证和模型验证；
- 保存每次尝试、验证结果、失败原因和产物引用；
- 汇总二级步骤为一级步骤，再汇总全部计划结果；
- 将无法自动处理的业务决策上报 Manager；
- 在全部步骤结局确定或工作安全收尾后提交报告事实给 Manager。

**输入**：

- `RequirementConfirmed` 的需求快照；
- `PlanConfirmed` 的计划快照；
- Agent Snapshot；
- 当前工作区状态和用户控制信号。

**产出**：

- 二级步骤执行结果；
- 验证结果和证据；
- 一级步骤汇总；
- 失败/阻塞上报；
- 全部执行事实汇总。

**禁止**：

- 修改需求或计划正文；
- 自行增加、删除或嵌套步骤；
- 在未确认计划时启动 Worker；
- 替 Manager 决定“跳过、改计划还是取消”；
- 绕过 ToolGateway 调用工具或 Agent。

### 4.3 工人（Worker Agent）

**职责**：

- 执行一个指定的二级步骤；
- 在授权工具和工作区范围内完成具体任务；
- 返回结构化结果、产物引用、日志摘要和未解决问题；
- 对无法完成的工作如实返回失败或不确定状态。

**输入**：

- 步骤指令；
- 需求和一级步骤上下文；
- 前置步骤的摘要和产物引用；
- Agent 权限、工作区和工具清单；
- 当前尝试次数及上次失败原因。

**产出**：

```json
{
  "stepId": "1.1",
  "attempt": 1,
  "claimedOutcome": "Succeeded",
  "summary": "已生成需求文档初稿",
  "artifacts": [
    {
      "path": "artifacts/requirements.md",
      "kind": "file",
      "contentHash": "由 Runtime 读取产物后计算"
    }
  ],
  "observations": [],
  "unresolvedItems": []
}
```

Worker 输出是候选结果，`claimedOutcome` 不是步骤状态。Runtime 重新解析产物、计算哈希并保存执行证据；Supervisor 验证通过后才提交权威 `Succeeded`。纯文本任务允许没有文件产物，但必须有持久化文本结果和对应验证标准。

**禁止**：

- 创建第三级步骤；
- 修改全局计划或其他步骤状态；
- 越过 Supervisor 直接派发其他 Agent；
- 访问 Agent Snapshot 未授权的工具、文件或网络；
- 把自然语言“完成”作为唯一结果证据；
- 伪造文件、测试或验证结果。

### 4.4 Runtime 和 ToolGateway

Runtime 不负责替模型决定业务内容，但必须负责：

- 生命周期和状态转换；
- 需求/计划版本校验；
- 两级深度和计划结构校验；
- 权限、路径隔离、资源限额和取消；
- Agent 调用和工具调用的统一入口；
- 幂等、超时、重试上限和未知副作用保护；
- 工作区原子提交、事件顺序和恢复；
- 阻止未确认需求/计划启动执行；
- 阻止不符合完成条件的 `Completed`。

### 4.5 主程序与控制面

主程序提供输入、工具/Agent 描述、交互界面和事件回放，不维护另一份执行权威。CLI 通过本地交互适配器履行同样的职责。

确认结果必须来自已认证的宿主响应或 CLI 用户操作，Manager 只提出请求，不能提交 `confirmedBy` 或伪造用户同意。用户的显式暂停、取消走独立控制通道，不能等当前 Manager/Worker 模型调用结束；自然语言控制意图可由 Manager 解释后发起请求。

### 4.6 通用模型循环与业务推进

Manager 对话、Worker 执行和 Supervisor 验证共用 Provider 请求/结果适配层，但各自使用独立消息投影和能力白名单。ToolGateway 负责副作用调用；纯模型请求仍由统一 Provider 调用层负责，不伪装成 Worker 工具。

每次模型请求都持久化角色、输入引用、响应及工具关联；每次请求的重试与每个步骤的尝试分开计数。Manager 普通回复只结束当前对话轮次，不结束 workId。发布需求/计划后，Runtime 原子建立确认交互，CLI/宿主立即展示，不要求用户先发一句“确认”才打开确认面板。

用户结果提交后，由持久化 continuation 唤醒对应角色；计划确认后的 `PlanConfirmed -> Executing` 也是可恢复 continuation。Supervisor 上报一级结果仅产生已读可确认的消息，Manager 的摘要不能再次触发相同执行。无工具、无有效产物且不能推进的模型响应按有限修复次数处理，耗尽后等待用户，不无限自我调用。

## 5. 固定生命周期

### 5.1 业务状态

以下枚举属于 `Work.phase`，不与需求/计划版本的 `status` 混用。版本状态统一为 `Published / Confirmed / Superseded / Withdrawn`，由状态记录派生；执行位置、暂停、失败和报告阶段属于 Work。`RequirementRevisionRequested`、`PlanRevisionRequested` 是交互动作，不是额外的持久业务状态。

```text
RequirementDiscussing
  -> RequirementPublished
  -> RequirementConfirmed
  -> Planning
  -> PlanPublished
  -> PlanConfirmed
  -> Executing
  -> Reporting
  -> Completed / PartiallyCompleted
```

异常和控制路径：

```text
RequirementPublished -- 请求修订 --> RequirementDiscussing
PlanPublished        -- 请求修订 --> Planning
Executing            -> Paused -> Executing / DecisionRequired
Executing            -> DecisionRequired -> Executing / Planning / RequirementDiscussing
任意未终态 -- 取消 --> Stopping(outcome=Cancelled) -> Reporting -> Cancelled
不可恢复执行错误    -> Stopping(outcome=Failed)    -> Reporting -> Failed
```

### 5.2 状态定义

| 状态 | 进入条件 | 允许动作 | 完成条件 |
| --- | --- | --- | --- |
| `RequirementDiscussing` | 新 Work 或用户补充需求 | Manager 对话、提问、修改草稿 | Manager 形成结构化需求 |
| `RequirementPublished` | 需求版本已持久化 | 用户确认、修改、取消 | 用户对当前版本作出决策 |
| `RequirementConfirmed` | 用户确认需求版本 | 读取 Agent Catalog、进入规划 | 需求版本锁定 |
| `Planning` | 需求已确认 | 选择/创建 Agent、生成计划 | 计划结构校验通过 |
| `PlanPublished` | 计划和 Agent Snapshot 已持久化 | 用户确认、请求修改、取消 | 用户对当前计划作出决策 |
| `PlanConfirmed` | 用户确认计划版本 | 启动 Supervisor | 计划版本锁定，禁止直接修改 |
| `Executing` | Supervisor 已接收确认计划 | 执行、暂停、取消、失败上报 | 所有步骤有结局，或进入等待决策/停止 |
| `Paused` | 用户或系统暂停 | 恢复、取消、查看状态 | 恢复信号有效 |
| `DecisionRequired` | 需要 Manager/用户业务裁决 | 选择动作、修改计划、取消 | 决策已持久化 |
| `Stopping` | 已接受取消或失败结束 | 撤销派发资格、收集在途调用、封闭剩余步骤 | 本地无派发资格；未决外部副作用列入结果 |
| `Reporting` | 执行事实或未执行的取消/失败事实已汇总 | 生成、校验、持久化报告 | 报告及结束记录原子提交，索引可稍后重建 |
| `Completed` | 所有二级步骤成功、无未知副作用，报告已提交 | 查看、回放 | 终态 |
| `PartiallyCompleted` | 计划已预授权跳过或用户接受缺口，报告已提交 | 查看、回放 | 终态，报告必须列出缺口 |
| `Failed` | 失败收尾报告已提交 | 诊断、回放 | 终态 |
| `Cancelled` | 取消收尾报告已提交 | 查看、回放 | 终态 |

`WaitingForUserInput`、`ProviderCalling`、`ToolExecuting`、`Recovering`、`ReportingFailed` 等属于运行技术状态，不替代上述业务状态。以活动调用/待处理交互集合派生技术状态，不能一个交互返回就清掉另一个交互的等待状态。

### 5.3 状态转换硬规则

- `RequirementPublished` 未得到 `confirmed: true`，不得进入 `RequirementConfirmed`；
- `PlanPublished` 未得到 `confirmed: true`，不得进入 `PlanConfirmed`；
- `PlanConfirmed` 之前不得创建有效二级步骤尝试记录；
- 用户拒绝需求或计划但提供修改意见时，旧版本保持只读，新版本递增版本号；
- 用户仅拒绝且不修改时，当前版本保持待确认，不得自动执行；
- `Paused` 不启动新的二级步骤，但可以收尾已开始的调用；
- 进入 `Stopping` 即关闭派发、使未完成交互失效；不等最终 `Cancelled` 才阻止执行；
- 进入 `Completed` 或 `PartiallyCompleted` 前必须存在已持久化的执行报告；
- 任何状态转换都必须携带当前版本、操作者、原因和提交序列。

状态转换需同时校验 `expectedStateRevision`；仅靠 planVersion 无法识别同一版本内先暂停又恢复的竞态。过期的确认/修订/恢复返回最新快照，不能重用旧许可。经过认证的取消属于安全控制，不因展示序列过期而丢弃，按请求 ID 幂等接受。暂停仅针对 Executing；其他阶段不启动 Worker，直接等待已有交互即可。终态不能恢复为 Executing，追加工作创建关联的新 workId。

### 5.4 发布版本与执行期间修订

发布需求/计划需要 `expectedStateRevision` 和 `replacesVersion`。拒绝但不修改时保持 Published；开始修订时撤销旧确认交互并将旧候选记为 Withdrawn。新版本校验通过后，原子提交“旧版本 Superseded、新版本 Published、当前引用和新确认交互”。失败时不留下两个当前版本。

执行中修订先进入 DecisionRequired，停止新派发，取消/收尾旧调用并撤销旧 generation 的派发资格，再进入规划。若目标、范围、约束或验收变化，必须先回 RequirementDiscussing 生成新需求版本并重新确认；仅步骤、Agent 或重试配置变化则回 Planning。两条路径均需要新计划确认，旧版响应不允许提交到新版。

新计划必须列出 `resumeFrom` 映射：原计划版本、步骤、结果、产物哈希和验证证据。只有指令、Agent/授权、验收及依赖输入均保持等价，且 Supervisor 对现存产物重新验证通过，才能提交带 `sourceResultRef` 的新版本结果；否则重新执行。复用事实不是伪造一次 Worker 调用。所有旧尝试保留，既有外部副作用不得在改版后盲目重放。

## 6. 阶段一：需求讨论与需求确认

### 6.1 需求理解产物

Manager 不直接把自然语言理解留在上下文中，而是生成版本化 `Requirement`。本节、计划和报告的 JSON 使用同一个“编写需求文档”示例，不代表整个 Runtime 重构已经完成；哈希、Prompt 引用和模型配置由 Runtime 实际解析，说明文字不能作为生产环境哈希值。

```json
{
  "workId": "work-001",
  "requirementVersion": 1,
  "status": "Published",
  "goal": "编写 Work 模式需求文档",
  "scope": [
    "只处理 Work 模式",
    "保留工具授权和恢复能力"
  ],
  "constraints": [
    "最大步骤深度为 2",
    "需要用户确认需求和计划"
  ],
  "acceptanceCriteria": [
    { "criterionId": "AC1", "description": "文档描述独立应用程序模式的验收流程" },
    { "criterionId": "AC2", "description": "文档描述主程序调用模式的验收流程" },
    { "criterionId": "AC3", "description": "文档包含结构化执行报告要求" }
  ],
  "outOfScope": [
    "不修改 Expert 和 Meeting"
  ],
  "openQuestions": [],
  "createdAt": "2026-10-02T00:00:00Z"
}
```

### 6.2 需求确认流程

```text
用户输入需求
  -> Manager 讨论、追问和整理
  -> mcli_work_set_requirement
  -> Runtime 保存 RequirementPublished 并建立一次确认交互
  -> mcli_work_confirm_requirement 复用该交互，不重复弹窗
  -> ReverseRpc/CLI 获取用户确认
  -> confirmed=true: RequirementConfirmed
  -> confirmed=false: 保持 Published，进入修改或取消
```

需求确认时用户确认的是：

- 目标是否准确；
- 范围和非范围是否准确；
- 约束是否准确；
- 验收标准是否足够；
- 未决问题是否已经清楚。

未决问题不为空时，默认不得确认需求。若用户明确接受风险，必须在确认记录中绑定需求版本、问题 ID、风险和用户决定；不可回写已发布需求正文。若接受风险改变目标或验收标准，则生成新需求版本重新确认。

### 6.3 需求工具

#### `mcli_work_set_requirement`

Manager 提交结构化需求。Runtime 校验字段完整性并创建新版本，不覆盖旧版本。

发布前允许 Manager 使用已授权只读检索理解需求，禁止业务写入、Worker 派发和创建有外部副作用的资源。创建临时 Agent 定义及保存需求/计划是控制面记录，不属于提前执行业务工作。

#### `mcli_work_confirm_requirement`

向用户展示当前需求版本，返回：

```json
{
  "workId": "work-001",
  "requirementVersion": 1,
  "confirmed": true,
  "userInput": null,
  "confirmedBy": "user",
  "timestamp": "2026-10-02T00:05:00Z"
}
```

#### `mcli_work_request_requirement_revision`

记录用户修改意见。Manager 必须根据意见生成新需求版本，重新进入发布和确认流程。

## 7. 阶段二：Agent Catalog 与两级计划

### 7.1 Agent Catalog

需求确认后，Manager 获取当前可用 Agent 清单。清单至少包含：

```json
{
  "catalogVersion": "catalog-2026-10-02-01",
  "availableAgents": [
    {
      "agentId": "doc-writer",
      "agentVersion": "2.1.0",
      "capabilities": ["写文档", "Markdown"],
      "description": "根据已确认需求编写文档",
      "allowedTools": ["file.read", "file.write"],
      "maxConcurrency": 1,
      "enabled": true
    }
  ]
}
```

Manager 选择 Agent 时必须依据能力和授权范围，不能仅依据名称。选择结果写入 `AgentSnapshot`，计划确认后冻结。

Catalog 的能力描述是候选信息，不是授权凭证。最终权限取“宿主策略、用户有效授权、计划声明、Agent 能力白名单”的交集；创建临时 Agent 不能扩权。快照保存 Prompt 内容/哈希、Provider 与 model 引用、工具版本和资源上限，不保存 apiKey。示例中的 file.read/file.write 是能力标识，不宣称已经存在对应工具。

### 7.2 临时 Agent

没有合适 Agent 时，Manager 可以申请创建临时 Agent，但必须经过 Runtime 校验。临时 Agent 至少包含：

```json
{
  "agentId": "temp-agent-001",
  "agentKind": "Temporary",
  "agentVersion": "1",
  "prompt": "你是一个专门分析配置迁移的 Agent。",
  "promptHash": "由 Runtime 对规范化 Prompt 计算",
  "capabilities": ["配置分析"],
  "allowedTools": ["file.read"],
  "workspacePolicy": "isolated",
  "expiresAt": "2026-10-02T12:00:00Z",
  "canCreateAgents": false,
  "canModifyPlan": false
}
```

临时 Agent 规则：

1. 默认只读，写权限必须在计划中显式声明并通过权限审批；
2. 不能创建其他 Agent、修改计划或直接改变步骤状态；
3. Prompt、能力、工具、模型和有效期进入 Agent Snapshot；
4. 计划确认后不得静默替换 Agent；
5. Agent 不可用时，必须上报 Manager，由 Manager 生成新计划版本或选择停止；
6. 临时 Agent 的生命周期和资源额度受 Runtime 限制。

创建接口必须实际返回已注册且可解析的 ID，Manager 不能自行编造 temp-agent ID 当成创建成功。定义保存在当前 workId 的私有目录，Worker 调用时才实例化；结束后释放执行资源但保留只读定义用于审计。暂停期间过期/凭据撤销一律重新校验，申请替换或续期需新快照和计划确认。

### 7.3 计划结构

计划包含一级步骤和二级步骤，二级步骤是唯一可执行节点：

```json
{
  "workId": "work-001",
  "requirementVersion": 1,
  "planVersion": 1,
  "status": "Published",
  "goal": "编写 Work 模式需求文档",
  "agentCatalogVersion": "catalog-2026-10-02-01",
  "agentSnapshot": [
    {
      "agentId": "doc-writer",
      "agentVersion": "2.1.0",
      "promptRef": "agents/definitions/doc-writer-2.1.0.json",
      "modelRef": "deepseek/deepseek-v4-pro",
      "allowedTools": ["file.read", "file.write"]
    }
  ],
  "steps": [
    {
      "stepId": "1",
      "depth": 1,
      "name": "完成需求文档",
      "objective": "形成包含双入口验收和报告要求的需求文档",
      "subSteps": [
        {
          "stepId": "1.1",
          "parentStepId": "1",
          "depth": 2,
          "name": "编写需求文档",
          "targetAgentId": "doc-writer",
          "targetAgentVersion": "2.1.0",
          "instruction": "根据已确认需求生成需求文档",

    { "criterionId": "AC1", "stepIds": ["1.1"], "check": "cli-acceptance-section" },
    { "criterionId": "AC2", "stepIds": ["1.1"], "check": "host-acceptance-section" },
    { "criterionId": "AC3", "stepIds": ["1.1"], "check": "report-requirements-section" }
  ],
  "createdAt": "2026-10-02T00:10:00Z"
}
```

### 7.4 两级深度约束

Runtime 必须执行以下硬校验：

- 顶层 `steps` 的 `depth` 必须为 1；
- `subSteps` 的 `depth` 必须为 2；
- 二级步骤的 `parentStepId` 必须指向当前一级步骤；
- 二级步骤不得包含 `subSteps`；
- 计划树中不得出现 `depth > 2`；
- `stepId` 在同一计划内必须唯一；
- `dependsOn` 只引用扁平执行顺序中位于当前步骤之前的二级步骤 ID，禁止前向依赖、自己、父节点和循环；
- 计划至少包含一个一级步骤，且每个一级步骤至少包含一个二级步骤；
- 一级步骤不能直接作为 Worker 的执行目标；
- 没有二级步骤的一级步骤不能标记为成功；
- 二级步骤必须有目标 Agent、指令、期望产出、超时和最大尝试次数。

“二级深度”限制的是计划结构，不限制 Worker 内部的推理过程。Worker 不得把内部推理转化为新的可调度步骤。

### 7.5 计划生成与确认

```text
RequirementConfirmed
  -> Manager 获取 Agent Catalog
  -> Manager 选择/创建 Agent
  -> Manager 生成 Plan + AgentSnapshot
  -> mcli_work_set_plan
  -> Runtime 校验并保存 PlanPublished、建立一次确认交互
  -> mcli_work_confirm_plan 复用该交互，不重复弹窗
  -> confirmed=true: PlanConfirmed
  -> confirmed=false: PlanRevisionRequested 或保持 Published
```

计划确认展示内容必须包括：

- 需求版本和目标；
- 一级步骤、二级步骤和依赖关系；
- 每个二级步骤的目标 Agent 和能力；
- 期望产出、验收规则、超时和最大尝试次数；
- 写入文件、外部调用和权限范围；
- 失败后的默认处理建议；
- 预计产生的产物。

计划确认后，计划内容和 Agent Snapshot 只读。任何步骤内容、Agent、权限或验收标准变化都必须生成新的 `planVersion` 并重新确认。

`mcli_work_set_plan` 输入为正文和 expectedStateRevision，planVersion 由 Runtime 分配；校验失败仅返回结构化错误，不发布部分计划。确认绑定正文哈希、需求版本与 Agent Snapshot 哈希。用户确认业务计划不等于授予所有工具权限，ToolGateway 执行时仍独立审批。

`required` 只定义在二级步骤上：false 允许按已确认计划在失败时自动跳过；true 必须由用户明确跳过。两者都必须有结局并进入报告，任何跳过或接受失败均不能记完整完成。

## 8. 阶段三：Supervisor 执行计划

### 8.1 执行前置条件

Supervisor 只有在以下条件全部满足时才可执行：

```text
Requirement.status == Confirmed
Plan.status == Confirmed
Plan.requirementVersion == current Requirement.version
AgentSnapshot 校验通过
工作区锁定成功
```

启动及每次派发都再次校验 Work.phase、stateRevision、generation 和当前需求/计划引用，防止“已检查—暂停/改版—仍派发”的竞态。调用记录先以当前 generation 原子占位，再执行外部调用；暂停/取消在占位后发生则视为在途调用，按收尾规则处理。

执行启动时写入 `ExecutionStarted` 记录，绑定：

- `workId`；
- `runId`；
- `requirementVersion`；
- `planVersion`；
- `agentSnapshotHash`；
- Runtime 版本；
- 启动时间和启动原因。

### 8.2 默认执行顺序

默认按计划顺序串行执行：

```text
for each topLevelStep in plan.steps:
    for each subStep in topLevelStep.subSteps:
        control = check current Work.phase and generation
        if control is Paused or Stopping or AwaitDecision: return control
        if current effective state is Succeeded: continue
        if current effective gap is explicitly accepted: continue
        if unresolved failure or Unknown exists: return AwaitDecision
        if dependency is not Succeeded:
            persist Blocked and DecisionRequired
            return AwaitDecision  // 不等待一个已失败依赖自动成功
        outcome = ExecuteAndValidate(subStep)
        if outcome is not Succeeded and outcome is not Skipped:
            return outcome       // 从提交位置恢复，不进入下一个步骤
    persist topLevelStep aggregate
atomically recheck phase, generation, all step outcomes and pending decisions
if phase is not Executing: return current control state
if any active attempt, Unknown or unresolved decision exists: return AwaitDecision
if any step lacks a final effective outcome: return Recovering
if acceptance failed without user waiver: persist DecisionRequired; return AwaitDecision
commit whole-plan aggregate and Reporting
return Reporting
```

本轮仅实现串行执行：一级步骤依次推进，各一级步骤内二级步骤依次推进，不在本轮引入 DAG 调度或并行波次。后续并行能力需要单独策划产物冲突与顺序协议，不能由模型临时开启。

### 8.3 二级步骤执行循环

```text
while true:
    control = check phase, generation and permission
    if control is Paused or Stopping or AwaitDecision: return control
    if an unfinished attempt exists:
        load the same attemptId, result and durable stage
        if stage is invocation-in-flight or Unknown:
            return Recovering  // 先核验原调用，不再次派发
    else:
        if persistedNextAttempt > maxAttempts:
            persist DecisionRequired
            return AwaitDecision
        create attempt atomically and consume one Worker attempt allowance
        result = invoke Worker through ToolGateway
        if timeout or cancellation:
            revoke attempt token; cancel and drain boundedly
            if phase is Stopping:
                persist cancellation outcome and known/unknown effects
                return Stopping
            if still running or side effects are unknown:
                persist Unknown and pending decision without overriding Paused/Stopping
                return current control state
        persist candidate result or definite invocation failure before validation
    if no valid Worker result:
        validation = execution failure classification; do not run content validation
    else if a final validation verdict was already committed:
        load that verdict  // 崩溃后只补状态提交，不重复 Worker 或验证
    else:
        validation = resume same attempt validation (program -> rules -> model)
        // 只恢复尚未完成的验证层；不消耗新的 Worker 尝试额度
        if validation service unavailable after bounded retries:
            if phase is Stopping: persist checkpoint for audit; return Stopping
            persist validation checkpoint and pending decision
            return Paused if paused else AwaitDecision
    persist attempt outcome and validation evidence
    atomically recheck phase, plan version and generation before result commit
    if phase is Stopping or generation changed: return current control state
    if validation passed:
        commit Succeeded and artifact references
        return Paused if paused else Succeeded
    if retryable AND retrySafetyVerified AND persistedNextAttempt <= maxAttempts:
        finalize this attempt; persist RetryPending
        if phase is Paused: return Paused
        wait bounded backoff; continue
    if subStep.required == false AND effects are known:
        finalize this attempt
        persist Skipped with confirmed-policy reason
        return Paused if paused else Skipped
    finalize this attempt; persist Failed and pending decision
    return Paused if paused else AwaitDecision
```

`maxAttempts` 表示**包含第一次执行在内的总尝试次数**。例如 `maxAttempts: 3` 表示最多执行三次，即第一次执行加两次重试。

失败分支必须 return，不能落入成功验证或下一轮循环。没有输出时不运行内容验证。已取得有效 Worker 结果后验证器暂时失败，只恢复验证阶段，不重新执行 Worker。

`unfinished attempt` 优先于新尝试额度检查；因此 maxAttempts=1 且已有候选结果时仍能恢复验证，不会误报“额度用尽”。验证服务故障的用户决定是 resume_validation，不是 retry_worker；已完成的验证层、剩余验证额度和同一 attemptId 必须沿用。若验证修复额度耗尽，需要用户明确批准受 Work 总预算限制的修复额度，不能重启归零。

有效状态来自追加记录的最新已提交结果，而不是“文件中曾经有一个结果”。用户批准续跑后，原失败保留为历史证据，当前状态变为 RetryPending；外层不跳过它。外层必须原样返回 Recovering 等未完成控制结果；暂停期间可提交步骤成功，但所有推进 Reporting 的路径都要再次原子检查 Work.phase。

伪代码中的 `pending decision` 提交动作会在同一事务中将 Executing 转为 DecisionRequired；若当前已是 Paused/Stopping，则只登记待决事项，不覆盖控制状态。`AwaitDecision / Recovering` 是执行器返回信号，分别对应等待业务决策和等待技术核验，不是新的 Work 终态。每一次 continue 都必须经过新尝试额度或尚未完成验证层的有界检查。

#### 8.3.1 步骤状态与依赖阻塞

二级步骤状态为 `Pending -> Running -> Validating -> Succeeded`；可重试失败进入 `RetryPending -> Running`。`Failed / Skipped / Cancelled / Blocked` 表示本次执行结局，只有同一版本尚有已批准尝试额度时 Failed 可由明确续跑记录进入 RetryPending；耗尽后不能重置计数。`Unknown` 是非成功、非可重试状态，等待副作用核验；全局失败/取消时将其封存为 Failed/Cancelled 并保留 effectState=Unknown，不消除风险。

依赖被跳过/失败后，所有依赖它的步骤阻塞，Supervisor 上报受影响列表。用户可接受整个阻塞子集为部分完成、修改依赖并重新确认计划或取消；不能因为选了“跳过当前步骤”就把缺失输入传给后续 Worker。一级步骤没有独立 required 开关，按下一节聚合。

### 8.4 上下文构造

Worker 收到的上下文必须结构化，不只传递“上一个步骤的自然语言结果”：

```json
{
  "workId": "work-001",
  "runId": "run-001",
  "requirementVersion": 1,
  "planVersion": 1,
  "topLevelStepId": "1",
  "stepId": "1.2",
  "parentStepId": "1",
  "instruction": "审核需求文档",
  "expectedOutput": "审核结论和问题列表",
  "previousResults": [
    {
      "stepId": "1.1",
      "status": "Succeeded",
      "summary": "已生成需求文档",
      "artifactRefs": ["artifacts/requirements.md"]
    }
  ],
  "retryContext": {
    "attempt": 2,
    "previousFailure": "缺少验收标准"
  },
  "workspacePolicy": "Runtime 解析后的本次尝试隔离目录",
  "allowedTools": ["file.read", "file.write"]
}
```

### 8.5 一级步骤汇总

一级步骤状态由 Runtime 根据二级步骤事实计算，不能只由模型自由指定：

| 二级步骤汇总 | 一级步骤状态 |
| --- | --- |
| 所有二级步骤 `Succeeded` | `Succeeded` |
| 工作取消，剩余步骤已收尾 | `Cancelled`（保留已成功步骤） |
| 有 `Failed / Blocked` 且未获准接受缺口 | `Failed` |
| 存在获准的 `Skipped / Failed / Blocked` 且其他步骤成功 | `PartiallyCompleted` |
| 有未终态/Unknown 或未消费决策 | 保持运行或等待，禁止完成汇总 |

一级步骤完成时，Supervisor 向 Manager 上报：

```json
{
  "topLevelStepId": "1",
  "status": "Succeeded",
  "subStepStatistics": {
    "total": 2,
    "succeeded": 2,
    "failed": 0,
    "skipped": 0,
    "cancelled": 0
  },
  "results": [],
  "artifactRefs": [],
  "unresolvedItems": []
}
```

汇总优先级为“活动/未知/待决策 -> 取消 -> 未接受失败 -> 已接受缺口 -> 全成功”。统计只计二级步骤，不将一级聚合重复相加；复用步骤计一次成功，attempts 只计真实 Worker 尝试。全部跳过也只能是 PartiallyCompleted，不能因成功数为零而误判 Completed。

## 9. 验证、超时、重试与失败决策

### 9.1 分层验证

每个二级步骤至少经过以下验证层：

**第一层：程序验证**

- 必需文件是否存在；
- 文件是否位于授权工作区；
- JSON、Markdown 或其他格式是否可解析；
- 必要字段是否完整；
- 编译、测试或命令退出码是否符合要求；
- 产物哈希和大小是否可记录；
- 是否超出资源、路径和工具权限限制。

**第二层：规则验证**

- 是否满足步骤声明的格式和章节要求；
- 是否修改了允许范围内的文件；
- 是否生成全部必需产物；
- 是否满足依赖步骤的输入条件；
- 是否出现不允许的副作用。

**第三层：Supervisor 模型验证**

- 实际结果是否达到 `expectedOutput`；
- 结果是否与需求和前置步骤一致；
- 是否存在遗漏、矛盾或需要返工的问题；
- 失败是否可以通过新的尝试解决。

### 9.2 验证结果

```json
{
  "passed": false,
  "reason": "输出缺少验收标准章节",
  "evidence": [
    {
      "artifact": "artifacts/requirements.md",
      "location": "heading: 验收标准",
      "message": "未找到对应章节"
    }
  ],
  "retryable": true,
  "failureType": "ValidationFailed",
  "suggestedFix": "补充验收标准后重新生成文档"
}
```

模型验证不能覆盖程序验证失败。程序发现产物不存在、权限越界或格式非法时，Supervisor 必须先处理程序事实。

验证请求绑定 `planVersion / stepId / attemptId / resultHash / validationPolicyHash`，记录验证模型配置、结论和引用证据。Worker 只能提供候选结论，不能提交验证通过记录。验证模型输出非法 JSON、无证据或 Provider 超时，记为验证调用故障；在有限次数内修复验证调用，不重新执行已有结果的 Worker。耗尽后进入 DecisionRequired，不将“验证器不可用”当成“任务已失败需要再次写文件”。

验证器的 `retryable` 只是建议，最终还必须通过 Runtime 的副作用安全和剩余额度检查。产物提交与后续引用均绑定内容哈希；需要修改前一步产物时生成新版本，并保留前一次验证对应的快照。

### 9.3 超时与重试

本方案拟定的初始配置（不是现有软件配置项说明）：

```json
{
  "timeoutSeconds": 300,
  "maxAttempts": 3,
  "backoffSeconds": [5, 15],
  "retryOn": ["Timeout", "TransientProviderError", "ValidationFailed"],
  "cancelDrainSeconds": 30,
  "validationMaxAttempts": 2
}
```

不可盲目重试的情况：

- 权限拒绝；
- Agent 不存在或版本不匹配；
- 计划版本过期；
- 用户取消；
- 外部副作用已发生但结果未知；
- 输入不满足前置条件；
- 非幂等操作无法确认是否已经提交。

重试必须复用同一逻辑步骤 ID，但每次尝试拥有唯一 `attemptId`。如果调用传输重试可能重复提交，则必须复用同一 `callId`，不能把同一调用误记为多个副作用。

时间与计数口径：`timeoutSeconds` 为一次 Worker 尝试的活动执行时长，工具授权等待单独持久化且不消耗该时长；验证调用有独立有限超时，不使用等待用户的无限窗口。`maxAttempts >= 1` 且为整数，所有超时须为正有限值；实际预算还受宿主给出的 Work 累计调用数、Token、成本和运行时长上限约束。重启不得重置累计预算。

超时后先撤销本尝试的工具执行令牌，再发送取消并等待最多 `cancelDrainSeconds`。收到停止确认且副作用已知，才考虑重试；仍运行或结果未知时进入 Unknown 并停止派发。不能把超时视为“肯定没有执行”。校验失败后的重试也可能重复外部操作，必须提供“纯计算/隔离产物、已验证补偿、执行端支持同一 operationId 去重”之一的安全证据；仅有模型 `retryable=true` 不够。

不同 attempt 使用不同 attemptId 和调用 callId；同一外部业务操作跨 attempt 用稳定 `operationId` 关联执行端幂等键。外部工具不支持幂等/状态查询时，Unknown 交给用户核验，不能自动换一个 callId 重放。Provider 传输重试、验证重试与 Worker 尝试分别计数，但全部受 Work 总预算约束。

### 9.4 失败上报与业务决策

Supervisor 负责判断技术事实，不负责替用户选择业务方案。达到最大尝试次数或遇到不可重试失败时，生成：

```json
{
  "decisionId": "decision-001",
  "stepId": "1.2",
  "status": "DecisionRequired",
  "failureType": "ValidationFailed",
  "retryable": false,
  "blocking": true,
  "attempts": 3,
  "reason": "三次输出均缺少审核结论",
  "availableActions": [
    "retry_with_new_instruction",
    "revise_plan",
    "skip_step",
    "cancel_work"
  ],
  "evidenceRefs": ["execution/attempts/1.2.jsonl"]
}
```

Manager 根据执行事实提出选项，用户经关联 decisionId 的交互作出裁决；只有计划中明确预授权的可选步骤跳过不需再次询问：

1. **继续重试**：仍有当前版本额度且输入/配置未变时可以显式续跑；修改指令、Agent、超时或增加额度必须走新计划确认。达到 maxAttempts 后禁止原版本归零重试；
2. **跳过步骤**：用户明确同意，步骤记为 `Skipped`，相关一级步骤和最终报告必须标记部分完成；
3. **修改计划**：遵循第 5.4 节重新确认及复用规则；复用必须有来源证据和重新验证，不能把旧调用伪造为新版 Worker 尝试；
4. **取消工作**：未启动步骤取消，进行中的调用按取消策略收尾；
5. **结束为失败**：保留完整失败证据，生成失败报告。

未收到业务决策时，Supervisor 必须暂停启动新的步骤。

Manager 暂不可用时，Runtime 直接呈现结构化失败和安全选项，保持等待；不得由 Supervisor 代替用户决定业务取舍。因额度或权限拒绝暂停后，只有有效用户决策和权限恢复才能继续。

## 10. 执行报告与最终总结

### 10.1 报告生成顺序

```text
正常执行结束，或取消/失败完成安全收尾
  -> Supervisor 汇总执行事实
  -> Runtime 校验统计、产物引用和需求验收覆盖
  -> 进入 Reporting
  -> Manager 生成总结（不可用时生成标注降级的事实报告）
  -> Runtime 原子提交不可变报告、终态和对应事件
  -> 可选生成 execution-report.md
  -> 投递 work.completed / work.partially_completed / work.failed / work.cancelled
  -> CLI/宿主展示已保存的报告和总结
```

Manager 可以压缩表达，但不能删除失败步骤、跳过步骤、未解决事项和关键证据。

总经理总结与最终输出是同一份已保存内容，不在 work.completed 后再依赖一次模型调用才能交付。统计和状态由 Runtime 从事实计算，Manager 不能改成功数、漏报失败或虚构测试通过。报告提交不以 SQLite 索引可用为前提。

### 10.2 报告结构

权威报告至少包含：

```json
{
  "workId": "work-001",
  "runId": "run-001",
  "requirementVersion": 1,
  "planVersion": 1,
  "agentSnapshotHash": "由 Runtime 计算的快照哈希",
  "status": "Completed",
  "startedAt": "2026-10-02T09:00:00Z",
  "completedAt": "2026-10-02T10:30:00Z",
  "stepStatistics": {
    "topLevelTotal": 1,
    "subStepTotal": 1,
    "succeeded": 1,
    "failed": 0,
    "skipped": 0,
    "cancelled": 0,
    "blocked": 0,
    "attempts": 1
  },
  "steps": [
    {
      "stepId": "1.1",
      "parentStepId": "1",
      "targetAgentId": "doc-writer",
      "status": "Succeeded",
      "attempts": 1,
      "resultSummary": "已生成需求文档",
      "artifactRefs": ["artifacts/requirements.md"],
      "validationRefs": ["execution/validations/1.1.jsonl"]
    }
  ],
  "failures": [],
  "acceptanceResults": [
    { "criterionId": "AC1", "passed": true, "evidenceRefs": ["execution/validations/1.1.jsonl"] },
    { "criterionId": "AC2", "passed": true, "evidenceRefs": ["execution/validations/1.1.jsonl"] },
    { "criterionId": "AC3", "passed": true, "evidenceRefs": ["execution/validations/1.1.jsonl"] }
  ],
  "unresolvedItems": [],
  "recommendations": [],
  "reportVersion": 1
}
```

报告状态定义：

- `Completed`：全部二级步骤成功，需求验收项有证据且通过，无未裁决副作用；
- `PartiallyCompleted`：存在计划预授权跳过，或用户明确接受的失败/阻塞/验收缺口；
- `Failed`：必需步骤失败、需求验收失败或不可恢复执行错误，且用户未接受对应缺口；已成功步骤保留成功事实，不为匹配报告状态改写为失败；
- `Cancelled`：用户取消。

`work.completed` 只能引用已经 flush/fsync 成功的报告文件。报告生成失败时不能发布完成事件，应进入 `ReportingFailed` 技术错误路径并保留执行事实。

### 10.3 异常报告与需求验收

计划发布时必须提供需求验收项到步骤验证或最终汇总检查的映射；Supervisor 汇总时逐项给出 evidenceRefs。步骤都成功但需求验收未满足，进入 DecisionRequired，不得自动宣布完成。

失败/取消走 Stopping -> Reporting -> Failed/Cancelled；未启动步骤标明 Cancelled，依赖阻塞标明 Blocked，旧失败原因保留。在需求/计划未确认前取消也要报告，未产生的 planVersion、runId 可为 null，步骤统计为 0，不伪造计划或成功步骤。总数校验为 succeeded + failed + skipped + cancelled + blocked = subStepTotal。

Manager 报告调用失败只进行有限报告重试，不重新执行任何 Worker；仍失败时 Runtime 根据已提交事实生成 `summarySource=RuntimeFallback` 的报告，明确“模型总结不可用”，并展示准确结果。如果文件存储本身故障，则保持 Reporting/Recovering、关闭派发并显式报告无法持久化；不能宣称完成，存储恢复后仅补报告提交。

未知外部副作用必须列入 unresolvedItems，正常或部分完成路径不允许忽略；用户选择失败结束/取消时可以封存风险，但不得将 Unknown 改成“无副作用”。之后补证据只新增报告版本和更正事件，不覆写已交付报告或恢复执行。

### 10.4 用户可读总结

最终总结至少说明：

- 本次确认的需求；
- 使用的计划版本和 Agent；
- 成功、失败、跳过、取消的步骤统计；
- 主要产物路径；
- 失败原因和未解决事项；
- 是否为完整完成或部分完成；
- 后续建议。

## 11. 工具、Agent 调用与通信协议

### 11.1 统一执行链路

所有 Worker 工具和 Agent 调用必须经过同一条链路：

```text
Manager 控制面请求 / Supervisor 派发 / Worker 业务工具请求
  -> Work Orchestrator
  -> ToolGateway
     1. 校验角色及必要关联字段（Worker 必须绑定 planVersion、stepId、attemptId）
     2. 校验 Agent Snapshot 和工具权限
     3. 校验取消、暂停、资源和路径边界
     4. 创建 callId 和待执行记录
     5. 通过 ReverseRpc、本地 Agent Host 或进程通道调用 Worker
     6. 记录结果、产物和副作用状态
     7. 发布工具事件
  -> Supervisor 验证并汇总
```

禁止新增绕过 ToolGateway 的 `dispatch_step` 旁路。Supervisor 的“派发”是业务编排动作，不是第二套工具执行协议。

Manager 在需求/计划阶段的控制面调用没有 stepId，不强制伪造 Worker 上下文。Worker 调用工具时继承当前 attempt 的权限和 generation，不能把模型传入的角色或工作目录当成可信身份。Supervisor 的外层 Worker 调用和 Worker 内部工具调用都经过网关，但等待模型/宿主时不持有工作区提交锁，也不占住内层所需的唯一并发配额，避免重入死锁。

暂停/停止门禁区分“新业务副作用”和“查询、收尾、验证、报告”：关闭新业务派发不应同时禁用状态查询与报告落盘。安全控制可撤销令牌，随后到达的 Worker 写工具被拒绝；已发出的外部副作用不能声称已回滚。

### 11.2 建议的内部能力

| 能力 | 调用方 | 作用 |
| --- | --- | --- |
| `mcli_work_set_requirement` | Manager | 发布需求版本 |
| `mcli_work_confirm_requirement` | Manager/用户交互 | 确认需求版本 |
| `mcli_work_request_requirement_revision` | Manager | 请求需求修订 |
| `mcli_work_get_agent_catalog` | Manager | 查询 Agent 清单 |
| `mcli_work_create_temporary_agent` | Manager | 申请临时 Agent |
| `mcli_work_set_plan` | Manager | 发布计划版本 |
| `mcli_work_confirm_plan` | Manager/用户交互 | 确认计划版本 |
| `mcli_work_request_plan_revision` | Manager | 请求计划修订 |
| `mcli_work_get_state` | Manager/Supervisor | 查询权威工作状态 |
| `mcli_work_ask_user` | Manager | 讨论、补充或失败决策所需的通用交互 |
| `mcli_work_pause` | 用户/Manager | 暂停工作 |
| `mcli_work_resume` | 用户/Manager | 恢复工作 |
| `mcli_work_cancel` | 用户/Manager | 取消工作 |
| `mcli_work_decide_failure` | Manager/用户交互 | 处理失败决策 |
| `work_supervisor_execute` | Runtime 内部 | 启动已确认计划的 Supervisor |
| `work_worker_invoke` | Supervisor 经 ToolGateway | 执行单个二级步骤 |
| `work_validate_result` | Supervisor | 运行验证并保存证据 |
| `work_generate_report` | Manager | 生成报告正文 |

上述名称是拟议能力名，最终命名在协议阶段冻结。模型仅看到其角色白名单；`work_supervisor_execute` 和 `work_worker_invoke` 不是给 Manager/Worker 自由调用的子任务接口。模型验证和报告生成由受控 Provider 调用承载，事实提交由 Runtime 完成，不允许模型自行写权威文件。

### 11.3 用户交互

需求确认、计划确认、修订反馈、失败决策和提问采用带 `interactionId` 的交互记录。显式暂停/恢复/取消使用幂等 controlRequestId 的控制命令，不要求再弹确认框，也不能阻塞在一个尚未返回的交互后面。

```json
{
  "interactionId": "interaction-001",
  "workId": "work-001",
  "runId": "run-001",
  "interactionType": "PlanConfirmation",
  "requirementVersion": 1,
  "planVersion": 1,
  "phase": "Pending",
  "requestPayload": {},
  "createdAt": "2026-10-02T09:00:00Z"
}
```

每条交互还必须记录正文哈希、当前期望 stateRevision、通道和 channelGeneration。确认需求前 planVersion 可为 null，尚未执行时 runId 可为 null，不能凭空填 1。通用提问的 answer 不会隐式确认需求或计划。

响应必须包含 `interactionId / requirementVersion / planVersion / subjectHash / channelGeneration / decision / userInput`；actor 从已认证连接确定，而不是采纳模型填写的用户名。示例中的内部确认结果可以省略传输信封，真实跨进程响应不可省略关联字段。

交互阶段按通道分别 compare-and-set：

| 当前阶段 | 可接受来源 | 后续状态与动作 |
| --- | --- | --- |
| `Pending` | 当前 generation 的宿主或独立 CLI 适配器 | 原子写入 `Completed`、用户结果、需求/计划状态及 continuation |
| `Pending` | Runtime 检测到可降级断线 | 原子转 `FallbackToCli` 并递增通道 generation，撤销原 RPC |
| `FallbackToCli` | 当前 generation 的 CLI | 原子写入 `Completed` 及对应业务结果；允许此合法降级结果 |
| `Completed / Cancelled / Superseded` | 任何来源 | 仅写重复/迟到审计，不再改变工作 |

同一响应重发返回原消费结果，不重复弹窗、不重复启动 Supervisor。版本被修订或工作进入 Stopping 时旧交互失效。消费与状态转换必须在同一提交中完成，不能出现“回答已消费、计划尚未确认且无法再消费”。

### 11.3.1 独立 CLI、宿主断线与恢复

- 独立交互式 CLI 从一开始选择本地交互适配器，不先调用不存在的宿主再等待超时；所有确认仍使用相同交互协议。
- 主程序模式优先 ReverseRpc。建议 RPC 等待超时为 300 秒，可配置；超时只是通道故障，不代表用户拒绝。
- 只有 Runtime 确实拥有可交互终端时才允许原子切换到 CLI；常驻 Server、SDK 嵌入或 stdin 重定向不自动读取控制台，保留 Pending，等待重连或返回可恢复的 waiting_for_user 结果。
- 非交互调用不得自动回答 yes。调用方通过 interactionId 提交决策后继续；等待结果必须含 workId、快照与恢复入口信息。
- 重连使用相同 interactionId 去重展示。快照中的待处理交互可恢复面板；若面板已显示，不再重复弹窗。用户授权交互和计划确认交互互不替代。
- 重启后仅重建待处理交互，不自动将 Pending 标为拒绝。FallbackToCli 的通道所有权需要显式移交才能改由宿主消费，旧通道响应始终失效。

### 11.4 事件

事件用于主程序展示和回放，不作为执行控制的唯一事实来源：

```text
work.requirement.updated
work.requirement.status_changed
work.agent_snapshot.created
work.plan.updated
work.plan.status_changed
work.execution.started
work.step.started
work.step.attempt_started
work.step.attempt_completed
work.step.validation_completed
work.step.decision_required
work.step.completed
work.top_level_step.completed
work.execution.paused
work.execution.resumed
work.execution.drained
work.report.created
work.completed
work.partially_completed
work.failed
work.cancelled
work.user_interaction.required
work.user_interaction.completed
```

每个事件包含：

```json
{
  "eventId": "event-001",
  "sequence": 42,
  "workId": "work-001",
  "runId": "run-001",
  "eventType": "work.step.completed",
  "requirementVersion": 1,
  "planVersion": 1,
  "stepId": "1.1",
  "payload": {},
  "committedAt": "2026-10-02T10:00:00Z"
}
```

事件由工作区单写者分配递增序列。主程序发生丢失或乱序时请求权威快照；不能通过 SQLite 投递索引补造缺失事件。

`work.execution.drained` 只表示执行已收尾，不表示用户工作已完成。`work.report.created` 与一个对应 work 终态事件由同一提交产生；终态事件携带 reportRef、reportVersion、reportHash。只有成功的完整报告才发 work.completed，其余结局使用各自事件。

投递语义为至少一次，主程序按 `(workId, sequence)` 去重。快照由单写者在同一提交边界生成，包含 snapshotAtSequence、stateRevision、当前需求/计划/Agent 快照、步骤结果、待处理交互和报告引用。客户端暂停增量应用，安装不倒退的快照，再只应用更大 sequence 的事件；不以回放事件反推一个新的可执行状态。

## 12. 数据权威、工作区与持久化

### 12.1 数据权威

| 数据 | 权威来源 | 派生用途 |
| --- | --- | --- |
| 用户输入与角色消息 | `messages/messages.jsonl` | 多轮上下文、展示和审计 |
| 原子提交与状态迁移 | `state/commits.jsonl` + `state/transitions.jsonl` | 确定哪些正文记录属于同一个已提交事实 |
| 需求版本 | `requirement/versions` | 当前需求读取 |
| Agent Snapshot | `agents/snapshots` | 执行时能力和权限 |
| 计划版本 | `plan/versions` | 当前计划读取 |
| 步骤执行尝试 | `execution/attempts` | 统计、恢复 |
| 验证结果 | `execution/validations` | 步骤状态判定 |
| 工具调用结果 | `state/tool-calls.jsonl` | 审计、去重 |
| 事件 | `events/events.jsonl` | 主程序展示和投递 |
| 报告 | `outputs/reports/{reportVersion}.json` | 最终结果和回放；execution-report.json 为当前报告读取投影 |
| SQLite | 可重建索引 | 查询、投递、加速 |

### 12.2 工作区布局

```text
.work/
└── {workId}/
    ├── requirement/
    │   ├── current.json
    │   └── versions/{version}.json
    ├── agents/
    │   ├── definitions/{agentId}-{version}.json
    │   └── snapshots/{snapshotHash}.json
    ├── plan/
    │   ├── current.json
    │   └── versions/{version}.json
    ├── execution/
    │   ├── runtime.json              # 当前执行位置、心跳的可重建投影
    │   ├── attempts/{stepId}.jsonl
    │   ├── validations/{stepId}.jsonl
    │   └── summaries/{planVersion}/{stepId}-{revision}.json
    ├── messages/
    │   └── messages.jsonl            # 用户、Manager、Worker、验证器消息及调用关联
    ├── state/
    │   ├── commits.jsonl             # 跨文件事务的唯一提交点
    │   ├── transitions.jsonl         # Work/需求/计划/步骤状态变化
    │   ├── continuations.jsonl       # 已提交后待唤醒的角色与消费记录
    │   ├── interactions.jsonl
    │   └── tool-calls.jsonl
    ├── events/events.jsonl
    ├── outputs/
    │   ├── reports/{reportVersion}.json
    │   ├── execution-report.json     # 当前不可变报告的可重建投影
    │   └── execution-report.md
    ├── staging/{attemptId}/          # Worker 隔离候选产物，不是权威状态文件
    └── artifacts/
        ├── objects/{contentHash}     # 验证时的不可变产物快照
        └── requirements.md          # 已提交产物的可读路径示例
```

### 12.3 提交规则

- 版本文件、尝试记录、验证记录和报告正文不可覆盖；
- `current.json` 只能在对应不可变版本文件持久化后更新；
- JSONL 记录必须带提交标记、序列和校验信息；
- 写入采用临时文件替换或 append-only，并完成 flush/fsync；
- 同一工作区由 Runtime 单写者串行提交；跨进程写入必须拒绝；
- SQLite 只有在文件正文提交后才能提交索引；
- SQLite 索引失败不改变业务事实，只影响查询和投递；
- 恢复时先扫描文件最后一个完整提交，再重建或校正 SQLite；
- 尾部半条记录可以截断，但必须写诊断事件，不能用于恢复状态。

### 12.4 跨文件原子提交与恢复边界

单写者和多次 fsync 本身不等于跨文件原子事务。本方案明确使用工作区提交日志，SQLite 不承担提交裁决：

1. 分配 transactionId、nextStateRevision 和本次事件序列，检查 expectedStateRevision。
2. 写入不可变正文，或向相应 JSONL 追加带 transactionId 的准备记录；记录各文件的字节范围、哈希和事件范围，逐个持久化。
3. 最后向 `state/commits.jsonl` 追加引用上述完整数据的 Commit 记录并持久化；**此刻才是唯一业务提交点**。
4. 提交后更新 current.json、runtime.json、报告投影、SQLite 索引及投递游标；这些失败只能延迟展示，不能反向改变已提交事实。
5. 重启只回放具有有效 Commit 的记录；没有 Commit 的准备数据隔离或清理。不能以某个文件“最后一行完整”推断整个事务已完成，也不能用最大版本号猜当前计划。

Commit 存在但其引用的正文丢失、哈希不符或提交链中间损坏时，进入 Recovering 并拒绝新执行，不能静默跳过损坏记录继续，也不能从 SQLite 补造事实。只有未提交尾部允许安全截断。事件只在对应 Commit 存在后对外可见。

每条尝试/验证/消息必须含 workId、runId、planVersion、stepId、attemptId、角色和 transactionId；同名 stepId 在不同计划版本不能相互覆盖。版本正文中的 Published 是发布时值，Confirmed/Superseded 从 transitions 重建，不回写不可变版本文件。

### 12.5 上下文、文件权限与产物提交

多轮恢复不能只靠计划和最终摘要。messages 保存用户补充、角色响应、完整工具请求/结果引用、模型配置版本及未消费 continuation。长上下文可压缩为带源消息范围和哈希的摘要，原始事实保留；确认需求、当前计划、权限和未决失败不能被压缩丢失。不要保存不可用的模型内部推理，只保存实际 API 可见消息和证据。

权威目录 requirement、plan、agents、state、events、execution、messages、outputs 只由 Runtime 写入，Worker 不能通过通用文件工具改计划或状态。Worker 写入 staging 或用户明确批准的业务工作目录，读写路径由 Runtime 规范化并检查符号链接/路径逃逸。业务文件原位修改属于已记录的副作用，验证失败不会自动回滚，重试前必须核对现场。

验证通过后 Runtime 计算内容哈希、保存 artifacts/objects 快照、登记产物引用并提交步骤结果。后续 Worker 即使继续编辑同一路径，也不改变先前验证和报告引用的快照。外部资源用资源 ID、查询证据和 operationId 记录，不假设它们能参加本地文件原子事务。

## 13. 暂停、取消、恢复与幂等

### 13.1 暂停

暂停只阻止新步骤和新尝试启动：

- 已开始的 Worker 调用按取消令牌和超时策略收尾；
- 当前交互可以完成，但完成后不自动启动下一步；
- Supervisor 将暂停原因和当前执行位置写入工作区；
- 恢复必须检查需求版本、计划版本和 Agent Snapshot 仍然有效。

暂停不强制杀死已启动尝试，允许其候选结果和验证事实落盘；Supervisor 不启动新的 Worker、重试或下一步骤。在 Paused 中验证完成可以记入当前步骤结果，但不推进 Work 阶段。恢复时先消费已保存结果/待决策，再继续游标，不能重新执行已成功的步骤。

暂停期间已有 attempt 内部的后续工具调用可在原授权、原超时和有效令牌内继续，直到该尝试收尾；这不允许开启另一个 attempt。用户要求立即停止在途副作用时走取消/撤销令牌，不把“暂停”描述为外部执行已停止。

### 13.2 取消

取消时：

- 未启动的二级步骤标记 `Cancelled`；
- 进行中的调用发送取消信号，但不假设外部副作用已经撤销；
- 未完成交互失效；
- 迟到结果只进入审计记录；
- 报告列出已经完成的产物和可能存在的不确定副作用。

收到取消即提交 Stopping 与取消事实、撤销活动 attempt 的派发令牌，按有限收尾时长等待。外部执行无法停住时保留 Unknown 风险并生成取消报告；禁止宣称所有副作用已撤销。取消后的控制、查询、诊断和报告仍可执行，新的业务工具不可执行。

### 13.3 重启恢复

Runtime 重启按以下顺序恢复：

1. 获取工作区单写者锁；
2. 扫描需求、Agent Snapshot、计划和执行记录；
3. 校验提交序列、校验和以及当前版本；
4. 处理 `PendingCommit`、`Unknown` 和未完成交互；
5. 重建或校正 SQLite 索引；
6. 恢复运行技术状态；
7. 对已确认但未启动的计划保留 PlanConfirmed 及 continuation，默认等待显式恢复；正常确认当场可以推进，重启不自动重放，也不重复确认原计划；
8. 对已成功提交的二级步骤不重复执行；
9. 对结果未知且可能有外部副作用的调用交给 Manager/用户决策；
10. 只有恢复校验通过后才允许继续 Supervisor。

### 13.4 幂等记录

每次调用必须记录：

```text
callId
attemptId
stepId
toolId
argumentsHash
status
result
sideEffectsApplied
stateCommitSequence
```

规则：

- 已完成且 `sideEffectsApplied=true` 的同一 `callId` 直接返回缓存结果；
- `PendingCommit` 先恢复校验，不直接重放；
- `Unknown` 不得盲目重放；
- 查询类工具可以按协议简化去重；
- 非幂等工具必须在提交事实前阻止重复执行。

Completed 包含成功、确定失败和确定拒绝三类已提交响应。对同一 callId 的重传，无论是否产生副作用都返回原结果；`sideEffectsApplied=false` 的确定拒绝不能再次执行。sideEffectsApplied 只表示已确认的副作用事实，不能替代调用完成状态；结果未知仍为 Unknown。

传输重试必须匹配 workId、工具 ID 和 argumentsHash；同 callId 不同参数直接拒绝。一次 Worker 派发可包含多个内层工具调用，分别记录 parentCallId 和 operationId。外层超时不得丢弃已经完成的内层结果；恢复先核验内层副作用，再决定是否可以重试整个步骤。

## 14. 两种运行模式验收

同一改动必须验证两种入口，并使用相同的核心 Work 场景。

本章是实施后的验收要求，**本轮只重构文档，没有运行 CLI/宿主联调，不代表功能已实现或测试已通过**。真实联调固定使用本机配置中的 `deepseek`，默认 `deepseek-v4-pro`，可选 `deepseek-v4-flash`；不读取或抄写 apiKey 到报告。临时脚本、日志和联调产物统一放仓库根 `.tmp/`；下面的 .work 布局在测试时位于该临时测试工作区内。

### 14.1 模式 A：独立应用程序模式

入口：CLI 或 Runtime 自行启动 Work。

最低验证：

1. 输入需求；
2. Manager 生成需求理解；
3. 用户确认需求；
4. Manager 读取 Agent Catalog 并生成两级计划；
5. 用户确认计划；
6. Supervisor 执行至少两个一级步骤和每个步骤的二级步骤；
7. 至少验证一次失败后重试；
8. 生成执行报告和产物；
9. 重新启动后可以查询和回放结果。

### 14.2 模式 B：主程序调用模式

入口：外部宿主或 Client SDK 连接 Runtime。

最低验证：

1. 宿主提供用户输入和 Agent/工具能力；
2. ReverseRpc 完成需求确认和计划确认；
3. 宿主可收到计划、步骤、验证和报告事件；
4. Supervisor 通过统一 ToolGateway 调用 Worker；
5. 断线重连后交互按 `interactionId` 恢复；
6. 宿主不能覆盖 Runtime 工作区事实；
7. 宿主可展示最终报告，但报告正文以 Runtime 文件为准。

### 14.3 最低联调场景

| 场景 | 必须验证 |
| --- | --- |
| 多轮需求讨论 | 同一 Work 连续补充信息，需求版本可追踪 |
| 需求拒绝和修订 | 旧需求只读，新版本重新确认 |
| 计划拒绝和修订 | 旧计划只读，新版本重新确认 |
| Agent 选择 | 选择结果进入 Agent Snapshot 并冻结 |
| 临时 Agent | 权限、有效期、隔离工作区和失败处理 |
| 两级执行 | 只能执行二级步骤，禁止第三级 |
| 工具调用 | Worker 调用经过 ToolGateway，结果可追踪 |
| 验证失败重试 | 记录每次尝试和验证证据 |
| 失败决策 | 跳过、修改计划、取消三条路径至少各验证一次 |
| 暂停恢复 | 暂停不启动新步骤，恢复后从检查点继续 |
| 产物检查 | 文件、报告、事件和数据库索引一致 |
| 断线恢复 | ReverseRpc 重连和重复响应不产生重复副作用 |
| 最终报告 | 完成、部分完成、失败状态与统计一致 |
| 授权批准/拒绝 | 同一写工具分别验证批准与拒绝，拒绝不执行且不自动改用其他 Agent 绕过 |

| 验证器故障 | 只恢复验证，不重新执行已经返回产物的 Worker |
| 重规划 | 在途旧版本失效；新需求重新确认；可复用结果有来源和重新验证 |
| 非交互宿主 | 无终端断线不读取 stdin，重连后只消费一次确认 |
| 报告降级 | Manager 不可用时事实报告可交付；存储失败时不虚报完成 |
| 原子提交故障注入 | 正文已写/Commit 未写、Commit 已写/索引未写两处崩溃恢复一致 |
| 终态重复投递 | 报告引用可解析，事件重复消费不再次执行 |

## 15. 重构实施阶段

### 阶段 1：冻结契约

- 确认 Manager、Supervisor、Worker 职责；
- 确认需求确认和计划确认是两个独立门禁；
- 确认两级步骤 JSON 契约；
- 确认报告状态和完成条件。

**出口条件**：所有状态、角色、字段和门禁无歧义。

### 阶段 2：盘点现有 Work 路径

- 盘点现有 Manager/Worker、计划、任务派发、工具、仓储和事件路径；
- 标记每条路径是否经过 ToolGateway；
- 标记旧状态和新状态的迁移关系；
- 确定旧任务只读迁移或兼容读取边界。

**出口条件**：每个现有入口都有迁移、保留或删除结论。

### 阶段 3：实现需求和计划门禁

- 增加需求版本、需求确认和需求修订；
- 增加 Agent Catalog、Agent Snapshot 和临时 Agent 校验；
- 增加两级计划结构和 `depth <= 2` 校验；
- 增加计划版本和计划确认；
- 删除未确认计划直接执行的路径。

**出口条件**：未确认需求或计划无法启动 Worker。

### 阶段 4：收敛 Supervisor 执行器

- 将二级步骤派发接入统一 ToolGateway；
- 实现超时、`maxAttempts`、取消和幂等；
- 实现程序验证、规则验证和模型验证；
- 实现一级步骤和全局结果汇总；
- 删除绕过 ToolGateway 的第二套执行路径。

**出口条件**：所有 Worker 调用都可通过 `callId` 和 `attemptId` 审计及恢复。

### 阶段 5：实现报告和恢复

- 落地执行尝试、验证记录和报告文件；
- 实现完成、部分完成、失败和取消报告；
- 实现断线、重启、重复响应和未知副作用恢复；
- 重建 SQLite 查询和投递索引。

**出口条件**：仅凭工作区文件可以恢复工作事实和最终报告。

### 阶段 6：双模式验收

- 运行独立应用程序模式；
- 运行主程序调用模式；
- 执行最低联调场景；
- 保存命令、日志、Work ID、Run ID 和产物路径；
- 通过后再拆分后续优化任务。

## 16. 旧 WorkMode 迁移边界

| 旧能力 | 新方案处理 |
| --- | --- |
| 旧任务目录和步骤字段 | 借鉴目录隔离和字段含义，迁移为新需求/计划/执行记录 |
| `PendingRequestId` 等待请求 | 转换为带 `interactionId`、phase、版本和载荷的交互记录 |
| 取消注册表 | 保留为进程内取消技术，取消事实必须写入工作区 |
| 旧执行日志 | 转换为二级步骤尝试、验证、工具调用和事件记录 |
| 心跳、孤儿扫描、停滞检测 | 保留为恢复和安全护栏，不恢复成替代 Manager 的业务状态机 |
| 旧 SQLite 计划和 checkpoint | 只作为迁移输入或只读回放，不作为新执行权威 |
| 覆盖式文件写入 | 禁止沿用，改为不可变版本和原子提交 |
| `MAX(Sequence) + 1` | 禁止沿用，改为单写者序列分配 |
| 关键词确认 | 不迁移，改为确认工具和 Runtime 状态门禁 |
| `dispatch_step` 旁路 | 不迁移为第二执行通道，改为 Supervisor 经 ToolGateway 派发 Worker |
| 无层级任务 | 迁移时生成符合两级结构的计划；无法映射的任务进入人工确认 |

旧任务迁移至少生成新的 `requirementVersion`、`planVersion`、`agentSnapshotHash` 和初始提交序列。迁移失败不得覆盖新工作区。

默认只读回放旧会话；用户要求继续时，在新 workId 下导入可校验的需求/计划候选和证据，重新经过需求及计划确认。不能根据旧 SQLite 字段或自然语言“同意”伪造新方案的确认。表中旧能力是盘点分类，不表示本轮已验证所有旧代码的存在或完成迁移。

## 17. 最终验收标准

本方案只有同时满足以下条件，才能判定 Work 重构完成：

1. 用户需求先经过 Manager 理解并形成结构化需求；
2. 用户明确确认需求后才能进入计划阶段；
3. 计划明确包含一级和二级步骤，且 Runtime 拒绝第三级；
4. Agent 选择、临时 Agent 定义和权限进入不可变 Agent Snapshot；
5. 用户明确确认计划后才能启动 Supervisor；
6. Supervisor 按一级步骤和二级步骤执行，Worker 只执行二级步骤；
7. 所有 Worker 调用经过同一 ToolGateway；
8. 每次尝试都有时限、真实结局和证据；无产物/未验证时明确记录原因，不伪造引用；
9. 验证失败和超时遵守最大尝试次数，未知副作用不盲目重放；
10. 技术失败和业务决策分离，跳过有计划预授权或明确用户决定，修改计划必须重新确认；
11. 一级步骤状态由二级步骤事实聚合，全局状态不能凭模型口头声明完成；
12. 所有步骤结局确定、需求验收通过、无未知副作用且报告持久化后，才可发布 work.completed；存在获准缺口则只能发布部分完成事件；
13. 完成、部分完成、失败、取消都生成准确报告；
14. 进程重启、宿主断线和重复响应不破坏工作事实；
15. 独立应用程序模式和主程序调用模式通过同一核心流程验收。

### 18.2 关键路径逻辑走查

| 输入场景 | 必须得到的状态/产物 | 禁止出现的结果 |
| --- | --- | --- |
| 用户确认需求、确认计划，全部步骤通过 | 逐级汇总、报告原子提交、Completed | 任一确认前执行 Worker |
| 需求/计划被拒绝并修改 | 新版本发布、旧交互失效、重新确认 | 修改已确认正文且静默继续 |
| 可重试验证失败两次、第三次通过 | 三个 attempt、证据完整、步骤成功 | 第四次无授权调用 |
| 工具超时且副作用未知 | Unknown、DecisionRequired、派发停止 | 超时立即重复非幂等操作 |
| 用户跳过失败步骤，其后有依赖 | 标记跳过及阻塞集合、等待处理依赖 | 缺少输入仍派发依赖步骤 |
| CLI 确认、宿主断线降级后确认 | 当前通道消费一次、恢复正确 continuation | FallbackToCli 状态永远无法消费 |
| 需求阶段取消、执行阶段失败 | 对应事实报告，空计划字段允许 null | 已进入终态却没有报告路径 |
| 报告正文及 Commit 成功、SQLite 失败 | 完成事实不回退，恢复后重建索引/投递 | 为补索引再次执行 Worker |
